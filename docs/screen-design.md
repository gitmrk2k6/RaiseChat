## 0. はじめに

### 0.1 本書のゴール

RaiseChat の **画面構成・画面遷移・各画面の責務** を確定させる。
具体的には以下を決める:

- アプリケーション全体の画面構成（3 ペイン構成の根拠を含む）
- ユーザーの認証状態とワークスペース所属状態に応じた **画面遷移**
- 各画面で表示する情報・操作・呼び出される API / WebSocket destination
- モーダル / ダイアログの運用ルール
- 空表示（empty state）の方針

本書は **「frontend の実装に入る前に、画面の責務と境界線を言語化しておく」** ことを目的とする。
ピクセル単位のデザイン指定や色・タイポグラフィの詳細はスコープ外とし、ASCII ワイヤーフレームで「どこに何があるか」「どう動くか」を示す。

## 1. 用語定義

本書で使う用語を先にまとめて定義する。本書中で初出の用語が分からなくなったらここに戻ること。

| 用語 | ひと言で | 補足 |
| --- | --- | --- |
| **画面 (page / screen)** | URL に対応する **1 つの表示単位** | Next.js App Router の `page.tsx` 1 つに対応 |
| **ビュー (view)** | 画面内のひとまとまりの表示領域 | 例: 「メッセージビュー」「スレッドビュー」 |
| **ペイン (pane)** | 同時に並べて表示する固定領域 | 本アプリは PC で 3 ペイン構成（rail / sidebar / main） |
| **モーダル (modal)** | 画面の上に重ねて開く **モーダルウィンドウ** | 開いている間は背後を操作不能にする |
| **ダイアログ (dialog)** | 確認・警告など **小さな判断を求める** ポップアップ | 「削除しますか?」など |
| **ルート (route)** | URL パスのこと | App Router では `app/foo/page.tsx` ⇔ `/foo` |
| **ルートグループ** | URL に出さない **論理的なフォルダ** | Next.js の `(group)` 記法。例: `(auth)` |
| **認可境界 (authorization boundary)** | ログイン要否や所属チェックなど **アクセス可否の切り替え線** | 認証されていないユーザーは `(auth)` 配下しか見られない |
| **rail** | 最左の縦長ストライプ。**ワークスペース切替** に使う | Slack の左端アイコン列に相当 |
| **sidebar** | rail の右、メイン領域の左。**チャンネル / DM 一覧** | |
| **main** | sidebar の右。**メッセージ表示・投稿** の本体領域 | スレッド開時は右ペインを併設 |
| **TopBar** | 画面上部の細い帯。**ワークスペース名 / 検索 / プロフィール** | |
| **composer** | メッセージ入力欄 | 改行可、送信ボタンまたは Enter 送信 |
| **無限スクロール** | 上方向にスクロールすると **過去のメッセージが追加読込** される | カーソルベース。`GET /api/channels/{id}/messages?cursor=...`（[D-1 §5.5.1](api-design.md#551-get-apichannelsidmessages)） |
| **empty state** | 一覧・履歴がゼロ件のときの **空表示** | |

## 2. 全体方針

### 2.1 3 ペイン構成（rail / sidebar / main）

#### 結論

ワークスペース内の主要画面は **rail + sidebar + main** の 3 ペインで構成する。スレッド表示時は main の右側に **rightPane**（4 番目のペイン）を一時的に追加する。

```text
┌──────────────────────────── TopBar ─────────────────────────────┐
│ [Workspace ▾]              [🔍 検索]                  [👤 Me]  │
├────┬─────────────────────┬──────────────────────────────────────┤
│ R  │ Sidebar             │ Main                                 │
│ a  │                     │                                      │
│ i  │ # general           │ ┌──────────────────────────────────┐ │
│ l  │ # random            │ │ チャンネルヘッダ                 │ │
│    │ # dev-backend       │ ├──────────────────────────────────┤ │
│ W1 │                     │ │ メッセージ一覧                   │ │
│ W2 │ Direct Messages     │ │ （無限スクロール）               │ │
│ +  │ - Alice             │ │                                  │ │
│    │ - Bob               │ ├──────────────────────────────────┤ │
│    │                     │ │ [Composer (入力欄)]              │ │
│    │                     │ └──────────────────────────────────┘ │
└────┴─────────────────────┴──────────────────────────────────────┘
```

#### なぜ 3 ペインか

| 観点 | 理由 |
| --- | --- |
| **同時参照** | 「他のチャンネルを見ながら今のチャンネルに投稿」「DM 相手を選びながらメッセージを書く」など、**チャンネル一覧とメッセージ本体を常に並べて見られる** ことが Slack 風 UX の本質 |
| **コンテキスト維持** | 画面遷移なしでチャンネル切替できることで「今どこにいるか」を失わない |
| **rail の独立** | ワークスペースを跨いだ切替は頻度が低いが操作可能であってほしい → 最左の細い rail に分離 |
| **既存実装との整合** | frontend/components/layout/ に [WorkspaceRail](../frontend/components/layout/WorkspaceRail.tsx) / [Sidebar](../frontend/components/layout/Sidebar.tsx) / [TopBar](../frontend/components/layout/TopBar.tsx) が既に存在し、user の UI イメージとも一致 |

#### 採用しなかった案

- **タブ型（複数チャンネルを同時に開く）**: ブラウザのタブと混乱する。Slack 系慣習からも外れる
- **モバイル風 1 画面ずつ**: PC 利用が主のユースケース（業務チャット）に対し、画面切替コストが大きすぎる
- **mail クライアント風 2 ペイン（左: チャンネル一覧 / 右: メッセージ）**: rail を分離しないとワークスペース切替が sidebar の中に押し込まれ視認性が下がる

### 2.2 認証境界による画面グループ分け

#### 結論

URL とアクセス可否を以下の 3 グループに分ける。Next.js App Router の **ルートグループ** で物理的に区切る。

| グループ | URL パターン | アクセス可否 | レイアウト |
| --- | --- | --- | --- |
| **公開** | `/` | 未ログインユーザーも可 | ランディング（簡素） |
| **(auth)** | `/signup`, `/login` | **未ログインのみ** | 中央フォーム、rail / sidebar なし |
| **(workspace)** | `/workspaces/...` | **ログイン必須 + ワークスペース所属チェック** | 3 ペイン構成 |

frontend のルートグループ記法 `(auth)` / 物理パス `workspaces/[workspaceId]/` で実装する（既存 `frontend/app/` 構造と一致）。

#### 認可境界の判定タイミング

| 判定 | タイミング | 違反時の挙動 |
| --- | --- | --- |
| ログイン済みか | `(workspace)` 配下アクセス時のミドルウェア | `/login` へリダイレクト（return-to を保持） |
| 当該ワークスペースのメンバーか | `/workspaces/{wsId}` のサーバー側で API 呼び出し時 | `/workspaces` 選択画面へリダイレクト（403） |
| 当該チャンネルの閲覧権限 | チャンネル詳細 API のレスポンスで判定 | 「アクセス権がありません」画面 → サイドバー再表示 |

[D-1 §1.1 認証ヘッダ](api-design.md#11-認証ヘッダの扱い) と整合させる（401 / 403 の使い分けはサーバー側に従う）。

### 2.3 URL 設計と Next.js App Router の対応

#### 設計原則

| # | 原則 | 例 |
| --- | --- | --- |
| 1 | **URL はリソース指向**（操作は内部状態に逃がす） | `/workspaces/1/channels/5` ⭕ / `/workspaces/1/channels/5/edit` ❌（編集は同じ URL でモーダル表示） |
| 2 | **ID は数値**（[D-1 原則 6](api-design.md#1-設計方針横断ルール)） | `/workspaces/1/channels/5` |
| 3 | **ワークスペースは URL の先頭階層に固定** | 1 ユーザーが複数 WS に所属しても URL でどの WS を見ているか即分かる |
| 4 | **DM ルームはチャンネルと別パス** | `/workspaces/1/dm/7`。Slack 同様、概念を分離 |

#### URL → page.tsx 対応

| URL | App Router ファイル | 認可 |
| --- | --- | --- |
| `/` | `app/page.tsx` | 公開 |
| `/signup` | `app/(auth)/signup/page.tsx` | 未ログインのみ |
| `/login` | `app/(auth)/login/page.tsx` | 未ログインのみ |
| `/workspaces` | `app/workspaces/page.tsx` | ログイン必須 |
| `/workspaces/{wsId}` | `app/workspaces/[workspaceId]/page.tsx` | + WS メンバー必須 |
| `/workspaces/{wsId}/channels/{id}` | `app/workspaces/[workspaceId]/channels/[channelId]/page.tsx` | + チャンネル閲覧権限 |
| `/workspaces/{wsId}/dm/{id}` | `app/workspaces/[workspaceId]/dm/[dmId]/page.tsx` | + DM メンバー必須 |
| `/workspaces/{wsId}/search` | `app/workspaces/[workspaceId]/search/page.tsx` | + WS メンバー必須 |

`/workspaces/{wsId}` は「最初のチャンネル」へリダイレクトする（既存実装 [`page.tsx`](../frontend/app/workspaces/[workspaceId]/page.tsx) と一致）。

### 2.4 スレッドビューの扱い（右ペイン or 独立ルート）

#### 結論

スレッドは **right pane（main の右側に並ぶ第 4 ペイン）** として表示する。**独立ルートにはしない**。

| 選択肢 | 採用 | 理由 |
| --- | --- | --- |
| right pane で開く | ⭕ | 親メッセージのコンテキストを失わない。Slack 慣習。クライアント側 state でトグル管理 |
| 独立ルート（`/threads/{parentId}`） | ❌ | URL シェアは魅力だが、コンテキスト喪失が大きい。MVP では却下 |
| モーダルで開く | ❌ | スレッド内で長文返信を書くケースが多く、モーダル UI には不向き |

ただし、スレッド URL シェア需要が出てきた場合は **クエリパラメータ** で表現する案を残す（例: `/workspaces/1/channels/5?thread=1001`）。これは [10. 未決事項](#10-未決事項) で扱う。

### 2.5 採用しなかった案（全体）

| 案 | 却下理由 |
| --- | --- |
| **モバイルファースト**（最小幅 320px〜） | MVP は PC 業務利用を想定。モバイルは後続検討 |
| **SPA 単一ルート + クライアント遷移のみ** | ブラウザバック / シェア URL の慣習を壊す |
| **タブ型でチャンネル切替** | ブラウザのタブと混乱する |
| **チャンネル URL に名前を使う**（`/workspaces/1/channels/general`） | 名前変更で URL が壊れる。ID 固定で安定 |
| **ワークスペース選択画面を経由しない**（ログイン → 直接デフォルト WS へ） | 複数 WS 所属が前提の Slack 系では選択画面が必要 |

## 4. 画面遷移図

### 4.1 認証フロー

```text
                ┌──────────────────┐
                │  S-01 / ランディング │
                └─────────┬────────┘
                          │ [ログイン] / [サインアップ]
                          ▼
            ┌─────────────────────────────┐
            │   S-03 /login   ←─────→  S-02 /signup
            └────────────┬────────────────┘
                         │ 認証成功
                         ▼
              ┌──────────────────────┐
              │  ワークスペース所属チェック
              └──────────┬───────────┘
              所属あり ↓             ↓ 所属なし or 未選択
                         │             │
                ┌────────▼──┐    ┌─────▼────────┐
                │ 最後に開いた│    │  S-04         │
                │ WS にリダイ │    │  /workspaces  │
                │ レクト      │    │ （選択 / 作成）│
                └────────┬──┘    └─────┬────────┘
                         │              │ WS 選択 / 作成
                         └──────┬───────┘
                                ▼
                ┌──────────────────────────┐
                │  S-05 /workspaces/{wsId} │
                │   → 最初のチャンネルへ      │
                │     リダイレクト          │
                └──────────────┬───────────┘
                               ▼
                ┌──────────────────────────────────────────┐
                │ S-06 /workspaces/{wsId}/channels/{id}   │
                └──────────────────────────────────────────┘
```

### 4.2 ワークスペース内遷移

```text
   ┌──────────────────────────────────────────────────────────┐
   │ 任意の WS 内画面（rail + sidebar + main + TopBar 常時表示）   │
   └──────────────────────────────────────────────────────────┘
        │            │             │              │
   rail │       sidebar       TopBar         main 内
   切替 ▼     チャンネル/DM クリック    ▼          ▼
   ┌────────────┐    ┌──────────────┐  ┌────────┐  ┌─────────────┐
   │ 別 WS の最初 │    │ S-06 or S-07 │  │ 検索   │  │ メッセージ      │
   │ チャンネルへ │    │ への遷移      │  │ S-08   │  │ クリック         │
   └────────────┘    └──────────────┘  └────────┘  │ → スレッド開    │
                                                    │ （右ペイン）    │
                                                    └─────────────┘
```

### 4.3 認可違反時の遷移

| 違反 | 遷移先 | 表示 |
| --- | --- | --- |
| 401 Unauthorized（トークン期限切れ） | `/login?returnTo=<元 URL>` | 「セッションの有効期限が切れました」トースト |
| 403 Forbidden（非 WS メンバー） | `/workspaces` | 「このワークスペースへのアクセス権がありません」トースト |
| 403 Forbidden（非チャンネルメンバー） | 同じ WS の最初の参加チャンネル | 「このチャンネルへのアクセス権がありません」トースト |
| 404 Not Found（チャンネル / DM 削除済） | 同上 | 「指定された場所が見つかりません」トースト |

### 5.1 S-01 ランディング `/`

```text

│                    RaiseChat                       │
│              Slack 風チャットアプリ                  │
```

#### 主要 API / WebSocket

- なし

### 5.2 S-02 サインアップ `/signup`（F-01）

#### ワイヤーフレーム

```text
┌────────────────────────────────────────────────────┐
│                                                    │
│            ┌──────────────────────────┐            │
│            │      アカウント作成        │            │
│            ├──────────────────────────┤            │
│            │ ユーザー ID                │            │
│            │ [______________________]  │            │
│            │ 表示名                    │            │
│            │ [______________________]  │            │
│            │ パスワード                 │            │
│            │ [______________________]  │            │
│            │                          │            │
│            │ [   サインアップ   ]      │            │
│            │                          │            │
│            │ すでにアカウントあり?      │            │
│            │ → ログイン                │            │
│            └──────────────────────────┘            │
│                                                    │
└────────────────────────────────────────────────────┘
```

#### 責務

- 新規ユーザー登録。成功時はログインも完了状態にして `/workspaces` へ遷移

## 6. モーダル / ダイアログ一覧

モーダル / ダイアログは **URL を持たない**（クライアント state で開閉）。表示時は背景を覆い、`Esc` キーで閉じられる。

| # | 名前 | 開く起点 | 関連 F-ID | API |
| --- | --- | --- | --- | --- |
| M-01 | ワークスペース作成 | S-04 の「+ 新しい WS」 | F-03 | `POST /api/workspaces` |
| M-02 | チャンネル作成 | sidebar Channels の `+` | F-04 | `POST /api/workspaces/{wsId}/channels` |
| M-03 | DM 開始 | sidebar DMs の `+` | F-06 | `POST /api/workspaces/{wsId}/dm/rooms` |
| M-04 | メッセージ削除確認 | メッセージの 🗑 | F-07 | `DELETE /api/messages/{id}` |
| M-05 | プロフィール編集 | TopBar 右アバター → ドロップダウン | F-02 | [5.9](#59-プロフィール編集モーダル_modalprofilef-02) |
| M-06 | チャンネル設定 / メンバー | チャンネルヘッダ ⚙️ | F-04 | `GET /api/channels/{id}` 等 |
| M-07 | ログアウト確認 | TopBar → ドロップダウン → ログアウト | F-01 | `POST /api/auth/logout` |

### 6.1 モーダル共通方針

| 観点 | ルール |
| --- | --- |
| 閉じる手段 | `Esc` / 背景クリック / `✕` / キャンセルボタン |
| 入力差分あり時 | 「変更が破棄されます」確認ダイアログを挟む |
| 送信中表示 | 送信ボタンを「送信中…」に変えて二重押下を防ぐ |
| エラー表示 | フォーム上部または該当フィールド直下に表示 |
| URL | 持たない（共有時は親画面の URL を共有） |

### 6.2 削除確認ダイアログ（M-04）詳細

```text
                    ┌──────────────────────────────────┐
                    │   メッセージを削除しますか？      │
                    ├──────────────────────────────────┤
                    │ この操作は取り消せません。        │
                    │ スレッド返信・リアクション・添付も │
                    │ まとめて削除されます。            │
                    │                                  │
                    │              [キャンセル] [削除]   │

```

[D-1 §5.5.3 副作用](api-design.md#553-delete-apimessagesid) と整合: 削除は論理削除で、関連スレッド / リアクション / 添付もまとめて論理削除される旨を user に明示する。

## 8. 状態と空表示（empty state）

「データがゼロ件」のときの表示方針を統一する。すべての一覧表示で **「次に何をすればよいか」を必ず示す**。

| 場面 | empty state |
| --- | --- |
| 所属 WS がゼロ件（S-04） | 「最初のワークスペースを作成しましょう」+ [新規作成ボタン] |
| sidebar Channels がゼロ件 | 「まだチャンネルがありません」+ [作成] |
| sidebar DMs がゼロ件 | 「メンバーに話しかけてみましょう」+ [DM を始める] |
| チャンネル内メッセージがゼロ件 | 「`#<チャンネル名>` の始まりです。最初のメッセージを送ってみましょう」 |
| スレッド返信がゼロ件 | 「最初の返信を投稿しましょう」（親のすぐ下） |
| 検索結果がゼロ件（F-13 追補） | 「『<キーワード>』に一致するメッセージはありませんでした」+ クエリ修正の案内 |
| ロード中 | 各エリアでスケルトンプレースホルダ表示（具体実装は実装フェーズで決定） |

## 9. レスポンシブ方針（MVP）

### 9.1 サポート範囲

| 範囲 | 状態 |
| --- | --- |
| **PC（最小幅 1024px〜）** | ✅ 本 MVP の対象 |
| タブレット（768〜1023px） | 🔄 表示は崩れない範囲で許容（rail / sidebar が狭くなる）。最適化はしない |
| モバイル（767px 以下） | ❌ 本 MVP ではスコープ外。「PC でご利用ください」のメッセージを表示 |

### 9.2 採用しなかった案

| 案 | 却下理由 |
| --- | --- |
| モバイルファースト + レスポンシブ完全対応 | 業務利用想定で MVP のスコープを超える |
| 専用ネイティブ / PWA モバイルアプリ | 同上。後続フェーズで検討 |
