関連: [「Slack 風」の捉え方](why-slack.md) / [機能要件書](functional-requirements.md)

## 1. 概要・目的

### 1.1 背景

業務コミュニケーションの中心が、メールから **ビジネスチャット** に移行して久しい。中でも Slack は、チャンネル設計・スレッド・全文検索・絵文字リアクションを軸に「**情報を整理しながら蓄積する**」体験を確立し、業務チャットのデファクトとなっている。

本プロジェクトでは、お客様から「Slack 風のチャットアプリを作ってほしい」と発注された想定で、**Slack の体験価値**（業務利用前提のチャンネル＋スレッド＋検索＋リアクション＋メンション）を MVP に再現する Web アプリケーション **RaiseChat** を開発する。

「Slack 風」という発注言葉が何を意味するか、他のビジネスチャット（Microsoft Teams / Chatwork / LINE WORKS / Google Chat / Discord / Mattermost）との比較、本プロジェクトが選択する機能スコープの根拠は [「Slack 風」の捉え方](why-slack.md) に整理している。

### 1.2 目的

- 業務チャット利用を前提に、**チャンネル単位での会話**を整理・蓄積できる
- **スレッド機能** で会話を分岐させ、メインの流れを汚さずに深掘り議論できる
- **メッセージ全文検索** で過去の議論を再利用できる
- **絵文字リアクション・メンション** で軽量なフィードバックと注意喚起ができる
- 上記の機能を題材に、**WebSocket リアルタイム通信 / Redis キャッシュ戦略 / 冗長化構成 / 自動デプロイ / Claude Code 自動コードレビュー** を実装・運用する

## 4. 非機能要件

本プロジェクトは RaiseTech **上級編** の課題のため、性能・スケーラビリティ・キャッシュ等の上級編テーマと紐づく要件を明示する。実装方式（STOMP / Redis Pub-Sub 等）は本書では宣言せず、設計フェーズの `docs/realtime-design.md` / `docs/cache-strategy.md` で詰める。

| カテゴリ | 要件 |
| --- | --- |
| **リアルタイム性** | メッセージ送信から受信側クライアントへの表示まで **1 秒以内** にプッシュ配信される |
| **スケーラビリティ** | バックエンドを **複数インスタンスに冗長化**しても、ワークスペース内の全クライアントへメッセージ・リアクション・編集イベントが正しくブロードキャストされる |
| **キャッシュ** | チャンネル一覧・直近 N 件のメッセージ・未読カウンタ等の高頻度参照データはキャッシュ層を経由し、DB ヒット率を下げる。整合性は **書き込み時のキャッシュ無効化または更新** で保つ |
| **性能** | 通常操作（チャンネル切替・メッセージ送信・スクロール）が **2 秒以内** に応答する。1 チャンネル 1 万件のメッセージ蓄積でも検索・表示が劣化しないこと |
| **セキュリティ** | パスワードはハッシュ化（Bcrypt）して保存。JWT 認証により自分のデータのみ操作可能。プライベートチャンネル / DM は所属メンバーのみがメッセージにアクセス可能 |
| **可用性** | バックエンド・キャッシュ・DB それぞれが単一障害点とならない構成を **目標**（後続フェーズで具体化）。学習用途のためコストとのバランスを取る |
| **保守性** | Controller / Service / Repository の層構造に基づく設計とする。WebSocket / REST / 認証の関心事を分離する |
| **互換性** | モダンブラウザ（Chrome / Firefox / Edge / Safari の最新版）で動作 |
| **ストレージ** | 画像・動画は AWS S3（または同等のオブジェクトストレージ）に保存し、アプリサーバーには保持しない |
| **オブザーバビリティ** | 構造化ログを出力し、後続フェーズで CloudWatch 等への集約を行う |

## 5. 画面設計（概要）

サインアップ・ログイン・ワークスペース選択・チャンネル一覧 + メッセージビュー（メイン）・スレッドビュー・DM ビュー・検索・プロフィール編集・ワークスペース管理を主軸とする。詳細は **設計フェーズで `docs/screen-design.md` を作成** する。

---

## 6. データベース設計（概要）

`users` → `workspaces` → `workspace_members` → `channels` → `channel_members` → `messages` → `threads` / `reactions` / `mentions` / `attachments` の階層を想定。DM は専用の `dm_rooms` / `dm_messages` または `channels` のサブタイプとして実装するかを設計フェーズで判断する。詳細は **設計フェーズで `docs/database-design.md` を作成** する。

---

## 7. 技術スタック（概要）

Java / Spring Boot + Next.js (React) + PostgreSQL + Redis + WebSocket（STOMP）を軸に構成する想定（[CLAUDE.md](../CLAUDE.md) に暫定版を記載）。確定版は **設計フェーズで `docs/tech-stack.md` を作成** する。

---

## 8. インフラ構成（概要）

AWS（ECS Fargate + ElastiCache for Redis + RDS + ALB + S3 + CloudFront 等）または Render を候補とする。Ansible によるプロビジョニングの題材としてもどちらが適するかを含め、**設計フェーズ〜実装フェーズで `docs/infrastructure.md` を作成** する。

---

## 9. スコープ外（今回は実施しない）

[「Slack 風」の捉え方 — 第 4.2 節](why-slack.md#42-スコープ外にする機能理由を明示して切る) の結論をそのまま採用する。

- **ボイスチャンネル / ハドル**（Slack の主軸ではなく、WebRTC は本プロジェクトの学習スコープ外）
- **音声・ビデオ通話**
- **カスタム絵文字のアップロード**（標準絵文字リアクション F-11 で体験は再現可能）
- **Bot / 外部サービス連携（GitHub・Webhook 等）**（API 設計と運用が重く、学習主題から逸れる）
- **モバイルネイティブアプリ**（Web で十分）
- **ワークフロー / フォーム自動化**
- **多言語化・国際化**（日本語のみで足りる）

> **注記**: WebSocket によるメッセージのリアルタイム配信はスコープ外ではなく **F-05 の一部として実装する**。
