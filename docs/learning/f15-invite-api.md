# F-15 ワークスペース招待 API 学習ノート

このノートは、F-15 ワークスペース招待 API（PR #60）の実装で身に付けた **設計判断と引き出し** を、後日 1 人で再学習できる質で書き残したものです。前提知識ゼロから読み始めても付いてこられるように章を組んでいます。

このノートは **読む順** に章を並べています。途中で「飛ばしても理解できる章」はありません。各章ともすべて重点章扱いで書いています。

招待機能は一見地味ですが、実は **「セキュリティ」「エラー設計」「冪等性」「並行処理」「再利用の判断」** という、どのアプリでも繰り返し出てくる論点が全部詰まっています。F-15 はそれらを一度に練習できる、おいしい題材でした。

---

## このノートで身に付く 5 つの引き出し

| # | 引き出し | このパターンが役立つ場面 |
|---|---|---|
| 1 | 秘密情報はハッシュで保存する（平文は一度だけ渡す） | トークン・APIキー・パスワードなど「漏れたら困るもの」を DB に持つとき |
| 2 | エラーは「意味」で選ぶ（404 / 403 / 410 / 422） | API のエラー設計全般。「どのステータスを返すか」で毎回迷うとき |
| 3 | 冪等性 ― 何度実行しても同じ結果にする | 「ボタンを2回押した」「リンクを再度踏んだ」を安全に扱いたいとき |
| 4 | 完璧主義をどこで捨てるか（同時実行の割り切り） | 並行アクセスの厳密さと実装コストを天秤にかけるとき |
| 5 | 再利用と結合のバランス（コピーして分ける判断） | 既存コードを使い回したいが、安易に依存させたくないとき |

最後の章でこの 5 つを「AI への指示テンプレ」として再掲します。次に別機能を AI に任せるときに、ここから引いて貼れる形にしてあります。

## はじめに: 招待機能は裏側で何をしているのか

本題に入る前に、招待リンクが実際にどう動くのかを一枚絵で掴んでおきましょう。これが全章の土台になります。

```
[オーナー]                    [サーバー]                  [招待される人]
   │                            │                            │
   │ ① 招待リンクを作って        │                            │
   │    と頼む                  │                            │
   │ ───────────────────────▶  │                            │
   │                            │ ② ランダムな合言葉を作る    │
   │                            │    DB には「合言葉の指紋」   │
   │                            │    だけ保存                 │
   │ ◀─────────────────────── │                            │
   │ ③ 合言葉つきの URL を受取   │                            │
   │                            │                            │
   │ ④ URL を相手に渡す（メール等）─────────────────────────▶ │
   │                            │                            │
   │                            │ ⑤ 「この合言葉で参加したい」 │
   │                            │ ◀─────────────────────── │
   │                            │ ⑥ 指紋を照合して OK なら     │
   │                            │    メンバーに追加           │
   │                            │ ───────────────────────▶  │
   │                            │     参加完了                │
```

この絵の中に、これから学ぶ論点が全部入っています。

- ②の「合言葉の指紋だけ保存」→ **引き出し1（ハッシュ保存）**
- ⑥の「OK なら／ダメなら」の分岐 → **引き出し2（エラーの意味）**
- ⑤を相手が何度も押したら？ → **引き出し3（冪等性）**
- ⑤を同時に大勢が押したら？ → **引き出し4（同時実行）**
- ②の「合言葉を作る」処理はどこから持ってきた？ → **引き出し5（再利用）**

では 1 つずつ見ていきます。

## Chapter 1: 秘密情報はハッシュで保存する

F-15 で最初に効いてくるのが「招待トークン（合言葉）をどう保存するか」です。ここはセキュリティの基本中の基本なので、一番丁寧に書きます。

### Step 1-1: 招待トークンとは何か

招待リンクは、こんな URL です。

```
http://localhost:3000/invite/abcXYZ123...（長いランダムな文字列）
```

この末尾のランダム文字列が **トークン（合言葉）** です。「この合言葉を知っている人＝招待された正規の人」とみなして、ワークスペースに入れてあげます。

つまりトークンは **「鍵」** です。鍵を持っている人はドアを開けられる。だから鍵の扱いを間違えると、本来入れてはいけない人が入れてしまいます。

### Step 1-2: 素朴な実装の落とし穴

一番素直に作ると、こうしたくなります。

> トークンの文字列をそのまま DB の `token` 列に保存し、受諾時に「DB に同じ文字列があるか」を検索する。

動きます。動きますが、**危険** です。なぜか。

DB の中身が漏れる事故は、現実に起こります。バックアップファイルの置き忘れ、SQL インジェクション、運用ミス、内部犯行…。もしトークンを平文（そのままの文字列）で保存していたら、DB が漏れた瞬間に **すべての招待リンクが第三者に使われ放題** になります。

これは「パスワードを平文で保存してはいけない」という有名なルールと、まったく同じ問題です。

### Step 1-3: ハッシュという考え方

そこで **ハッシュ** を使います。ハッシュとは、ざっくり言うと **「元に戻せない一方向の変換」** です。

例え話で言うと、**「食材をミンチにする」** ようなものです。

- 肉と玉ねぎ → ミンチにする → ハンバーグのタネ
- ハンバーグのタネ → 元の肉と玉ねぎに戻す → **不可能**

同じ材料を入れれば必ず同じタネになりますが、タネを見ても元の材料の形には戻せません。

ハッシュも同じです。

- 同じトークン文字列 → ハッシュ化 → 必ず同じ「指紋」になる
- 「指紋」 → 元のトークン → **戻せない**

この「戻せない」性質が鍵です。DB には **指紋（ハッシュ）だけ** を保存します。元のトークンは保存しません。

### Step 1-4: それで照合はできるのか

「元に戻せないなら、どうやって受諾時に照合するの？」と思いますよね。ここがハッシュの巧妙なところです。

受諾のとき、相手は URL から **元のトークン文字列** を持ってきます。サーバーはそれを受け取って、**その場でもう一度ミンチにします**（ハッシュ化します）。

```
受け取ったトークン → ハッシュ化 → 指紋A
DB に保存してある指紋 → 指紋B
指紋A == 指紋B ？ → 一致すれば本物
```

同じトークンからは必ず同じ指紋が出るので、**指紋同士を比べれば本物かどうか分かる**。元に戻す必要は一切ないのです。

これで「DB が漏れても安全」と「正しく照合できる」を両立できます。DB の指紋だけ盗まれても、そこから元のトークンは作れないので、攻撃者はドアを開けられません。

### Step 1-5: 「平文は一度だけ」の原則

ここで重要なのが、**元のトークン（平文）をサーバーが返すのは「発行した瞬間」の一度だけ** という点です。

- 発行 API のレスポンスにだけ、平文トークンと完成した招待 URL を入れて返す
- DB には指紋しか残らないので、後から「あの招待のトークン何だっけ？」と聞かれても **サーバーは答えられない**

これはパスワードや API キーを発行するサービスとまったく同じ挙動です。GitHub で個人アクセストークンを作ると「この画面を離れると二度と表示されません」と言われますよね。あれと同じ思想です。

「後から取り出せない」のは不便に見えますが、**取り出せること自体がリスク** なので、あえて取り出せなくしているのです。

### Step 1-6: 引き出し1「秘密はハッシュで保存」

**引き出し**：DB に保存する「鍵」（トークン・パスワード・APIキー）は、平文ではなく **ハッシュ（指紋）** で保存する。照合は「受け取った値を同じ方法でハッシュ化して指紋同士を比べる」。平文をユーザーに返すのは **発行時の一度だけ** にする。

**AI への指示テンプレ**

> このトークン（招待 / API キー / リセットリンク等）は、DB には **平文ではなく SHA-256 ハッシュで保存** してください。
> - 発行時: ランダムな平文を生成 → ハッシュを DB に保存 → **平文はレスポンスで一度だけ返す**
> - 照合時: 受け取った平文を同じ方法でハッシュ化し、DB の保存値と比較
> - 平文は DB に残さないでください（漏洩時の被害を抑えるため）

## Chapter 2: エラーは「意味」で選ぶ

招待の受諾は、失敗するパターンがたくさんあります。「トークンが間違っている」「期限が切れている」「もう無効にされている」「使いすぎた」…。これらに **どの HTTP ステータスコードを返すか** が、この章のテーマです。

### Step 2-1: HTTP ステータスコードは「結果の意味」を伝える番号

まず前提から。Web の世界では、サーバーは結果を **3 桁の番号** で伝えます。

- `200` 番台 = 成功
- `400` 番台 = **クライアント（呼んだ側）が悪い**
- `500` 番台 = **サーバーが悪い**

この番号は、人間にもプログラムにも「何が起きたか」を一目で伝える共通語です。だから適当に選んではいけません。番号の選び方は **「誰が、なぜ失敗したのか」を正しく表す** ことが目的です。

### Step 2-2: F-15 で使った 4 つの番号

招待 API では次の 4 つを使い分けました。それぞれの「意味」をセットで覚えてください。

| 番号 | 名前 | 意味（一言で） | F-15 での場面 |
|---|---|---|---|
| `403` | Forbidden | 「あなたにはその権限がない」 | オーナー以外が招待リンクを作ろうとした |
| `404` | Not Found | 「そんなものは存在しない」 | でたらめなトークンで受諾しようとした |
| `410` | Gone | 「**昔はあったが、もう無い**」 | 期限切れ・無効化済み・使用上限のトークン |
| `422` | Unprocessable Entity | 「形式は正しいが、値がおかしい」 | 有効期限に -5 時間など変な値を指定した |

特に注目してほしいのが **`410 Gone`** です。これは F-15 で初めて使った、ちょっと珍しい番号です。

### Step 2-3: 404 と 410 の違い ― 「無い」にも種類がある

ここが一番おもしろいところです。`404 Not Found` と `410 Gone` は、どちらも「無い」を表しますが、**ニュアンスが違います**。

例え話で説明します。あなたが友達の家を訪ねるとします。

- **404 の状況**：地図を見て訪ねたが、その住所には **最初から家が無かった**。番地を間違えたのかもしれない。「そんな家、知りませんよ」
- **410 の状況**：確かにそこに家があった。でも **取り壊されて、もう無い**。「ああ、あの家はこの前壊しましたよ。もう来ても無駄ですよ」

招待トークンに当てはめると:

- でたらめな文字列で受諾 → そんなトークンは **最初から存在しない** → `404`
- 正しいトークンだが期限切れ → **昔は有効だったが、もう使えない** → `410`

`410` を返すと、クライアントに「このリンクはもう死んでいる。再取得しても無駄だから、新しい招待をもらってね」という強いメッセージを伝えられます。これが `404` との違いです。

### Step 2-4: なぜ期限切れを 422 にしなかったのか

ここで設計判断が登場します。「期限切れ・無効化・使用上限」を `422`（バリデーション失敗）で返す手もありました。実際、最初はそれも検討します。

でも、このプロジェクトでは **`422` は「リクエストの中身（ボディ）の値がおかしいとき専用」** と決めていました。たとえば「有効期限に -5 を入れた」「名前が長すぎる」のような、**送ってきたデータそのものが不正** なケースです。

一方で「期限切れの招待を受諾しようとした」は、**送ってきたデータ（トークン）は完全に正しい** のです。問題はデータではなく、**サーバー側のリソースの状態**（その招待がもう使えない状態になっている）にあります。

この区別が大事です。

- データが悪い → `422`
- データは正しいが、対象の状態が悪い → `410`

「誰の、何が問題なのか」を正確に表す番号を選ぶ。これがエラー設計の本質です。`422` で何でも返してしまうと、クライアントは「ボディを直せばいいのか？」と勘違いします。`410` なら「ボディは関係ない、リンク自体が死んでる」と正しく伝わります。

### Step 2-5: 403 を「メンバーでない」と「オーナーでない」の両方に使う

もう一つの判断。招待リンクを作れるのは **オーナーだけ** にしました。すると失敗パターンが 2 つ出ます。

- そもそもそのワークスペースのメンバーですらない人 → 拒否
- メンバーではあるが、オーナーではない（ただの一般メンバー）人 → 拒否

この 2 つ、どちらも `403 Forbidden`（権限がない）で返しました。**わざと同じ番号** にしています。

理由は **セキュリティ** です。もし「あなたはメンバーじゃない（404）」「あなたはメンバーだがオーナーじゃない（403）」と細かく区別して返すと、攻撃者に **「このワークスペースに自分が所属しているかどうか」という情報** を与えてしまいます。

「権限がない」ことだけを伝えて、それ以上の内部情報は漏らさない。**エラーメッセージも情報漏洩の経路になりうる**、という視点を持っておくと一段レベルが上がります。

### Step 2-6: 引き出し2「エラーは意味で選ぶ」

**引き出し**：HTTP ステータスは「誰の・何が問題か」を正確に表す番号を選ぶ。`404`（最初から無い）と `410`（昔はあったが消えた）を区別する。「データが悪い（422）」と「対象の状態が悪い（410）」を区別する。権限系は情報を漏らさないため `403` に寄せる。

**AI への指示テンプレ**

> このエンドポイントのエラーを、意味に応じて使い分けてください。
> - 対象が **最初から存在しない**（でたらめな ID / トークン）→ `404`
> - 対象は **存在したが、もう利用できない**（期限切れ・無効化・上限到達）→ `410 Gone`
> - **リクエストボディの値** が不正（範囲外など）→ `422`
> - **権限がない**（非メンバー / 非オーナーの両方）→ `403`（区別すると所属情報が漏れるため同じ番号に寄せる）

## Chapter 3: 冪等性 ― 何度でも安全に

招待リンクは、メールやチャットで共有されます。つまり **同じ人が同じリンクを何度もクリックする** ことが当たり前に起きます。この「何度押されても大丈夫」を保証するのが **冪等性（べきとうせい）** です。

### Step 3-1: 冪等性とは

難しそうな言葉ですが、意味は単純です。

> **冪等性 = 同じ操作を何回やっても、結果が同じになること**

身近な例:

- **エレベーターのボタン**：1 回押しても 5 回押しても、エレベーターは 1 回来るだけ。これは冪等。
- **自動販売機**：100 円を 5 回入れたら、5 回分課金される。これは冪等ではない。

招待の受諾は、エレベーターのボタンであってほしい。**「1 回参加したら、あと何回押しても参加状態は変わらない」** が理想です。

### Step 3-2: 冪等でないと何が困るか

もし受諾を「素直に」作ると、こうなりがちです。

> トークンを照合 → メンバーとして DB に追加 → 完了

これだと、同じ人が 2 回リンクを踏むと **同じワークスペースに 2 回メンバー登録されよう** とします。すると:

- 運が良ければ DB のユニーク制約に弾かれてエラー（500 番台のサーバーエラー）
- 運が悪ければ重複したメンバー行ができてデータが汚れる

どちらにせよ、ユーザーから見たら「2 回目を押したらエラーになった」という嫌な体験です。本人は何も悪くないのに。

### Step 3-3: F-15 での冪等な受諾

そこで、受諾処理にこういう分岐を入れました。

> トークンを照合 → **もう既にメンバーか確認** → メンバーなら何もせず「成功（200）」を返す → メンバーでなければ追加する

ポイントは **「既にメンバーならエラーにせず、しれっと成功を返す」** ことです。

ユーザーから見ると:

- 1 回目クリック → 参加した（200）
- 2 回目クリック → すでに参加してるので、そのまま成功（200）。画面はワークスペースが開くだけ

何度押しても「ワークスペースが開く」という同じ結果になります。これがエレベーターのボタンです。

### Step 3-4: なぜ 409 Conflict にしなかったのか

「既にメンバーなのに受諾した＝重複だから 409 エラーでは？」という考えもあります。Chapter 2 のエラー設計の話とつながりますね。

でもここでは **あえてエラーにしませんでした**。理由は Chapter 2 の DM の話（200/201 切り分け）と同じ思想です。

> 招待リンクを再度踏むのは、ユーザーにとって **異常な操作ではなく、ごく普通の操作** だから。

普通の操作をエラー扱いすると、ユーザーは「自分が何か間違えたのかな」と不安になります。「もう入ってますよ、どうぞ」と成功で返すのが、UX として正しい。

エラーにするか・成功にするかは、**「それはユーザーにとって異常事態か、それとも想定内か」** で決めます。想定内なら成功で受け止める。

### Step 3-5: 「使用回数」を二重カウントしない工夫

冪等性には、もう一段おもしろい話があります。招待リンクには「最大 5 回まで使える」のような **使用回数の上限** を設定できます。

ここで、もし同じ人が 3 回リンクを踏んで、その 3 回とも使用回数を 1 ずつ増やしてしまったら？ 本当は 1 人しか参加していないのに、使用回数が 3 も減ってしまいます。これはおかしい。

なので **「既にメンバーだった場合は、使用回数を増やさない」** ようにしました。実際に新しく参加した人がいたときだけ、使用回数を 1 増やす。

冪等性を「参加状態」だけでなく **「使用回数」にも効かせる** ことで、リンクの消費が正しくカウントされます。冪等性は 1 箇所だけでなく、関連する全部の状態に効かせて初めて完成する、という気付きです。

### Step 3-6: 無効化（revoke）も冪等にする

同じ発想を「招待の無効化」にも適用しました。オーナーが招待リンクを無効化するとき:

- 1 回目の無効化 → 無効になる（204 成功）
- 2 回目の無効化（もう無効なのに、もう一度押した）→ 何もせず、そのまま成功（204）

「既に無効なものをもう一度無効にしてくれと言われたら、何もせず成功を返す」。これも冪等です。状態を変える操作（追加・削除・無効化）はすべて、この「もう目的の状態なら、黙って成功」の形にしておくと安全になります。

### Step 3-7: 引き出し3「冪等性」

**引き出し**：「ボタンを 2 回押す」「リンクを再度踏む」が普通に起きる操作は、**何度実行しても結果が同じ** になるように作る。「すでに目的の状態なら、エラーにせず黙って成功を返す」。状態を持つ副作用（使用回数など）も二重に動かさないよう、関連する全部に冪等性を効かせる。

**AI への指示テンプレ**

> このエンドポイントは、同じユーザーが複数回呼ぶことが普通に起きます。**冪等** に作ってください。
> - 既に目的の状態（参加済み・無効化済みなど）なら、エラーにせず **成功を返す**
> - 付随するカウンタ（使用回数など）は、実際に状態が変わったときだけ更新する
> - 「2 回目以降は何もしないが成功」という形を全ての状態変更操作に適用してください

## Chapter 4: 完璧主義をどこで捨てるか

この章は、エンジニアとして一段成長するための話です。テーマは **「厳密さとコストのトレードオフ」**。

### Step 4-1: 同時に大勢がリンクを踏んだら

招待リンクに「最大 1 回だけ使える」と設定したとします。そこへ、**ほぼ同時刻に 2 人が受諾ボタンを押した** らどうなるでしょう。

サーバーの中では、それぞれの受諾処理がこう動きます。

```
処理A: 使用回数を読む（0 回）→ まだ上限じゃない → 参加させる → 使用回数を 1 に
処理B: 使用回数を読む（0 回）→ まだ上限じゃない → 参加させる → 使用回数を 1 に
```

問題が見えますか? A も B も「使用回数を読む」段階では **まだ 0** なんです。お互いの更新がまだ反映されていない一瞬のスキを突いて、**両方とも「まだ上限じゃない」と判断** してしまう。結果、上限 1 回のはずが 2 人入ってしまう。

これは **競合状態（レースコンディション）** と呼ばれる、並行処理の古典的な落とし穴です。

### Step 4-2: 例えると「最後の 1 個のセール品」

ネット通販で「残り 1 個」の商品を、2 人が同時にカートに入れてレジに進む状況を想像してください。在庫管理を雑に作ると、両方とも「在庫あり」と判定されて、2 人とも購入完了 → でも商品は 1 個しかない、という事故が起きます。

招待の使用回数も、これとまったく同じ構造の問題です。

### Step 4-3: 厳密に防ぐ方法はある

この競合を完璧に防ぐ方法は、ちゃんと存在します。代表的なのは 2 つ。

- **楽観ロック**：データに「バージョン番号」を持たせ、更新時に「自分が読んだときからバージョンが変わってないか」を確認する。変わっていたら「誰かが先に更新した」とみなしてやり直す。
- **条件付き更新**：DB に「使用回数が上限未満のときだけ +1 する」という更新を 1 命令で投げる。DB が原子的（割り込まれない 1 動作）に処理してくれる。

どちらも有効です。では、F-15 ではどうしたか?

### Step 4-4: あえて厳密にしない、という判断

F-15 では、**あえてこの厳密な対策を入れませんでした**。普通に「読む → 判定 → 更新」のシンプルな形にしています。つまり、**ごく稀に上限を 1〜2 回超えるかもしれない** ことを承知の上で、許容しました。

「えっ、バグを放置していいの?」と思うかもしれません。ここがエンジニアリングの面白いところです。判断の根拠はこうです。

- 招待リンクの使用回数が「ぴったり上限で止まる」ことに、**ビジネス上のシビアな要求はない**。上限 5 回のリンクが、超高負荷の一瞬で 6 回使われても、実害はほぼ無い。
- 一方、楽観ロックや条件付き更新を入れると、**コードが複雑になり、テストも難しくなる**。「やり直し処理」のバグを新たに生む risk もある。
- F-15 は学習プロジェクトであり、招待が秒間に何百件も同時受諾されるような負荷は来ない。

つまり **「防ぐコスト」＞「起きたときの被害」** だったので、防がない方を選んだ、ということです。

### Step 4-5: ただし「逃げ道」は残す

大事なのは、**ただ手を抜いたのではない** ことです。この判断をコードのコメントとして明記し、「もし将来、厳密さが必要になったら、楽観ロックか条件付き更新に切り替えられる」という逃げ道を書き残しました。

これが「割り切り」と「手抜き」の決定的な違いです。

- **手抜き**：問題に気付かず、何も考えずシンプルに作る
- **割り切り**：問題を理解した上で、コストと被害を天秤にかけ、**意図的に** シンプルを選び、判断を記録する

「ここは厳密にしていません。理由は◯◯。必要なら△△で直せます」と言える状態にしておくこと。これがプロの割り切りです。

### Step 4-6: 「いつ厳密にするか」の判断軸

では、どういうときに厳密に防ぐべきか。判断軸はこうです。

| 状況 | 厳密にすべきか |
|---|---|
| お金が関わる（在庫・決済・ポイント） | **する**（1 個の超過が実害） |
| 一意性が絶対（ユーザー登録の重複防止） | **する** |
| 多少ズレても実害が小さい（招待回数・閲覧数カウント） | しなくてよい（割り切る） |
| 超高負荷が現実に来る | する |

招待回数は「多少ズレても実害が小さい」に当てはまったので、割り切った。**全部を完璧にしようとすると、いつまでも完成しない**。どこに労力を割くかを選ぶのが設計です。

### Step 4-7: 引き出し4「完璧主義をどこで捨てるか」

**引き出し**：並行処理の競合は「厳密に防ぐ」と「割り切る」の選択肢がある。**防ぐコスト > 起きたときの被害** なら、意図的にシンプルを選んでよい。ただし「割り切った」ことと「必要なら直せる方法」をコメントに残す。お金・一意性が絡むときは厳密に防ぐ。

**AI への指示テンプレ**

> このカウンタ更新（使用回数など）に競合の可能性があります。今回は **厳密なロックは入れず、シンプルな read-modify-write** で実装してください。
> - 理由（多少のズレに実害がない / 高負荷が来ない）をコメントで明記
> - 将来厳密化する場合の手段（楽観ロック or 条件付き UPDATE）もコメントに書き残す
> - ※もしこれがお金・在庫・一意性に関わるなら、逆に厳密なロックを入れてください

## Chapter 5: 再利用と結合のバランス

最後は「既存のコードをどう使い回すか」という、地味だが奥深い判断の話です。

### Step 5-1: 同じ処理が既にあった

招待トークンを作るには「ランダムな文字列を生成する」「それをハッシュ化する」という処理が必要です（Chapter 1 で学んだ通り）。

ところが、このプロジェクトには **まったく同じ処理が既に存在していました**。認証機能（ログイン）で使う「リフレッシュトークン」を作る処理です。リフレッシュトークンも「ランダム生成して、ハッシュで DB 保存」という、招待トークンと瓜二つの仕組みだったのです。

ここで判断が問われます。**「その既存の処理をそのまま呼び出して使い回すべきか?」**

### Step 5-2: 素直に使い回す案の落とし穴

「同じ処理があるなら、それを呼べばいいじゃん。コードを書かずに済む」――DRY（Don't Repeat Yourself：繰り返すな）という有名な原則からすると、これは正しそうに見えます。

でも、ここには落とし穴があります。既存の処理は **「認証機能（auth）」という別の部署のもの** でした。それを招待機能（workspace）から直接呼ぶと、こういう結びつきができます。

```
招待機能 ──依存──▶ 認証機能
```

「招待機能が、認証機能に寄りかかっている」状態です。これの何が問題か。

- 認証機能のトークン生成を、認証の都合で変えたくなったとき、**招待機能にまで影響** が及ぶ
- 「招待」と「認証」という、本来別々の関心事が、コード上で絡まる
- 半年後に「招待のトークンの作り方を変えたい」と思っても、「これ認証で使ってるやつだから、迂闊に触れないぞ…」と動けなくなる

これを **「結合（カップリング）が強い」** と言います。部署同士が癒着している状態です。

### Step 5-3: 例えると「隣の部署の判子を借りる」

例え話で言うと、こういうことです。

あなたの部署で書類に判子が要るとします。たまたま隣の経理部に同じ判子があった。「借りればいいや」と毎回借りに行く。

最初は楽です。でも経理部がその判子を金庫にしまったり、廃止したりすると、**あなたの部署の業務が止まります**。隣の部署の都合に、自分の仕事が振り回される。

それなら、**同じ判子を自分の部署でもう一本作って持っておく** ほうが、長い目で見て自由です。判子 1 本のコストより、「他部署に振り回されない」価値のほうが大きい。

### Step 5-4: F-15 の判断 ― コピーして独立させる

そこで F-15 では、**既存の認証のトークン処理を呼び出すのではなく、招待機能の中に「同じ実装」を持たせる** ことにしました。中身のロジックは認証のものと同じ（ランダム生成＋ハッシュ）ですが、**招待機能専用の道具として独立** させたのです。

```
招待機能 → 招待機能専用のトークン処理（中身は認証と同等だが独立）
認証機能 → 認証専用のトークン処理
```

これで「招待機能は認証機能に依存しない」状態になりました。招待のトークンの作り方を変えたくなっても、認証に気兼ねせず自由に変えられます。

### Step 5-5: 「DRY」と「結合を避ける」のせめぎ合い

ここで重要なのは、これが **「DRY 原則 vs 結合を避ける原則」のトレードオフ** だということです。

- **DRY を優先**：同じコードは 1 箇所に。重複は悪。→ 既存を呼び出す
- **結合回避を優先**：別々の関心事は、コードが似ていても分けておく。→ コピーして独立

どちらも正しい原則ですが、**ぶつかります**。F-15 では「結合回避」を優先しました。判断の根拠は:

- トークン生成のロジックは **数行で、めったに変わらない**（重複してもメンテ負担が小さい）
- 一方で「認証と招待が癒着する」デメリットは **長期的に効いてくる**（自由が奪われる）

「重複のコスト（小）」より「結合のコスト（大）」のほうが大きいと判断したわけです。

逆に言えば、**重複する処理が大きく複雑で、頻繁に変わる** ものなら、DRY を優先して共通化（両方から使える「中立な部署」に置く）すべきです。これも「コストの天秤」で決まります。

### Step 5-6: 「中立な場所に置く」という第三の道

実は選択肢は 2 つではなく 3 つあります。

1. 既存（認証）をそのまま呼ぶ → 結合が強い（不採用）
2. 招待側にコピーして独立 → 重複するが自由（**F-15 で採用**）
3. どちらにも属さない「共通の部署」を作り、認証も招待もそこから使う → 結合せず重複もしない（理想だが、共通部署を作る手間）

3 が一番きれいに見えますが、「共通部署」を作るのも設計判断とコストが要ります。今回はトークン処理が小さかったので、2 で十分と判断しました。もし将来 3 つ目・4 つ目の機能で同じ処理が要るようになったら、そのとき 3 に格上げすればよい。

**最初から完璧な共通化を目指さず、必要になったら共通化する**。これも Chapter 4 の「完璧主義をどこで捨てるか」と通じる発想です。

### Step 5-7: 引き出し5「再利用と結合のバランス」

**引き出し**：既存に同じ処理があっても、それが **別の関心事（別ドメイン）のもの** なら、安易に呼び出して依存させない。処理が小さく変わりにくいなら **コピーして独立** させる方が、長期的な自由度が高い。重複が大きく頻繁に変わるなら共通化を検討。「重複のコスト」と「結合のコスト」を天秤にかけて決める。

**AI への指示テンプレ**

> この処理は既存の <別機能> に似た実装がありますが、**そのまま呼び出して依存させないでください**。
> - <別機能> は別の関心事なので、依存すると将来お互いを変えづらくなります
> - 処理が小さく変わりにくいなら、この機能の中に **同等の実装を独立して持たせて** ください
> - もし重複が大きく頻繁に変わるなら、両者から使える中立な場所への共通化を提案してください
> 判断は「重複のコスト」と「結合のコスト」の天秤で決めてください

## Chapter 6: F-15 で増えた引き出しまとめ

最後に、ここまでの 5 つの引き出しを **AI への指示テンプレ集** として 1 箇所にまとめます。次に別機能を実装するときは、ここから引いて貼ってください。

### 6-1: 引き出し一覧（再掲）

| # | 引き出し | 一行で言うと |
|---|---|---|
| 1 | 秘密はハッシュで保存 | 鍵は指紋にして保存、平文は発行時の一度だけ返す |
| 2 | エラーは意味で選ぶ | 404（最初から無い）/ 410（消えた）/ 422（値が変）/ 403（権限なし） |
| 3 | 冪等性 | 何度押しても同じ結果。既に目的の状態なら黙って成功 |
| 4 | 完璧主義を捨てる | 防ぐコスト > 被害 なら意図的に割り切り、逃げ道を記録 |
| 5 | 再利用と結合の天秤 | 別ドメインの処理は安易に依存させず、小さいならコピーで独立 |

### 6-2: AI への指示テンプレ集

**秘密のトークンを扱うとき**

> トークンは DB に **SHA-256 ハッシュで保存**、平文は発行時に一度だけ返す。照合は受け取った平文を同じ方法でハッシュ化して比較。平文は DB に残さない。

**エラーステータスを決めるとき**

> 最初から無い → 404 / 存在したが利用不可（期限切れ・無効化）→ 410 Gone / ボディの値が不正 → 422 / 権限なし → 403（所属情報を漏らさないため非メンバーと非権限を同じ番号に寄せる）。

**何度も呼ばれる操作を作るとき**

> 冪等に作る。既に目的の状態ならエラーにせず成功を返す。カウンタは状態が実際に変わったときだけ更新する。

**並行処理の競合があるとき**

> 防ぐコストと被害を天秤にかける。実害が小さく高負荷も来ないなら、シンプルな実装で割り切り、理由と将来の厳密化手段をコメントに残す。お金・在庫・一意性が絡むなら厳密に防ぐ。

**既存に似た処理があるとき**

> 別ドメインの処理には安易に依存しない。小さく変わりにくいならコピーして独立させる。重複のコストと結合のコストを天秤にかけ、必要になってから共通化する。

### 6-3: F-01〜F-06 とのつながり

F-15 の引き出しは、これまでのノートと地続きです。

- **冪等性（引き出し3）** は、F-06 の「200/201 切り分け（既存なら返す、なければ作る）」と同じ思想。「普通の操作をエラーにしない」という一貫した態度。
- **エラーは意味で選ぶ（引き出し2）** は、F-02 で学んだ ProblemDetail（RFC 7807）の上に乗っている。「エラーも設計対象」という考えの延長。
- **再利用と結合（引き出し5）** は、F-06 の「既存パターンを伸ばす」のさらに一歩先。「伸ばす（真似る）」と「依存する（呼び出す）」は別物だと気付けたのが成長。
- **割り切り（引き出し4）** は、F-04 / F-05 で何度も出てきた「MVP では◯◯を許容」という判断の、より明確な言語化。

### 6-4: 次に役立つ視点

招待機能で学んだ 5 つは、**ほぼすべてのアプリ機能で再登場** します。

- ログイン・パスワードリセット・API キー発行 → **引き出し1（ハッシュ）**
- あらゆる API のエラー設計 → **引き出し2（意味で選ぶ）**
- 決済・予約・いいね・フォロー → **引き出し3（冪等性）**
- 在庫・カウンタ・ランキング → **引き出し4（割り切り）**
- どの機能でも既存コードの再利用 → **引き出し5（天秤）**

次にどんな機能を AI に任せるときも、「これは F-15 のどの引き出しが効くか?」と自問するクセをつけてください。「ここはトークンだからハッシュで」「ここは何度も押されるから冪等に」と言えるようになると、AI に対して **「何を・なぜ」そう作るのかを指示できる** ようになります。これが上級編で目指す「AI を前提にしてアプリを作る」スタンスそのものです。

## おわりに

F-15 ワークスペース招待は、コード量こそ多くないものの、**セキュリティ・エラー設計・冪等性・並行処理・再利用判断** という、エンジニアリングの「考え方の核」が凝縮された機能でした。

このノートの中で 1 つだけ「絶対に忘れたくないもの」を選ぶなら、Chapter 4 の **「完璧主義をどこで捨てるか」** です。技術的には「全部を厳密に・完璧に」作れます。でも、**限られた時間で何に労力を割くかを選ぶ** ことこそが設計であり、エンジニアの腕の見せどころです。「防ぐコストと被害を天秤にかけ、意図的に割り切り、判断を記録する」――この姿勢は、招待機能に限らず、これから作るすべてのものに効いてきます。

次の機能に進むときは、まず「これは F-15 のどの引き出しが効くか?」を自問するところから始めてみてください。
