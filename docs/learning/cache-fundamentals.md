## 1. そもそも「キャッシュ」って何？

### 1.1 一行定義

> **キャッシュ** = 同じ問い合わせを毎回やらなくて済むように、**結果を手前にコピーして置いておく仕組み**

### 1.2 なぜ要るか（シナリオ）

Slack 風アプリのサイドバーには「自分が参加しているチャンネル一覧」が出ている。
画面を切り替えるたび・サイドバーを開くたびに、同じ問い合わせを DB に投げる:

```
[ あなた ]
   │ サイドバーを開く
   ▼
[ Spring Boot ]
   │ 「このユーザーが参加してるチャンネル一覧ください」
   ▼
[ PostgreSQL ]   ← DB に毎回問い合わせ
   │
   ▼
出力: [#general, #dev, #random]   ← 画面に出る
```

中身ほぼ変わらないのに、毎回 DB を叩くのは無駄。
→ **手前にコピーを置いて、毎回 DB に行かなくて済むようにする**。

### 1.3 イメージ

```
[ あなた ]
   │
   ▼
[ Spring Boot ]
   │  まず Redis を見る → あればそれを返す（速い）
   │  なかった時だけ DB に聞く
   ▼
[ Redis ]   ← 手前のコピー置き場
   │
   ▼
[ PostgreSQL ]   ← 本物。Redis が消えても再構築できる
```

### 1.4 🔴 マスト

- 「キャッシュは手前にコピーを置いておく仕組み」と言える
- 「本物は DB、Redis は派生（消えても作り直せる）」が区別できる

## 2. Redis と DB は何が違うのか

「手前のコピー置き場」になぜ **Redis** を使うのか。

### 2.1 比較表

| | PostgreSQL（本物の DB） | Redis（手前の置き場） |
|---|---|---|
| データの形 | テーブル（行と列） | **key と value のペア**（辞書のようなもの） |
| 保存場所 | ディスク（HDD/SSD） | **メモリ（RAM）** |
| 速度 | ミリ秒（ms）単位 | **マイクロ秒（μs）単位** ← 約 1000 倍速い |
| 得意なこと | 複雑な検索・JOIN・集計 | 単純な「この key の値ちょうだい」 |
| 消えたら | 困る（本物が消える） | **困らない**（DB から作り直せる） |
| RaiseChat での役割 | 本物の保管庫 | 手前の作業机 |

### 2.2 key と value のイメージ

Redis は「テーブル」じゃなくて、辞書みたいなペアで保存する:

```
key                                      value
─────────────────────────────────────    ─────────────────────────────
cache:user:123                       →   { name: "Mrk", avatar: "..." }
cache:workspace:5:channels           →   [ 1, 2, 3, 5, 10 ]
unread:user:12:channel:5             →   3
```

key を指定して取りに行くだけ。SQL の `WHERE name LIKE '...'` みたいな複雑な検索はできない。**そのかわり超速い**。

### 2.3 「派生キャッシュ」の意味

```
   ┌─────────────────┐                    ┌─────────────────┐
   │   PostgreSQL    │  ──コピー作成──▶   │     Redis       │
   │  （本物・正本）  │                    │  （コピー・派生）│
   └─────────────────┘                    └─────────────────┘
        絶対消えない                          消えてもいい
        消えたら大事件                        再起動で消えて OK
                                              → 次の問い合わせで作り直す
```

D-3 設計書の原則: **「DB がソース・オブ・トゥルース、Redis は派生キャッシュ」**。

### 2.4 🔴 マスト

- Redis = **メモリに置く / key-value 形式 / 速い / 単純取得が得意**
- 「Redis が消えても DB から作り直せる」と言える

## 3. cache-aside ＝ アプリ側で書く「キャッシュの使い方パターン」

### 3.1 まず「これは何ではない」

- ❌ Spring の機能名ではない（`@Cacheable` とは違う）
- ❌ Redis の機能でもない
- ✅ **アプリが自分で書く「キャッシュの使い方のパターン」の名前**

つまり、Spring Boot のコードの中で「まず Redis を見る、無ければ DB に行く、取れた結果を Redis にも入れておく」という手順を自分で書く方式のこと。

### 3.2 読み取りの流れ（シナリオ）

ユーザー 123 のプロフィール情報を取りたい:

```
                       ┌──────────┐
                       │   APP    │
                       └────┬─────┘
                            │
              ① cache:user:123 ある？
                            │
                  ┌─────────┴─────────┐
                  ▼                   ▼
            あった (hit)         なかった (miss)
                  │                   │
                  │            ② DB に SELECT
                  │                   │
                  │            ③ Redis に保存
                  │               (TTL 1 時間 とか)
                  │                   │
                  └─────────┬─────────┘
                            ▼
                         結果を返す
```

### 3.3 用語

- **hit**（ヒット）= Redis に **あった**
- **miss**（ミス）= Redis に **無かった** → DB に行く羽目になった

### 3.4 疑似コード

```python
def get_user(user_id):
    key = f"cache:user:{user_id}"
    value = redis.get(key)         # ① まず Redis
    if value is None:              #   miss だったら
        value = db.query(...)      # ② DB から取る
        redis.set(key, value, ttl=3600)  # ③ Redis に置いておく
    return value
```

たった 4 行のパターン。これだけ。

### 3.5 この戦略の良さ

| | うれしい点 |
|---|---|
| シンプル | アプリ側で 4 行書くだけ |
| Redis が落ちても OK | `redis.get()` を try-catch で握れば、DB 直接にフォールバックできる |
| 無効化が明示的 | 「いつキャッシュを消すか」をアプリが自分で決められる（§4 で扱う） |

### 3.6 🔴 マスト

- cache-aside = **「まず Redis → なかったら DB → DB の結果を Redis に置く」** という読み取りパターンと言える
- hit / miss の意味が言える

## 4. 無効化（invalidation）— なぜ DELETE するのか

### 4.1 まず「これは何ではない」

- ❌ Redis を止めるわけではない
- ❌ アプリを止めるわけでもない
- ✅ **「Redis の中身がもう古いので消す」操作のこと**

### 4.2 何が困るのか

```
時刻 T1:  Redis: cache:user:123 = { name: "Mrk" }    ← キャッシュあり
時刻 T2:  あなたがプロフィール名を "Keisuke" に変更
時刻 T3:  DB: name = "Keisuke" になった
          Redis: { name: "Mrk" } のまま ←← まずい！古い！
時刻 T4:  別のユーザーがあなたのプロフィールを見る
          → Redis から "Mrk" が返ってくる（古い）
```

### 4.3 解決: DB 更新時に Redis を「消す」

DB を更新したら Redis の該当 key を DELETE。
次に誰かが読みに来たら miss → DB から取得 → Redis に再格納 → 自動的に最新に。

### 4.4 なぜ「DELETE」？「SET 上書き」じゃダメ？

```
[ SET 上書き方式の問題 ]
時刻 T1:  A さん: DB を name="X" に更新
時刻 T2:  B さん: DB を name="Y" に更新  ← ほぼ同時
時刻 T3:  DB の最終値: name="Y"
時刻 T4:  A さんの SET が遅れて到着 → Redis = "X"  ←← DB と不一致！

[ DELETE 方式 ]
時刻 T1:  A さん: DB を "X" に更新 → Redis DEL
時刻 T2:  B さん: DB を "Y" に更新 → Redis DEL
時刻 T3:  Redis: 空
時刻 T4:  次に読んだ人 → miss → DB から "Y" を取って Redis に置く ✅
```

→ **DELETE は「次に読む人に最新版を取り直させる」** ので、競合が起きない。

### 4.5 「いつ消すか」のトリガ表（D-3 §6.2 抜粋）

| 起点イベント | 消す key |
| --- | --- |
| プロフィール更新 | `cache:user:{自分のid}` |
| ワークスペース参加 | `cache:user:{id}:workspaces` / `cache:workspace:{id}:members` |
| チャンネル作成 | `cache:workspace:{wsId}:channels` |
| 既読更新 | `unread:user:{id}:channel:{id}` を 0 |
| ログアウト | `jwt:blacklist:{jti}` を SET |

これがチェックリストになる（実装時の「キャッシュ消し忘れバグ」防止）。

### 4.6 🔴 マスト

- 無効化 = 「もう古いから Redis から **消す**」操作と言える
- なぜ「上書き」じゃなくて「削除」なのか、ひと言で言える

## 5. カウンタ系の例外 — 未読数

### 5.1 まず「これは何ではない」

- ❌ §4 までの cache-aside の流れに乗らない
- ❌ DELETE で消すパターンでもない
- ✅ **Redis のカウンタを直接 +1 / -1 / 0 する** ／ DB は別途持つ

### 5.2 シナリオ（Alice / Bob / Carol の 3 人）

```
チャンネル #general に Alice / Bob / Carol の 3 人
全員、全メッセージ既読の状態からスタート

時刻 T1: Alice がメッセージを送信
   Alice の未読: 0    ← 自分が送ったので増えない
   Bob の未読:   1    ← +1
   Carol の未読: 1    ← +1

時刻 T2: Bob が画面を開いて読んだ
   Alice の未読: 0
   Bob の未読:   0    ← 0 にリセット
   Carol の未読: 1

時刻 T3: Carol がメッセージを送信
   Alice の未読: 1    ← +1
   Bob の未読:   1    ← +1
   Carol の未読: 0
```

やっている操作は **「+1 する」か「0 にする」だけ**。

### 5.3 Redis にはこう入っている

```
unread:user:Bob:channel:general    = 1
unread:user:Carol:channel:general  = 1
```

数字だけ。

### 5.4 なぜ cache-aside じゃダメか

「Bob のチャンネル #general の未読数」を DB で出そうとすると、サイドバー開くたびに:

1. 「Bob が最後に読んだメッセージはどれ？」を DB に聞く
2. そのチャンネルで、それより新しいメッセージの **件数を数える**

これを **チャンネル 50 個 × サイドバー開くたび** やる。重い。

→ Redis に「いまの未読数」をそのまま持っておく作戦に切り替える。

### 5.5 用語: INCR / DECR

| コマンド | 意味 |
| --- | --- |
| `INCR key` | その key の数値を **+1**（無ければ 0 から始めて 1 にする） |
| `DECR key` | **-1** |
| `SET key 0` | 0 にリセット |

→ **数の増減専用の高速コマンド**。Redis の中で原子的に行われるので、100 人が同時にメッセージ送っても数がズレない。

### 5.6 Redis が飛んだら未読数も消える？ → DB から再構築できる

```
Redis が飛んだ → unread:user:Bob:channel:general が消えた

復旧方法:
  DB の read_states に「Bob はチャンネル general の id=42 まで読んだ」と記録あり
  → DB で COUNT(*) WHERE channel_id=general AND id > 42 を 1 回だけ走らせる
  → 結果を Redis に SET → 以降は INCR/DECR で運用継続
```

つまり **DB は「最終既読位置」だけ持ち、未読数そのものは Redis が正本に近い形で持つ** という分担。

### 5.7 戦略の使い分け（重要）

| 対象 | 戦略 | 書き込み時の操作 |
| --- | --- | --- |
| ユーザー情報、メンバー一覧、チャンネル一覧、直近メッセージ ID リスト | **cache-aside** | DELETE |
| 未読数 | **カウンタ直接運用** | INCR / DECR / SET 0 |
| プレゼンス、JWT ブラックリスト、レート制限 | **TTL 任せ** | SET + TTL（自動消滅） |

### 5.8 🔴 マスト

- 「カウンタ系（未読数）だけは cache-aside の例外」と言える
- 理由：毎回 COUNT すると重いから、Redis を正本に近い形で持つ
- INCR = +1、DECR = -1（数の増減コマンド）

## 6. TTL（自動的に消える期限）

### 6.1 まず「これは何ではない」

- ❌ アプリの寿命ではない
- ❌ DB に保存される期間でもない
- ✅ **Redis 上で「この key、◯秒経ったら勝手に消えてね」と Redis に教える期限**

### 6.2 シナリオ

```
時刻 T1: cache:user:123 をセット (TTL = 1 時間)
時刻 T2: 30 分経過 ─ まだ Redis にある
時刻 T3: 1 時間経過 ─ Redis が自動的に消す（誰も触ってないのに）
時刻 T4: 誰かが get → miss → DB から取って Redis に置き直す
```

→ **Redis 側が勝手に時計を見て消してくれる**。

### 6.3 なぜ TTL が要るのか（3 つ）

| 理由 | 例 |
| --- | --- |
| ① 無効化を忘れたバグの **安全網** | プロフィール更新時の DELETE をうっかり書き忘れても、1 時間後には消える |
| ② **使われなくなった key** がメモリを圧迫するのを防ぐ | 退会したユーザーの cache:user:999 を消す処理を忘れても、TTL で勝手に消える |
| ③ **そもそも期限つきのデータ** はそれ自体が TTL と合う | ログアウトしたトークンのブラックリスト → トークン期限と同じ TTL で自動掃除 |

### 6.4 D-3 で決めた TTL ポリシー

| 区分 | TTL の長さ | 当てはまる対象 | なぜその長さ |
| --- | --- | --- | --- |
| **短命** | 60〜90 秒 | プレゼンス、レート制限 | 揮発性で良い・短時間で勝手に消えていい |
| **中** | 1 時間 | ユーザー情報、メンバー一覧、チャンネル一覧 | 整合性は緩くて OK・基本は DELETE で消す、TTL は安全網 |
| **長** | 24 時間 | 直近メッセージ ID リスト | 高頻度で読まれる・あまり消したくない |
| **トークン連動** | トークン残存時間 | JWT ブラックリスト | トークン自体が切れたら一緒に消えれば OK |
| **TTL なし** | 期限なし | 未読カウント（§5）| 明示的に SET 0 で更新する |

### 6.5 プレゼンスの TTL は「ハートビート」式

```
WebSocket 接続中、クライアントは 30 秒ごとに「いるよ」と送る
→ サーバーは presence:user:12 を SET (TTL = 90 秒) で上書き

もし 90 秒以内に次の「いるよ」が来なかったら
→ Redis 側で自動失効 → そのユーザーは offline 扱い
```

→ TTL を **「生存確認の心拍」** として使うパターン。🟡 知っとく。

### 6.6 🔴 マスト

- TTL = 「Redis が時計を見て勝手に消す期限」
- TTL は **無効化の安全網**（DELETE 忘れのバグを救う）
- 整合性が緩いものほど長い TTL、揮発性のものほど短い TTL

## 7. Pub-Sub と Redis の共有（重点章 — ここが詰まったところ）

振り返り学習で「微妙にわからん」となった章。**ここを一番丁寧に書き直す**。

### 7.1 何の話なのか（背景）

D-2（[realtime-fundamentals.md §6〜§7](realtime-fundamentals.md)）で出てきた **Redis Pub-Sub** を覚えていますか？

> Spring Boot を 2 台に冗長化したとき、片方のインスタンスが受け取ったメッセージをもう片方にも伝える必要がある。
> そのために Redis の **Pub-Sub 機能** で「あるチャネルに publish したら、subscribe してる全員に届く」仕組みを使う。
> RaiseChat ではワークスペースごとに 1 本のチャネルを切る → `ws:workspace:5` のような名前。

これが D-2 の話。

ここで疑問が出る:

> **キャッシュも Redis を使う。Pub-Sub も Redis を使う。同じ Redis を共有していいの？**

これが D-3 §2.4 で決めた話。

### 7.2 まず「これは何ではない」

D-3 で採用した方式は:

- ❌ **別の Redis インスタンスを立てた** わけではない
- ❌ **Redis の中で物理的にデータベースを分けた** わけでもない（後述の「論理 DB index」も採らない）
- ✅ **同じ 1 つの Redis を共有する。ただし key の頭文字（prefix）でデータの種類を区別する**

### 7.3 「同じ Redis を共有する」とはどういうこと？

docker-compose に `redis:7` のコンテナが 1 つだけ立っている。これに対して:

- **キャッシュ層**（Spring Boot のキャッシュ機能）が `GET cache:user:123` のように key 操作
- **WebSocket 層**（Spring Boot のリアルタイム機能）が `PUBLISH ws:workspace:5 ...` のように Pub-Sub 操作

→ どちらも **同じ Redis に対して** 操作している。

```
            ┌─────────────────────────────────────────┐
            │              Redis (1 つ)                │
            ├─────────────────────────────────────────┤
            │  cache:user:123              → 値        │
            │  cache:workspace:5:members   → メンバー   │
            │  unread:user:12:channel:5    → 3        │
            │  presence:user:12            → online   │
            │  jwt:blacklist:abc           → 1        │
            │  rate:login:ip:1.2.3.4       → 4        │
            │  ws:workspace:5              → Pub-Sub  │ ← D-2 で決めたチャネル
            └─────────────────────────────────────────┘
                      ↑                       ↑
                      │                       │
            キャッシュ用に GET/SET      Pub-Sub 用に PUBLISH/SUBSCRIBE
            （Spring Boot の          （Spring Boot の
              キャッシュ層）             WebSocket 層）
```

### 7.4 衝突しないの？

ここがピンと来づらいポイント。

**結論: 衝突しない。理由は「key の頭の prefix が違うから」**。

key を全部書き出すと:

| 用途 | key の例 | 操作の種類 |
| --- | --- | --- |
| キャッシュ（ユーザー情報） | `cache:user:123` | GET / SET / DEL |
| キャッシュ（メンバー一覧） | `cache:workspace:5:members` | GET / SET / DEL |
| 未読カウンタ | `unread:user:12:channel:5` | INCR / DECR / SET |
| プレゼンス | `presence:user:12` | SET（TTL 付） |
| JWT ブラックリスト | `jwt:blacklist:abc` | SET（TTL 付） |
| Pub-Sub チャネル | `ws:workspace:5` | PUBLISH / SUBSCRIBE |

`cache:workspace:5:members` と `ws:workspace:5` は **文字列として違う key** なので、Redis 内で別物として扱われる。ぶつからない。

> 例えるなら「同じマンションに住んでるけど部屋番号が違う」状態。住所（マンション）が同じでも、号室が違えば別の家。

### 7.5 D-3 §2.4 で決めた prefix 一覧

| prefix | 用途 |
| --- | --- |
| `cache:` | 派生キャッシュ（DB から再構築可） |
| `unread:` | 未読カウンタ（§5 のやつ） |
| `presence:` | オンライン状態（§6 のハートビート） |
| `jwt:` | JWT 関連（ブラックリスト等） |
| `rate:` | レート制限カウンタ |
| `lock:` | 分散ロック（将来用） |
| `ws:` | **Redis Pub-Sub チャネル名**（D-2 で確定） |

実装時は **必ずこの prefix を付ける**。バラバラに付けると、後から「これは何のための key だっけ」が分からなくなる。

### 7.6 ほかにどんな分け方があったか（採らなかった案）

3 つの選択肢のうち、prefix 方式を採った理由を整理しておく。

#### 案 A. 別の Redis インスタンスを立てる

```
┌──────────────────┐     ┌──────────────────┐
│ Redis #1（キャッシュ用）│   │ Redis #2（Pub-Sub 用）│
└──────────────────┘     └──────────────────┘
```

- **メリット**: 完全に分離される
- **デメリット**: docker-compose に 2 つのコンテナ・運用ドキュメントも 2 つ・本番でも 2 台・モニタリングも 2 セット → **コストが高い**
- → **採らない**

#### 案 B. 論理 DB index で分ける

Redis には「1 つのインスタンスの中に **0〜15 番の名前空間** を切る」機能がある。これを **論理 DB index** と呼ぶ。

```
1 つの Redis インスタンスの中:
   ┌──────────────────────────────────────┐
   │   DB index 0  ← キャッシュ用に使う       │
   │     cache:user:123 = ...              │
   │     cache:workspace:5:members = ...   │
   │                                        │
   │   DB index 1  ← Pub-Sub 用に使う       │
   │     ws:workspace:5 のチャネル          │
   └──────────────────────────────────────┘
```

接続時に `SELECT 0` / `SELECT 1` のように番号を指定して切り替える。

- **メリット**: 同じインスタンスを「論理的に分けられる」
- **デメリット**:
  - 接続を **2 種類使い分ける必要がある**（キャッシュ用接続と Pub-Sub 用接続）
  - 「あ、今どっちの index に居るんだっけ？」が起きやすい
  - 設定ミスで本番事故になりやすい
  - 視認性も悪い（key の見た目だけで「これはキャッシュ」「これは Pub-Sub」が分からない）
- → **採らない**

#### 案 C. key prefix で分ける（採用）

key の頭文字でカテゴリーを区別する。接続は 1 種類のままで OK。

- **メリット**:
  - 接続は 1 本だけ
  - key を見れば一目で用途が分かる（`cache:` / `unread:` / `ws:` 等）
  - 設定ミスのリスクが小さい
- **デメリット**:
  - 全員が prefix ルールを守る必要がある（ルール違反の `random_key` を SET されると分類が壊れる）→ コードレビューで防ぐ
- → ✅ **採用**

### 7.7 ここを腹落ちさせるための 1 行イメージ

> **Redis は 1 つの大きな倉庫。倉庫の中に置く荷物に「種類別のシール」（prefix）を貼って区別する。キャッシュ用の荷物には `cache:` のシール、Pub-Sub 用の荷物には `ws:` のシール。**

倉庫を 2 つに分ける（案 A）でも、倉庫の中に仕切り板を入れる（案 B 論理 DB index）でもなく、**シールで区別する** のが D-3 の選択。

### 7.8 🔴 マスト

- 「キャッシュと Pub-Sub は **同じ Redis を共有している**」と言える
- 「key の頭の prefix（`cache:` / `ws:` 等）で衝突を防いでいる」と言える

### 7.9 🟡 知っとく

- 論理 DB index という機能が Redis にあるが、RaiseChat では採らなかったこと
- 別 Redis インスタンスを立てる案もあるが、運用コストで採らなかったこと

## 8. うまくいかない時の話

最後に **失敗パターン** を 2 つ。両方とも D-3 では「MVP では深入りしない」と決めた話なので軽め。

### 8.1 cache stampede（雪崩 / 突進）

#### 何が起きるか

```
ある人気の key（例: cache:channel:5:recent）の TTL が切れた瞬間…

時刻 T0:  TTL 切れ。Redis 上から消える
時刻 T0 直後:
   ユーザー A: get → miss → DB へ取りに行く
   ユーザー B: get → miss → DB へ取りに行く
   ユーザー C: get → miss → DB へ取りに行く
   ユーザー D: ...（同時 100 人）
   
→ DB に同じクエリが一気に殺到！
```

「同時に大量 miss して DB に殺到する」現象を **cache stampede（雪崩）** または **thundering herd（家畜の群れの突進）** と呼ぶ。

#### D-3 での対応: MVP では許容（深入りしない）

| 対策案 | 採否 |
| --- | --- |
| 同時 miss 時、1 人だけ DB に行かせて他は待たせる（SETNX ロック）| ❌ MVP では採らない |
| TTL を **長め（24h）** にして、そもそも切れる頻度を下げる | ✅ 採用（直近メッセージ ID リスト） |
| MVP では許容、性能テストで顕在化したら対策を入れる | ✅ 採用 |

→ ⚪ **雑学レベル**。「こういう問題があるんだな」程度で OK。

### 8.2 Redis ダウン時のフォールバック

#### 基本パターン: try-catch で握る

```
get_user(123) のとき:
   try:
       Redis.get(cache:user:123)
   catch (Redis 接続エラー):
       ログだけ書く（例外は上に投げない）
   
   ← Redis から取れなかった場合の続きを実行
   DB.query(...)
   
   return 結果
```

→ **Redis が落ちてもアプリは動く**。レイテンシは劣化するが、サービスは止まらない。

#### 機能ごとの影響度

| 機能 | Redis ダウン時の挙動 |
| --- | --- |
| ユーザー情報・各種一覧 | DB 直接でいけるので問題なし（遅くなるだけ） |
| 未読数 | 一時的に **未読バッジを諦める**（出ない or `-` 表示）|
| プレゼンス | 全員 offline 表示 |
| JWT ブラックリスト | **チェックをスキップ**（ログアウトしたトークンが期限まで生きてしまう。許容） |
| レート制限 | スキップ |

→ どれも「データが消えても致命的にならない」設計。これが「Redis は派生キャッシュ」（§2.3）の真の意味。

### 8.3 🟡 知っとく

- cache stampede という単語と「TTL 切れの瞬間に DB に殺到する問題」が結びつけば OK
- Redis ダウン時は **try-catch で握って DB 直行** が基本パターン

## 9. チートシート

### 9.1 ひと言まとめ

| 概念 | ひと言 |
| --- | --- |
| キャッシュ | 同じ問い合わせを毎回やらなくて済むよう、結果を手前にコピー |
| Redis | 速い key-value 形式の置き場。メモリ上。消えても DB から作り直せる |
| cache-aside | 「まず Redis → なかったら DB → DB の結果を Redis に置く」パターン |
| hit / miss | Redis にあった / 無かった |
| 無効化 | 古くなったキャッシュを Redis から **消す** 操作 |
| なぜ DELETE か | SET 上書きだと競合が起きる。DELETE は次の人に DB から取り直させる |
| カウンタ系の例外 | 未読数は cache-aside ではなく INCR/DECR で直接運用 |
| TTL | Redis が時計を見て勝手に消す期限。無効化の安全網 |
| prefix 分離 | 同じ Redis をキャッシュと Pub-Sub で共有。key の頭で区別 |
| cache stampede | TTL 切れの瞬間に DB へ殺到する問題（MVP では許容） |
| Redis ダウン時 | try-catch で握って DB 直行 |

### 9.2 戦略の使い分け表（実装時の判断軸）

| 対象 | 戦略 | TTL | 書き込み時の操作 |
| --- | --- | --- | --- |
| ユーザー情報・メンバー一覧・チャンネル一覧 | cache-aside | 1h | DELETE |
| 直近メッセージ ID リスト | cache-aside | 24h | DELETE（編集 / 削除時）/ 追記（送信時） |
| 未読数 | カウンタ直接運用 | なし | INCR / DECR / SET 0 |
| プレゼンス | TTL 任せ | 90s | SET（ハートビートで上書き） |
| JWT ブラックリスト | TTL 任せ | トークン残存時間 | SET |
| レート制限 | TTL 任せ | 60s | INCR |

### 9.3 key 命名規則

```
<prefix>:<resource>:<id>[:<sub-resource>[:<id>]]
```

- すべて小文字、区切りは `:`、ID は数値、単数形

### 9.4 prefix 一覧

| prefix | 用途 |
| --- | --- |
| `cache:` | 派生キャッシュ |
| `unread:` | 未読カウンタ |
| `presence:` | オンライン状態 |
| `jwt:` | JWT 関連 |
| `rate:` | レート制限 |
| `lock:` | 分散ロック（将来用） |
| `ws:` | Pub-Sub チャネル名 |
