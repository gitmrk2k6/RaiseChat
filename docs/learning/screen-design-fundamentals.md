## 0. このノートの位置づけ

このノートは D-4 画面設計書（`docs/screen-design.md`）の振り返り学習で扱った内容を、**前提知識ゼロから読み返せる密度** で残したものです。

D-4 で確定した画面設計（3 ペイン構成、`(auth)` ルートグループ、URL に動詞を書かない、スレッドは右ペイン、モーダルは URL を持たない、MVP は PC 優先）の **根拠** を、シナリオと絵で理解できるように書いています。

設計書本体は決定事項のドキュメントなので、「なぜそうしたのか」が断片的にしか書かれていません。このノートは **「なぜ」を一本のストーリーで追える** ように構成しています。後日設計判断を見直す必要が出てきたとき、まずこのノートに戻ってきてください。

### 通底するメンタルモデル

D-4 のほぼ全ての判断は、次の一文に還元できます。

> **URL = 安定した「場所の住所」**  
> **モーダル / ペイン / スレッド開閉 = 画面内の「一時的な状態」**

このメンタルモデルが頭に入ると、「これは URL を変えるべき？ 変えないべき？」の判断軸でほとんどの設計が決まります。

## 1. 前提用語のおさらい

D-4 で出てきた用語を 1 行で定義します。各章の本文で再度説明しますが、用語が分からなくなったらここに戻ってください。

| 用語 | 一行で |
| --- | --- |
| **画面 (page)** | URL に対応する 1 つの表示単位（Next.js の `page.tsx` 1 つに対応） |
| **ビュー (view)** | 画面内のひとまとまりの表示領域（例:「メッセージビュー」） |
| **ペイン (pane)** | 同時に並べて表示する固定領域。VS Code の左ファイルツリー + 右エディタ = 2 ペイン |
| **モーダル (modal)** | 画面の上に重ねて表示される小ウィンドウ。開いている間、背後を操作不能にする |
| **スレッド** | あるメッセージへの返信を、本流から切り離して別枠で表示する機能 |
| **親メッセージ** | スレッドの起点になる本流のメッセージ |
| **返信 (reply)** | 親に紐づくスレッド内のメッセージ |
| **ルート (route)** | URL パスのこと（例: `/login` がルート） |
| **ルートグループ** | URL に出さない論理的なフォルダ。Next.js の `(group)` 記法（例: `(auth)`） |
| **独立ルート** | 専用の URL を持った独立画面（例: `/threads/1001` のようなスレッド専用 URL） |
| **階層** | URL を `/` で区切った各パーツ。`/workspaces/1/channels/5` なら 4 階層 |
| **認可境界** | ログイン要否や所属チェックなど、アクセス可否の切り替え線 |
| **ID** | ものを区別する番号や記号。D-1 / D-4 では数値（1, 5, 42 など）で持つ |
| **リネーム** | 名前を変えること（rename） |
| **レスポンシブ** | 画面の大きさに応じてレイアウトを自動で組み替える Web 用語 |
| **MVP** | Minimum Viable Product。実用に耐える最小限の製品 |
| **スコープ / スコープ外** | やる範囲 / 今回はやらない範囲 |
| **px (ピクセル)** | 画面のドット 1 つの単位。1024px = 横幅 1024 ドット ≒ ノート PC サイズ |

## 2. なぜ 3 ペインなのか

### 2.1 まず「これは何ではない」

3 ペイン構成は **「Slack のマネをしたから」ではありません**。Slack も含めて業務チャットがほとんど 3 ペインなのには **明確な理由** があります。

### 2.2 シナリオ — 「同時参照」の必要性

業務チャットで頻繁に起こる操作:

```
「#dev-backend を見ながら、#general にメッセージを書く」
```

もし 1 画面ずつしか表示できない設計だったら:

1. `#dev-backend` を開いて読む
2. 書きたくなって `#general` に **画面遷移**
3. でも `#dev-backend` の内容が消える
4. 「あれ、何書こうとしたっけ？」となる

業務チャットでは「**他のチャンネルの内容を見ながら、今のチャンネルに書く**」が **頻繁** に起きます。だから画面遷移ではなく **複数のペインを並べて表示する** 必要があります。

### 2.3 なぜ 2 ではなく 3 ペインなのか

2 ペインで済ます案（sidebar の上にワークスペース選択ドロップダウンを置く）と比較:

| 観点 | 3 ペイン（rail 独立） | 2 ペイン（ドロップダウン） |
| --- | --- | --- |
| 「今どの WS にいるか」の視認性 | 常に左端に表示、一目で分かる | ドロップダウンを開くまで分からない |
| WS 切替の操作回数 | 1 クリック（rail のアイコン） | 2 クリック（▾ を開いて選ぶ） |
| sidebar の責務 | チャンネル / DM 一覧に専念できる | WS 切替も同居して情報過多 |

WS 切替は **頻度は低いが状況把握は常に必要**。だから「細く独立した領域 (rail)」に分けます。

### 2.4 役割分担

```
┌──── TopBar ──────────────────────────────────────────────────────┐
│ [WS 名 ▾]              [🔍 検索]                          [👤 Me] │
├────┬─────────────────────┬───────────────────────────────────────┤
│ R  │ Sidebar             │ Main                                  │
│ a  │                     │                                       │
│ i  │ # general           │ メッセージ本体                          │
│ l  │ # random            │                                       │
│    │                     │ (スレッド開時は ← この右に右ペイン追加)  │
│ W1 │ Direct Messages     │                                       │
│ W2 │ - Alice             │                                       │
│ +  │ - Bob               │                                       │
└────┴─────────────────────┴───────────────────────────────────────┘
```

| ペイン | 役割 | 操作頻度 |
| --- | --- | --- |
| **rail** | WS 切替（状況把握 + たまの切替） | 低 |
| **sidebar** | チャンネル / DM 一覧（今の WS 内で何を見るか） | 高 |
| **main** | メッセージ本体（読む / 書く） | 最も高 |

### 2.5 🔴 マスト

- 3 ペインは **「同時参照を画面遷移なしで実現するため」** に必要
- rail を独立させるのは **「頻度は低いが状況把握が常時必要」な機能** を切り出したから
- 操作頻度が違う情報を 1 つのペインに混ぜると、情報過多で使いにくくなる

## 3. 認証境界とルートグループ

### 3.1 まず「これは何ではない」

「認証境界」は **「ログインしているかどうか」だけの話ではありません**。「**その URL を見られるかどうか**」を決める境界線一般を指します。ログイン要否に加えて、**ワークスペース所属チェック** などもこの境界に含まれます。

### 3.2 認証境界 = URL のアクセス可否 3 タイプ

どんな Web サービスでも、URL は **誰が見られるか** で 3 つに分かれます。

| タイプ | 例 | アクセス可 |
| --- | --- | --- |
| **公開** | トップページ、利用規約 | 誰でも |
| **未ログインのみ** | サインアップ、ログイン | **未ログインのみ**（ログイン済みは redirect） |
| **ログイン必須** | マイページ、設定 | **ログイン済みのみ** |

**「未ログインのみ」が意外なポイント**: ログイン済みなのにログイン画面が見えると「もう一度ログインしようとして余計な操作になる」「URL を直接打った人が混乱する」ので、自動で別の場所（`/workspaces` など）へ飛ばします。

### 3.3 RaiseChat の場合

```
┌──────────────────────────────┐
│ 公開                          │  /
├──────────────────────────────┤
│ 未ログインのみ                 │  /signup, /login
├──────────────────────────────┤
│ ログイン必須                   │  /workspaces, /workspaces/{id}/...
│   + ワークスペース所属チェック   │
└──────────────────────────────┘
```

ログイン必須グループにはさらに「+ ワークスペース所属チェック」がついています。「ログインしてても、その WS のメンバーじゃなきゃ見られない」というもう一段の境界線です。

### 3.4 Next.js での実装 — ルートグループ `(group)`

Next.js (App Router) では、**フォルダ構造がそのまま URL になります**。

```
app/
├── page.tsx                ← URL: /
├── about/page.tsx          ← URL: /about
└── workspaces/page.tsx     ← URL: /workspaces
```

ここで困るケース:

> サインアップ画面とログイン画面に共通レイアウト（中央フォーム）を当てたい。  
> でも URL は `/signup` `/login` のままがいい（`/auth/signup` にしたくない）。

解決策が **ルートグループ `(group)` 記法**。フォルダ名をカッコで囲むと **URL から消えます**。

```
app/
├── (auth)/                 ← ✨ カッコ付き = URL に出ない
│   ├── layout.tsx          ← (auth) 配下の共通レイアウト
│   ├── signup/page.tsx     ← URL: /signup ⭕
│   └── login/page.tsx      ← URL: /login  ⭕
└── workspaces/
    ├── page.tsx            ← URL: /workspaces
    └── [workspaceId]/page.tsx ← URL: /workspaces/{id}
```

### 3.5 なぜ URL に出さない必要があるのか

URL とフォルダ構造は **別の責務** を持ちます。

| | URL | フォルダ |
| --- | --- | --- |
| 誰のためのもの | **ユーザー / 外部** | **開発者 / 内部** |
| 評価軸 | 短い / 覚えやすい / 共有しやすい | 整理されている |
| 変えていいか | できれば変えたくない（リンクが壊れる） | 自由に変えていい |

- `/signup` の方が短く覚えやすい
- `/auth/` という階層はユーザーには「何のためにあるの？」と疑問に映る
- 将来 `(auth)` を `(public-only)` に名前変更しても **URL は影響を受けない**（保険）

つまり「**開発者の整理上の都合を URL から隠す**」のがルートグループの本質です。

### 3.6 認可境界の判定タイミング

| 判定 | タイミング | 違反時の挙動 |
| --- | --- | --- |
| ログイン済みか | `(workspace)` 配下アクセス時のミドルウェア | `/login?returnTo=<元 URL>` |
| WS のメンバーか | `/workspaces/{wsId}` のサーバー側 API 呼び出し時 | `/workspaces` へ |
| チャンネル閲覧権限 | チャンネル詳細 API のレスポンス | 同じ WS の最初のチャンネルへ |

これらは `(auth)` `(workspace)` のグループの **layout.tsx に共通処理として書ける**、というのがルートグループの嬉しいところです。

### 3.7 🔴 マスト

- 認証境界は「公開 / 未ログインのみ / ログイン必須」の 3 タイプに分かれる
- Next.js では `(group)` 記法で URL に出さず論理グループ化できる
- URL とフォルダは **別の責務**。URL は対外的な契約、フォルダは内部整理
- 共通レイアウトと共通の認可チェックを `(group)/layout.tsx` にまとめられる

## 4. URL 設計の判断軸（3 つの原則）

D-4 の URL 設計は次の 3 原則で組まれています。1 つずつ見ます。

### 4.1 原則① URL に「やること」を書かない（リソース指向）

#### まず「これは何ではない」

URL は **「今どこを開いているか」** を表すもの。  
**「何をしているか（編集中など）」は URL に書かない**。

#### 具体例

「チャンネル 5 番の設定を編集する」操作の URL:

| 案 | URL | 説明 |
| --- | --- | --- |
| ❌ | `/workspaces/1/channels/5/edit` | URL の末尾に「edit（やること）」が書いてある |
| ⭕ | `/workspaces/1/channels/5` ＋ 編集モーダル | URL は「5 番チャンネルにいる」だけ。編集ウィンドウは画面の上に重ねる |

#### なぜか — 最も重要な理由

URL を他人にコピペで送ったとき:

- ❌ `/workspaces/1/channels/5/edit` を送ると、相手の画面でも **編集モードで開いてしまう**。意味不明
- ⭕ `/workspaces/1/channels/5` を送ると、相手は **そのチャンネルを普通に開ける**。共有として自然

URL は「**人と共有するもの**」だから、**共有して自然な内容だけ** を入れる、という発想です。

### 4.2 原則② URL は「名前」ではなく「ID（数字）」

#### シナリオで追ってみる

シーン 1: 最初は問題なし

```
チャンネル名: general
URL:         /workspaces/1/channels/general   ← 動いてる
```

シーン 2: メッセージに URL を貼って共有した

```
Alice → Bob:
  「ここ見て → https://raisechat.example.com/workspaces/1/channels/general」
```

シーン 3: 後日 `general` を `general-room` にリネーム

```
チャンネル名: general-room ← 名前が変わった
URL:         /workspaces/1/channels/general-room   ← 新しい URL

過去のメッセージに貼られた URL:
  /workspaces/1/channels/general   ← ❌ もう存在しない、リンクが死ぬ
```

リネーム 1 回で **過去に貼られた全部の URL が死ぬ**。これが「URL が壊れる」現象。

#### ID（数字）ベースなら壊れない

```
チャンネル名: general → general-room ← 変わった
ID:          5                         ← 変わらない
URL:         /workspaces/1/channels/5  ← ✅ 変わらない
```

リネームしても **ID は変えない** のがポイント。

#### 一般化

URL に「**ユーザーが変えられるもの**（名前）」を入れると壊れやすい。  
URL には「**システムが内部で管理する、変えないもの**（ID）」を入れる。

### 4.3 原則③ WS を URL の先頭階層に固定

#### シナリオ — 複数 WS に所属

```
- WS ①「RaiseTech」 → ID = 1
    └ # general (ID=5)

- WS ②「社内プロジェクト」 → ID = 2
    └ # general (ID=12)  ← 同じ名前のチャンネル！
```

**両方の WS に同じ名前のチャンネルがある**。これは普通に起きる状況です。

#### ID だけだと困る

もし URL が `/channels/5` だったら:

```
URL: /channels/5

→ どの WS の 5 番？
   RaiseTech の general？ 社内プロジェクトの何か？
   URL を見ただけでは判断できない
```

ID は **WS の中で一意** であって、**全体で一意とは限らない**。

#### WS を先頭に固定すれば解決

```
URL: /workspaces/1/channels/5
     └────────┘ │ └──────┘ │
       「RaiseTech」「の 5 番チャンネル (general)」と確定
```

別の WS の同じ名前のチャンネルでも問題なし:

```
RaiseTech       の general:  /workspaces/1/channels/5
社内プロジェクトの general:  /workspaces/2/channels/12
                       ↑↑              ↑↑↑↑
              WS が違うから別 URL、混ざらない
```

### 4.4 🔴 マスト

- 原則① 動詞を URL に出さない（編集はモーダル、削除も場所遷移なし）
- 原則② 名前ではなく ID（数字）を使う（リネームで壊れない）
- 原則③ WS を先頭階層に固定（複数 WS の衝突回避）
- 3 つに共通するのは「**URL は安定**」「**共有して自然**」「**システム内部の都合をユーザーに見せない**」

## 5. スレッドを「右ペイン」で開く判断（★重点）

D-4 で最も判断に時間がかかった部分です。3 つの案を比較して右ペインを採用しました。振り返り学習で「よくわからない」のサインを出した章なので、ここは丁寧に書きます。

### 5.1 まず「スレッド」を確認

普通のチャットはメッセージが **上から下へ一直線** に並びます。

```
Alice:  おはよう
Bob:    ログイン直したい
You:    お疲れさま
Carol:  今日も頑張ろう
```

ここで Bob の「ログイン直したい」に対して Carol が詳しく聞きたいとします。普通に返信したら本流が「ログインの話」で埋まる:

```
Alice:  おはよう
Bob:    ログイン直したい
You:    お疲れさま
Carol:  今日も頑張ろう
Carol:  ↑↑ ログインのどこ壊れたの？  ← Bob の話を続けたい
Bob:    ここです
Carol:  ありがと
You:    ところで...   ← 別の話したい人が割り込みづらい
```

「ログインの話」と「別の話」が **同じ場所で混ざって読みにくい**。

#### スレッドの仕組み

Bob のメッセージに対する返信だけを、**別の場所に束ねて表示** する:

```
本流のチャット                          Bob のスレッド
────────────                             ──────────────────────
Alice:  おはよう                          Bob: ログイン直したい (親)
Bob:    ログイン直したい  💬 3            ├ Carol: どこ壊れたの? (返信)
You:    お疲れさま                        ├ Bob:   ここです       (返信)
Carol:  今日も頑張ろう                    └ Carol: ありがと       (返信)
```

本流は **クリーンなまま**、ログイン議論は **スレッド側に独立** して進む。Bob のメッセージの下に「💬 3」と数字が出て「3 件の返信あり」と分かる。

| 用語 | 意味 |
| --- | --- |
| 親メッセージ | スレッドの起点（Bob のメッセージ） |
| 返信 | スレッド内のメッセージ（Carol たち） |

### 5.2 スレッドをどこに表示するか — 3 つの候補

D-4 で検討した 3 つの案:

| # | 案 | イメージ |
| --- | --- | --- |
| ① | **右ペインで開く**（採用） | 本流の右隣に並べる |
| ② | 独立ルートにする | `/threads/1001` の専用画面に飛ぶ |
| ③ | モーダルで開く | 本流の上に重ねる |

### 5.3 シナリオで比較

「Bob のログイン質問のスレッドで返信を書きながら、Alice が本流に新着を書いたら気づきたい」という現実によくあるシーン。

#### ① 右ペイン（採用）

```
┌──── 本流 ────┬──── スレッド ────┐
│ Alice: おはよう│ Bob: ログイン...   │
│ Bob: ログイン. │  ├ Carol: どこ?    │
│ You: お疲れ    │  ├ Bob: ここ       │
│ Alice: 新着!! │  └ You: [入力中…]  │  ← スレッド書きつつ
└──────────────┴───────────────────┘     ↑ Alice の新着も見える ⭕
```

- 本流とスレッドが横並び
- 両方の流れを同時に追える
- 本流の新着に気づける

#### ② 独立ルート

```
URL: /threads/1001
┌────────────────────────────────┐
│  Bob: ログイン...               │  ← スレッドしか表示されない
│   ├ Carol: どこ?               │     本流の Alice 新着に気づけない ❌
│   ├ Bob: ここ                  │
│   └ You: [入力中…]             │
└────────────────────────────────┘
```

- スレッド専用画面 = 本流が完全に画面外
- 本流で何が起きてるか見えない
- ただし URL をシェアできる（後述）

#### ③ モーダル

```
┌────── 本流 ──────────────────┐
│ Alice: おはよう                │
│ Bo┌── スレッド (モーダル) ──┐│
│ Yo│ Bob: ログイン...         ││  ← モーダルは背景を操作不可
│ Al│  └ You: [入力中…]        ││     本流が薄暗くなって読めない ❌
│   └─────────────────────────┘│     さらに長文を書くには窮屈
└──────────────────────────────┘
```

- モーダルは「背景を操作できない」のが本質
- 本流を見たくても暗くなって読めない
- スレッドで長文の返信を書くには窮屈

### 5.4 比較表

| 観点 | ① 右ペイン | ② 独立ルート | ③ モーダル |
| --- | --- | --- | --- |
| 本流の新着に気づけるか | ⭕ | ❌ | ❌ |
| 長文返信を書きやすいか | ⭕ | ⭕ | ❌（窮屈） |
| URL でシェアできるか | ❌ | ⭕ | ❌ |
| 実装の単純さ | 中 | 高 | 中 |

### 5.5 なぜ「右ペイン」を選んだか

業務チャットでは **「本流の流れを見続けながらスレッドの議論をしたい」** が圧倒的に重要。

- 別の人が本流に何か書いたら気づきたい
- 「ちょっと脇道」のスレッドのために本流を見えなくするのは本末転倒
- だから「本流が見えなくなる ②③」は却下

URL シェアできないデメリットは認識しつつ、**MVP では妥協** しました。需要が出てきたら **URL の末尾にちょっと印を付ける案**（例: `/workspaces/1/channels/5?thread=1001`）を後で検討する、という形で「未決事項」（[screen-design.md §10.1](../screen-design.md)）に残してあります。

### 5.6 スレッドを開いても URL が変わらない

ここが原則① の延長です。

```
本流の URL:    /workspaces/1/channels/5
                          ↓ スレッドの 💬 をクリック
スレッド開後: /workspaces/1/channels/5  ← URL 変わらない
                          ↓ ✕ で閉じる
スレッド閉後: /workspaces/1/channels/5  ← URL 変わらない
```

スレッドの開閉は「**画面の中の状態**」であって「**場所の移動**」ではない。だから URL を変えない。これはモーダルが URL を持たないのと同じ理屈です（次章）。

### 5.7 🔴 マスト

- スレッド = メッセージへの返信を本流から切り離して別枠で表示する仕組み
- 表示場所の 3 候補（右ペイン / 独立ルート / モーダル）の中で **「本流を見続けられる」** ことを最優先 → 右ペイン
- URL シェアできない欠点は MVP では妥協、未決事項に残してある
- スレッド開閉では URL を変えない（場所の移動ではないから）

## 6. モーダルが URL を持たない理由

ここは原則① と Step 5 ですでに本質を話し終えています。まとめだけ。

### 6.1 モーダルとは

画面の上に重ねて表示される小ウィンドウ。

- ブラウザの「このページから離れますか?」
- Web サイトの「無料登録しませんか?」のポップアップ
- ゴミ箱を空にする確認窓

```
┌──────────────────────────────────┐
│  元の画面                         │
│  ┌──────────────────────────┐    │
│  │  モーダル                 │    │
│  │  ┌────────────────────┐  │    │
│  │  │ 編集フォーム         │  │    │
│  │  │ [保存] [キャンセル]  │  │    │
│  │  └────────────────────┘  │    │
│  └──────────────────────────┘    │
│ (背景は薄暗くなって、操作できない)  │
└──────────────────────────────────┘
```

特徴:

- 元画面の上に重なる
- 開いている間、背後を操作できない
- `Esc` / 背景クリック / `✕` で閉じる

### 6.2 なぜ URL を持たないか

3 つの理由が重なります。

| # | 理由 |
| --- | --- |
| 1 | モーダルは「**場所の移動**」ではなく「**画面の中の一時状態**」。URL は場所しか表さないから、変えない |
| 2 | モーダル URL を共有しても「相手の画面でもモーダルが開く」のは不自然。原則① と同じ |
| 3 | URL を変えるとブラウザ履歴が増える。「設定モーダルを開閉するだけで履歴 +2」は UX ノイズ |

### 6.3 副作用として嬉しいこと

- モーダルを閉じるのはブラウザバックではなく `Esc` / `✕`（URL を戻すのではない）
- URL を共有してもモーダルは開いた状態にならない（普通の画面が開く）

### 6.4 RaiseChat のモーダル一覧（[screen-design.md §6](../screen-design.md)）

| # | 名前 | 開く起点 |
| --- | --- | --- |
| M-01 | WS 作成 | `/workspaces` の「+ 新しい WS」 |
| M-02 | チャンネル作成 | sidebar Channels の `+` |
| M-03 | DM 開始 | sidebar DMs の `+` |
| M-04 | メッセージ削除確認 | メッセージの 🗑 |
| M-05 | プロフィール編集 | TopBar 右のアバター |
| M-06 | チャンネル設定 / メンバー | チャンネルヘッダ ⚙️ |
| M-07 | ログアウト確認 | TopBar → ドロップダウン |

どれも **URL を持たない**。共有時は親画面の URL を共有します。

### 6.5 🔴 マスト

- モーダルは「画面の中の一時状態」
- URL は変えない（場所の移動ではないから）
- 閉じる手段は `Esc` / 背景 / `✕`、ブラウザバックではない

## 7. レスポンシブ方針（MVP は PC 優先）

### 7.1 D-4 で決めたこと

| 範囲 | 対応 |
| --- | --- |
| PC（最小幅 1024px 〜） | ✅ 対応 |
| タブレット（768〜1023px） | 🔄 表示は崩れない程度、最適化はしない |
| モバイル（767px 以下） | ❌ スコープ外。「PC でご利用ください」表示 |

### 7.2 なぜ PC 優先なのか — 3 つの理由

#### ① ユースケース

RaiseChat は **業務チャット**。Slack も同じカテゴリで、メインの利用シーンが PC です。

```
業務時間中の Slack 利用先（イメージ）
PC:     ████████████████████  圧倒的に多い
スマホ: ████                  通知確認・移動中の補助
```

メイン利用シーンが PC なので、まず PC をしっかり作る方が価値が高い。

#### ② 3 ペイン構成との相性

3 ペイン構成（rail + sidebar + main）はモバイル（横幅 390px とか）にそのまま入りません。

```
PC (1280px)                    モバイル (390px)
┌──┬─────┬───────────┐       ┌─────────┐
│Rl│Sider│ Main      │       │  ?????  │
└──┴─────┴───────────┘       └─────────┘
                              ペインが横に並ばない
```

モバイル対応するには:

- ペインを **縦に積む** ように組み直す、または
- ペインを **1 つずつ画面切替** で見せる

→ **まったく別のレイアウト設計** が必要 = 工数が大きい。

#### ③ MVP の精神

> 最小限の機能で「使える価値」を確かめてから、足していく

「PC + モバイル両対応」を最初からやると:

- 価値を確かめる前に **倍以上の工数** がかかる
- 「実は誰もモバイルで使わなかった」と分かったら **無駄になる**

なので **「まず PC だけで動かして価値を確かめ、後でモバイルを足すか判断」** が正しい順番。

### 7.3 「PC 優先」は手抜きではない

「PC 優先」= 「**最初のリリースに含めないと意図的に判断した**」  
≠ 「手抜き」「モバイル対応を捨てた」

優先順位をつけた結果として **PC を先に完璧にする**、という戦略判断です。

### 7.4 🔴 マスト

- PC 優先は「業務利用 × 3 ペイン構成 × MVP」3 つの理由が重なった結論
- モバイル対応は捨てたのではなく「**最初のリリースに含めない**」と意図的に決めた
- 反応を見て後でモバイル対応を足すかを判断する

## 8. 通底するメンタルモデル（再掲）

D-4 のほぼ全ての判断は次の一文に還元できます。

> **URL = 安定した「場所の住所」**  
> **モーダル / ペイン / スレッド開閉 = 画面内の「一時的な状態」**

### 8.1 この軸で判断できること（チェックリスト）

| 判断したい操作 | URL を変える？ | 理由 |
| --- | --- | --- |
| チャンネルを切り替える | ⭕ 変える | 場所の移動 |
| DM ルームを開く | ⭕ 変える | 場所の移動 |
| 検索結果ページへ行く | ⭕ 変える | 場所の移動 |
| 編集モーダルを開く | ❌ 変えない | 画面内の一時状態 |
| スレッドを開く | ❌ 変えない | 画面内の一時状態 |
| メッセージを削除確認 | ❌ 変えない | 画面内の一時状態 |
| 設定モーダルを開く | ❌ 変えない | 画面内の一時状態 |

### 8.2 この軸でブレなくなる

「これは URL を変えるべきか？」と迷ったら、

> **そのリンクを他人に送ったとき、開いた相手にも同じ意味になるか？**

を考えてください。

- なる → URL を変える（場所の移動）
- ならない → URL を変えない（画面内の一時状態）

### 8.3 設計書 D-4 に戻る

このノートで腹落ちしたメンタルモデルを持って [screen-design.md](../screen-design.md) を読むと、§2 全体方針 / §3 画面一覧 / §5 各画面のワイヤーフレーム の判断が **「ああこれは場所、これは状態」** という軸でスッと整理できるはずです。

設計書本体に戻る前に、このノートで軸を作っておくのがおすすめです。
