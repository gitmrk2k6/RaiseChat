# F-06 DM API 学習ノート

このノートは、F-06 ダイレクトメッセージ API（PR #56）の実装で身に付けた **設計判断と引き出し** を、後日 1 人で再学習できる質で書き残したものです。前提知識ゼロから読み始めても付いてこられるように章を組んでいます。

このノートは **読む順** に章を並べています。途中で「飛ばしても理解できる章」はありません。各章ともすべて重点章扱いで書いています。

| # | 引き出し | このパターンが役立つ場面 |
|---|---|---|

## Chapter 1: F-06 は「F-05 をそのまま伸ばす」設計

最初に、F-06 全体が **F-05 メッセージ API のコピー＋差分** で出来ていることを掴みます。これを掴むと残りの章がスッと入ります。

### Step 1-1: 一枚絵で全体像を掴む

DM のやり取りが起きるとき、裏側で動いている要素はこの 5 つです。

```
[クライアントA] ←── 受信 ── [サーバー] ←── 公開 ── [Redis]
      │                       │                     │
      │ 送信                  │ 保存                │ 配信
      ↓                       ↓                     ↓
   /app/dm/                メッセージ          messages:dm:
   {roomId}                 を DB に保存       {roomId} に publish
   /messages
                                                    │
                                                    ↓
                                           [サーバー2 / サーバー3...]
                                                    │
                                                    ↓ /topic/dm/{roomId}
                                              [クライアントB]
```

ここで気付いてほしいのは、**この絵は F-05 のチャンネルメッセージとまったく同じ形** だということです。違うのは送り先のラベル（`channels` か `dm` か）だけ。

| 役割 | チャンネル（F-05） | DM（F-06） |
|---|---|---|
| 送信 destination | `/app/channels/{id}/messages` | `/app/dm/{roomId}/messages` |
| 配信 destination | `/topic/channels/{id}` | `/topic/dm/{roomId}` |
| Redis チャネル | `messages:channel:{id}` | `messages:dm:{roomId}` |
| メッセージ保存先 | `messages.channel_id` 列 | `messages.dm_room_id` 列 |

「形」は全く同じ、「ラベル」だけが違う、これが F-06 の全体像です。

### Step 1-2: 何を「同じに保ち」、何を「変えた」か

F-06 で「変えたところ」は意外と少ないです。

**変えたもの（=新規に増やしたもの）**

- DM ルームの CRUD エンドポイント（作成・一覧）
- DM メッセージ履歴を取る GET
- WebSocket の送受信 destination のラベル違い
- Pub-Sub の Subscriber を 1 つ追加（DM 専用）
- ProblemDetail のエラーハンドラを 3 種追加（DmNotFound / DmForbidden / DmValidation）

**変えていないもの（=F-05 のコードがそのまま動く）**

- メッセージの保存形（`messages` テーブルの 1 行）
- 編集・削除のエンドポイント（`PATCH /api/messages/{id}` / `DELETE /api/messages/{id}`）
- 認証の仕組み（JWT + ChannelInterceptor）
- ページングの形（cursor ベース、limit+1 で hasMore 判定）
- Service 層の構造（Repository を介して JPA で動かす）

「変えていない」方が多い、というのが大事な気付きです。**新機能を作るとき、既存の似た機能のコピーで済む範囲をまず最大化する** と、品質も速度も担保できます。

### Step 1-3: なぜ「同じ」を保つと学習が加速するのか

学習者目線で見ると、F-05 で覚えたパターンを F-06 で **何の追加学習もなく適用できた** ことには大きな意味があります。

- 新しい用語を増やさずに済む（destination, Pub-Sub, ProblemDetail などはそのまま）
- 「設計判断の比較」だけに集中できる（ラベル違いの議論にエネルギーを使わない）
- **次の F-07 / F-08 でも同じパターンが効くと確信できる** ようになる

これは「再利用できる引き出しを増やす」という学習目標（A〜D の D：AI への指示力）に直結します。コードを書くスキル（E）ではなく、**「これは F-05 と同じ形でいけますね」と AI に伝える判断力** が育ちます。

### Step 1-4: 引き出し1「既存パターンを伸ばす」

**引き出し**：新機能を作るときは、まず「既存の似た機能はどれか」を探し、その構造をなるべく崩さず差分だけ載せる。

**AI への指示テンプレ**

> F-06 DM API を実装してください。**設計と構造は F-05 メッセージ API（PR #52）と同じパターンを踏襲** してください。
> 差分は次の通りです：
> - REST: DM ルーム作成 / 一覧 / メッセージ履歴の 3 エンドポイントを新規追加
> - WebSocket: destination のラベルを `channels` → `dm` に
> - Redis Pub-Sub: prefix を `messages:channel:` → `messages:dm:` に
> - エラー型は F-02 / F-04 と同じ ProblemDetail
> 他は F-05 のコードをそのまま流用してください。「同じ形」を崩さないでください。

このテンプレを覚えておくと、F-07 招待 / F-08 スレッド / F-09 リアクション もすべて同じ呼び方で AI に指示できます。

## Chapter 2: DB 制約をサービス層で吸収する

ここが F-06 で **新しく学んだパターン** の最重要章です。

### Step 2-1: 制約の正体

DM ルームのテーブル `dm_rooms` には、こんな CHECK 制約が入っています。

```sql
CONSTRAINT dm_rooms_user_order CHECK (user_a_id < user_b_id)
```

これは「userA の id は userB の id より小さくないと INSERT できない」という DB レベルのルールです。

例えば keisuke (id=1) と haruka (id=2) の DM を作るとき、`user_a_id=1, user_b_id=2` なら通りますが、`user_a_id=2, user_b_id=1` だと DB が弾きます。

### Step 2-2: なぜ DB で順序を強制するのか

「1:1 DM」を素直に作ると、こういう問題が起きます。

- keisuke が haruka に DM を送りたい → DM ルームを作る
- haruka が keisuke に DM を送りたい → 同じ 2 人なのに別のルームを作ってしまう

これを防ぐには「**同じ 2 人の DM ルームは 1 つしか存在できない**」というルールを DB レベルで持ちたい。

そのために `UNIQUE INDEX (workspace_id, user_a_id, user_b_id)` を貼ります。これで「同じ workspace 内で同じ userA / userB の組み合わせはユニーク」になります。

でもこれだけだと不十分です。**`(1, 2)` と `(2, 1)` は別の組み合わせとして INDEX が許してしまう** からです。

そこで `user_a_id < user_b_id` の CHECK 制約を足します。これで「組み合わせを表現するときは必ず小さい方が userA」というルールが確定します。`(1, 2)` だけが許され、`(2, 1)` は DB が拒否する。これで本当の意味で「同じ 2 人 = 同じ 1 行」になります。

### Step 2-3: 例えると「双子の片方を常に左に立たせる」

順不同のペアを表現したいとき、DB はそのまま「順不同」を扱えません。`{1, 2}` のような集合型は普通のリレーショナル DB には無いからです。

なので **「順序のあるペアの形で保存するけど、順序を必ず正規化することで実質的に順不同にする」** という発想を使います。

例えば「双子の写真を撮るとき、必ず弟が左に立つルール」と決めれば、写真を見たときに兄と弟を一意に判別できます。位置（左 = userA、右 = userB）に意味を持たせる代わりに、立つ順番をルール化する、という仕組みです。

### Step 2-4: クライアントには順序を意識させたくない

問題は、これを「クライアント（フロントエンドや API 利用者）にも守らせるのは酷」ということです。

クライアント側はこう書きたい：

```
「keisuke として、haruka とのDM ルームを作って」
```

逆向きにこう書きたいときもある：

```
「haruka として、keisuke とのDM ルームを作って」
```

このどちらが来ても **サーバー側で正しく動いてほしい**。クライアントに「id の小さい方を userA に入れてね」と要求するのは UI として変です。

### Step 2-5: サービス層で「正規化」する

そこで、サービス層に入った瞬間に id を並び替えます。

```java
Long smallerId = Math.min(userId, partnerUserId);
Long largerId  = Math.max(userId, partnerUserId);
// この時点で smallerId が userA、largerId が userB に確定
```

このたった 2 行が **「正規化」** と呼ばれるパターンです。「クライアントから来るデータを、ある決まった形に整える」処理です。

このあとは smallerId / largerId を使って Repository を呼ぶだけ。CHECK 制約に違反する INSERT は起きません。

### Step 2-6: 他のパターンと比較すると何が嬉しいか

正規化を「どこで」やるかには選択肢があります。

| どこで正規化するか | メリット | デメリット |
|---|---|---|
| クライアントが頑張る | サーバーは単純 | クライアント全部に同じロジックを書く必要、忘れる |
| DB トリガーで BEFORE INSERT 時に並び替え | サーバーコードが超単純 | DB の振る舞いがトリッキーで、ログを見ても気付きにくい |
| **サービス層で並び替える（採用）** | 1 箇所で完結、コードを読めば見える | サービス層が CHECK 制約を知っている必要がある |

**採用したのはサービス層** です。理由は「コードを読めば挙動が分かる」が最重要だからです。DB トリガーで黒魔術的に並び替えると、サービス層を読んでも何が起きるか分からず、デバッグで詰まります。

### Step 2-7: この発想が効く別の場面

正規化パターンは、DM 以外でもよく出てきます。

- **タグの順不同集合**（例：記事に `["typescript", "react"]` のタグを付ける）→ アルファベット順にソートして保存
- **無向グラフのエッジ**（例：友達関係 A-B）→ id の小さい方を src に正規化
- **時刻範囲**（例：09:00〜18:00 と 18:00〜09:00 を同じ意味で扱う？）→ 用途次第で正規化

「順不同のペア / 集合を DB に入れる」場面で必ず思い出してください。

### Step 2-8: 引き出し2「DB 制約をサービス層で吸収する」

**引き出し**：DB に CHECK / UNIQUE 制約があり、その制約をクライアントに守らせるのが不自然な場合、**サービス層に入った瞬間に正規化** する。コードを読めば挙動が分かる位置に書く。

**AI への指示テンプレ**

> このテーブルには `CHECK (X < Y)` の制約と `UNIQUE (workspace_id, X, Y)` の索引が貼ってあります。
> クライアントから来る 2 つの id を、サービス層に入った直後に **小さい方を X、大きい方を Y に正規化** してください。
> Repository には正規化済みの値だけを渡してください。DB トリガーは使わないでください。コードを読んで挙動が分かる位置に置きたいからです。

## Chapter 3: 「既存なら返す、なければ作る」エンドポイント

F-06 で 2 番目に学んだのは、`POST /api/workspaces/{wsId}/dm/rooms` が **2 つのステータスコードを使い分ける** ことです。

### Step 3-1: ユーザーの操作を思い浮かべる

Slack を思い出してください。サイドバーで「Direct Messages」の横にある `＋` ボタンを押し、相手の名前を選びます。すると：

- 過去に DM したことがある相手なら → **既存の DM 画面が開く**（過去のやり取りも見える）
- 初めての相手なら → **新しい空の DM 画面が開く**

ユーザーから見れば「相手を選んだら DM が開く」という同じ動作ですが、裏側では **既存ルームを取得 / 新規ルームを作成** という 2 つの異なる挙動を取っています。

### Step 3-2: 素直な REST 設計だと困る

普通の REST 設計だとこんな感じです。

| 操作 | エンドポイント | レスポンス |
|---|---|---|
| 新規作成 | POST /api/dm/rooms | 201 Created |
| 既存取得 | GET /api/dm/rooms/{id} | 200 OK |

でもクライアント目線では「相手の userId しか持っていない」状況で、どっちのエンドポイントを呼べばいいか分かりません。一度 GET で探して、404 だったら POST、というのも美しくないし、競合（同時に 2 人が押した）も起きやすい。

### Step 3-3: 1 つの POST で両方を表現する

そこで、F-06 では **同じ POST エンドポイントで両方の挙動** を返す設計にしました。

```
POST /api/workspaces/{wsId}/dm/rooms
{ "partnerUserId": 15 }
```

サーバー側の挙動：

1. partnerUserId と自分の id で DM ルームを検索する
2. **見つかったら 200 OK** で返す（既存ルームの中身）
3. **見つからなかったら作って 201 Created** で返す（新規ルームの中身）

クライアントは「ステータスコードで分岐したければ分岐できる」し、「区別せず常にレスポンスを使ってもいい」。どちらでも動きます。

### Step 3-4: なぜ 409 Conflict にしないのか

「既存があるのに POST されたら 409 Conflict（重複エラー）が普通では？」と思うかもしれません。

確かに「リソースを `name` で一意に作る」ような POST では 409 が正解です。例：ユーザー登録で既存の email が来たら 409。

ただ DM ルームは違います。「既に存在することは **エラーではない**」のです。Slack で既存の DM を開くのは普通の動作ですよね。それをサーバーが「409 エラー！」と返すと、クライアント側は「いや、それは欲しい挙動なのですが…」となります。

**409 はエラー、200/201 は成功** という HTTP のセマンティクスを思い出すと、ここでは 200/201 が正しい選択になります。

### Step 3-5: 200 と 201 の細かい違い

両方とも「成功」ですが、意味が違います。

- **201 Created**：新しいリソースを作った。Location ヘッダ等で「どこに作ったか」を返すこともある。
- **200 OK**：既存のリソースを返した。何も変えていない。

クライアント側は通常区別する必要はありません。が、例えば「新規作成時だけログを取りたい」「初回 DM 時だけウェルカムメッセージを表示したい」のような分岐をしたいときに、ステータスコードを使えば API のレスポンス本文を増やさずに区別できます。

### Step 3-6: PUT で表現する別案との比較

別案として「PUT で表現する」という選択肢もあります。

```
PUT /api/workspaces/{wsId}/dm/rooms/by-partner/{partnerUserId}
```

PUT は「URI で指定したリソースをこの状態にしてください」という意味なので、「既存があれば再利用、なければ作る」と相性が良い動詞です（冪等性が高い）。

ただ F-06 では POST を採用しました。理由：

- URI に partnerUserId を入れると URL が縦に伸びる
- partnerUserId は body にあった方がクライアントが書きやすい
- 「相手を指定して DM を開く」を「ルームを作る」と読むのは自然

設計判断としては「PUT も間違ってない、POST のほうがクライアントに優しい」という選び方です。**正解は 1 つではない** ということを覚えておいてください。

### Step 3-7: 引き出し3「200/201 切り分け」

**引き出し**：「相手を選んだら開く」「タグを付けたら付くべき場所に付く」のような **「既存があってもエラーにしたくない」操作** は、1 つの POST で 200 / 201 を使い分ける設計にする。409 にしない。

**AI への指示テンプレ**

> このエンドポイント `POST /api/...` は、既存リソースがあれば再利用、なければ新規作成、という挙動にしてください。
> - 既存があれば **200 OK** で既存のリソースを返す
> - 新規作成したら **201 Created** で新規リソースを返す
> - 409 は返さないでください（既存はエラーではないため）
> サービス層は `Optional` の有無で if-else 分岐させ、Controller で ResponseEntity のステータスを切り替えてください。

## Chapter 4: Pub-Sub チャネルの粒度設計

ここからは F-06 で「複数の選択肢から 1 つを選んだ」ポイントの話です。

### Step 4-1: 何が問題なのか

Redis Pub-Sub というのは、**サーバーから流したメッセージを、同じトピックを購読している全インスタンスが受け取る** 仕組みです。F-05 で詳しく解説した通り、Spring Boot を複数台動かしていても全員にリアルタイム配信が届くようにするための仕組みです。

このとき、**トピック名（Pub-Sub チャネル名）の粒度** を決める必要があります。F-06 では DM メッセージが流れる新しい場所が増えたので、どんな名前で publish するかを決める必要があります。

### Step 4-2: 3 つの選択肢

選択肢はだいたいこの 3 つでした。

**案A: 既存のチャンネル用 prefix に相乗りさせる**

```
messages:channel:dm-{roomId}
```

→ 既存 Subscriber が `messages:channel:*` を購読しているので、そのまま動く。
→ でも DM はチャンネルじゃないので「名前が嘘」になる。混乱の元。

**案B: ワークスペース単位に 1 本の prefix**

```
ws:workspace:{workspaceId}
```

→ realtime-design.md でも「ワークスペース単位粒度」が候補に挙がっていた案。
→ 1 つのチャネルにチャンネルメッセージも DM も流れるので、購読側で「自分宛か」をフィルタする必要が出る。

**案C: DM 専用に新しい prefix を切る（採用）**

```
messages:dm:{roomId}
```

→ 用途と名前が一致して読みやすい。
→ Subscriber を 1 つ増やす必要がある（コードが少し増える）。

### Step 4-3: なぜ案 C を選んだか

採用したのは案 C です。理由は **「名前と用途が一致していること」** が最優先だったからです。

- 案 A は「DM なのに channel という名前」で、半年後にコードを読んだときに必ず詰まる
- 案 B は「1 つのトピックに混ぜる」せいで、購読側にフィルタロジックが必要になり、何が流れているか把握しづらい
- 案 C は「dm 用 prefix」が一目で分かり、Subscriber も 1 ファイル増えるだけで済む

設計の判断基準で「コードの読みやすさ」を最優先にすると、ほとんどの場合は **専用 prefix を切る** が勝ちます。

### Step 4-4: 既存 Subscriber を流用しなかった理由

「既存の `MessageChannelRedisSubscriber` を改造して、DM もそこで扱う」案も検討しました。

```java
// 1 つの Subscriber で両方を扱う案
if (topic.startsWith("messages:channel:")) { ... }
else if (topic.startsWith("messages:dm:")) { ... }
```

これも動きますが、避けました。理由：

- 1 つの Subscriber に分岐が入ると、F-07 / F-08 で更にトピックが増えるたびに if-else が増える
- 「チャンネル用」「DM 用」と **クラスを分けたほうが責務がはっきりする**
- 各 Subscriber は数十行で済むので、増えても可読性は落ちない

**「分岐で広げる」より「責務ごとにクラスを分ける」** ほうが、長期的に読める設計になります。

### Step 4-5: マルチインスタンスを思い浮かべる

念のため動きを言葉で追っておきましょう。

```
[サーバー1] が DM メッセージを保存
  ↓
publish("messages:dm:42", JSON)  ← Redis に流す
  ↓
[Redis Pub-Sub] が「messages:dm:42」を購読している全員に配信
  ↓
[サーバー1, サーバー2, サーバー3] の MessageDmRedisSubscriber が受信
  ↓
各サーバーが /topic/dm/42 を購読している自分のクライアントに WebSocket で送る
  ↓
[クライアント] が画面に表示
```

この経路を 1 度きちんと頭で追えれば、Pub-Sub の役割が「**サーバー間で配信を共有するための連絡網**」だと腹落ちします。

### Step 4-6: 引き出し4「Pub-Sub チャネル粒度の決め方」

**引き出し**：Pub-Sub トピックは「**名前と用途を一致** させる」ことを最優先にする。既存トピックに相乗りさせると、半年後に必ず読めなくなる。トピックが増えるたびに Subscriber を 1 ファイル増やすのが正解。

**AI への指示テンプレ**

> 新しいリアルタイム配信を追加します。
> - Redis Pub-Sub の prefix を **専用に切ってください**（既存 prefix への相乗りは禁止）
> - prefix 名は用途を表す名前にしてください（例: `messages:dm:`, `notifications:user:`）
> - Subscriber は責務ごとにクラスを分けてください。1 つの Subscriber に if-else で複数 prefix を詰めないでください
> - RedisConfig に PatternTopic を 1 つ追加してください

## Chapter 5: Controller の境界をどう引くか

最後は「Controller の境界」の話です。F-04 と F-06 で違う判断をしたので、その理由を比較して残します。

### Step 5-1: URL の階層と Controller の境界は別物

F-06 では DM 関連のエンドポイントが 3 つあります。

| # | URL | 何をする |
|---|---|---|
| 1 | POST /api/workspaces/{wsId}/dm/rooms | DM ルーム作成 |
| 2 | GET /api/workspaces/{wsId}/dm/rooms | DM ルーム一覧 |
| 3 | GET /api/dm/rooms/{id}/messages | DM メッセージ履歴 |

このとき、誰が見ても自然な疑問は **「3 つとも DmController に入れるべきか、それとも 3 を MessageController に入れるべきか」** です。

採用したのは **「1, 2 → DmController」「3 → MessageController」** という分け方でした。

### Step 5-2: URL が同じだから同じ Controller、ではない

URL の前半が `/api/dm/...` だから DmController に集約、というのは **間違った判断基準** です。

例えば次のような URL は、URL 階層的には同じでも担当する責務が異なります。

```
GET  /api/dm/rooms          ← ルームのリスト
GET  /api/dm/rooms/42        ← ルームの詳細
GET  /api/dm/rooms/42/messages  ← その中のメッセージ一覧
```

ここで「ルームを操作する」と「メッセージを操作する」は別の関心事です。**URL 階層よりも、扱うリソースの種類が判断基準** です。

### Step 5-3: F-04 で 1 Controller に集約した理由

F-04 では `/api/workspaces/{wsId}/channels` と `/api/channels/{id}` の 2 系統を **同じ ChannelController に集約** しました。理由：

- 両方とも「チャンネルというリソース」を扱っている
- どちらも `Channel` Entity の CRUD
- 分けると「create はこっち、get はあっち」と読みにくい

URL は 2 系統に分かれているが、**扱うリソースは同じ** だったので集約が正解でした。

### Step 5-4: F-06 で分けた理由

F-06 では：

- DM ルームの作成 / 一覧 → DmRoom リソース → DmController
- DM メッセージの履歴 → Message リソース（dm_room_id 列に紐づく） → MessageController

DM ルームと DM メッセージは **別の Entity / 別の Repository / 別のドメイン概念** です。これを 1 つの Controller に入れると、責務が混ざります。

具体的に：

- DmController は「ルームの寿命」を管理する
- MessageController は「ルームに乗っているメッセージの寿命」を管理する

これは URL の前半が同じでも、ドメインモデルとして別物です。だから別 Controller。

### Step 5-5: 判断基準の一般化

Controller の境界を引くときの判断基準は次の順です。

1. **扱うリソース（ドメイン上の Entity）が同じか？** → 同じなら集約
2. **責務（CRUD の対象）が同じか？** → 同じなら集約
3. **URL 階層が同じか？** → これは判断基準にしない

URL 階層は **最後の最後** に考えるものです。最初に見るのは「ドメイン的に同じものを扱っているか」。

### Step 5-6: 例えると「役所の窓口」

Controller は役所の窓口のようなものです。

- **住民票** を扱う窓口 = UserController
- **転居届** を扱う窓口 = MoveController
- **転居届の中の引越し荷物の補助申請** = （新リソース） MoveSupportController

「窓口の名前」を住所階層で決めると変なことになります。引越しに関わる手続きでも、それが「転居届」なのか「補助申請」なのかで窓口を変える、というのが自然です。**ドメイン上の区別** を窓口（Controller）に反映するのが正解です。

### Step 5-7: 引き出し5「Controller 境界の判断」

**引き出し**：Controller の境界は、**「扱うリソース（Entity）が同じかどうか」** で引く。URL 階層は判断基準にしない。同じリソースなら 2 系統 URL でも 1 Controller、別リソースなら同じ URL 前半でも別 Controller。

**AI への指示テンプレ**

> このエンドポイントを実装するときは、**Controller の境界を URL ではなく扱うリソースで引いて** ください。
> - リソース A（例：DmRoom）の CRUD → AController
> - リソース B（例：Message）の CRUD → BController
> URL 階層が同じでも、扱う Entity / 責務が違うなら別 Controller に入れてください。
> 過去の参考: F-04 はリソースが同じだったので 1 Controller に集約、F-06 はリソースが違うので別 Controller に分けています。
