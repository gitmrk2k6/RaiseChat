## 1. 前提知識 — F-04 で何を作ったのか

判断の話に入る前に、F-04 で **物理的に何が増えたか** を一度整理する。これがクリアでないと、後続の章が「何の話?」になりがち。

### 1.1 そもそもチャンネルとは（モデル上の意味）

Slack で言う「**#general**」や「**#random**」のような、メッセージを投稿する場のこと。RaiseChat では:

- 1 つのワークスペース（職場の単位）の中に、複数のチャンネルがある
- 1 つのチャンネルには、複数のユーザーが参加できる
- チャンネルには **PUBLIC（公開）** と **PRIVATE（非公開）** の 2 種類がある
  - PUBLIC: ワークスペースに居る人なら誰でも見える / 参加できる
  - PRIVATE: 招待された人だけが見える / 参加できる
- 例外的に **`general`** という名前のチャンネルは特別扱い（退出できない / 削除できない）

### 1.2 F-04 で実装した 6 つの操作

| 番号 | URL の例 | 何をする |
| --- | --- | --- |
| 1 | `POST /api/workspaces/{wsId}/channels` | 新しいチャンネルを作る |
| 2 | `GET /api/workspaces/{wsId}/channels` | ワークスペース内のチャンネル一覧を取る |
| 3 | `GET /api/channels/{id}` | チャンネル 1 つの詳細を取る |
| 4 | `POST /api/channels/{id}/join` | チャンネルに参加する |
| 5 | `POST /api/channels/{id}/leave` | チャンネルから退出する |
| 6 | `DELETE /api/channels/{id}` | チャンネルを削除する（論理削除） |

これに加えて、**ワークスペースを新規作成したときに `general` チャンネルを自動で作る** という機能を、F-03 のワークスペース作成処理に追加した。

### 1.3 登場するデータ（テーブル）

| テーブル | 1 行が表すもの |
| --- | --- |
| `channels` | チャンネル 1 つ（名前、PUBLIC/PRIVATE、削除日時など） |
| `channel_members` | 「ユーザー A がチャンネル B に参加している」関係 1 つ |

`channel_members` には「参加日時」「退出日時」のような列があり、**退出してもこの行は消さない**（後述）。

### 1.4 認証の前提

すべての操作はログインが必要。リクエストヘッダに JWT（前回 F-01 で実装したログイン後のトークン）を付ける。誰がログインしているかは Spring がフィルタで取り出してくれて、サービス層では「リクエストしたユーザー ID」が引数として渡ってくる前提で考える。

ここまでが前提整理。以降の 4 章で、F-04 で迫られた 4 つの設計判断を順に深掘りする。

## 2. 重点章 1 — 可視性チェックをどこに置くか

### 2.1 用語整理

| 言葉 | 1 行説明 |
| --- | --- |
| **可視性チェック** | 「このユーザーがこのデータを見て良いか」を判定すること。NG なら HTTP の 403（禁止）を返す |
| **Repository（リポジトリ）** | DB に SQL を投げる窓口の役。「条件に合う行を持ってきて」と頼む |
| **Service（サービス）** | アプリケーションの処理を組み立てる場所。Repository を呼んで取得した結果をどう加工し、誰に返すかを決める |
| **ページング** | リストが大量にあるとき、一度に全部返さず「20 件ずつ」とかに分けて返す仕組み |
| **EXISTS サブクエリ** | SQL の中に書ける「別の表にこの条件に合う行が 1 件でもあるか」という問い合わせ。1 行も無ければ false、1 行でもあれば true |

### 2.2 何が問題だったか — 「PRIVATE は招待された人だけ見える」をどう守るか

PRIVATE チャンネルのルール: **「メンバーじゃない人には、そもそも存在を見せたくない」**。

これは 2 つの場面で問題になる:

1. **チャンネル一覧** を返すとき: ワークスペースに 100 個チャンネルがあって、そのうち 10 個が PRIVATE で、ユーザーがメンバーなのが 2 個だったら、返すのは **92 個** にしないといけない（PUBLIC 90 個 + 自分が参加している PRIVATE 2 個）
2. **チャンネル 1 個の詳細** を返すとき: そのチャンネルが PRIVATE でユーザーがメンバーじゃなければ、403 を返す

このとき、可視性チェックを **どこに書くか** が判断ポイントになる。

### 2.3 選択肢の比較

選択肢は 2 つある。

#### 選択肢 A: SQL の WHERE に条件を埋め込む（Repository 側でやる）

「SQL を投げる時点で『見えないものは結果に含めない』ように条件を書く」やり方。Repository に「PRIVATE は自分がメンバーのものだけ返して」とお願いする。

- 例えると: 図書館の司書に「禁帯出の本は除いて、貸出可能なものだけ持ってきて」と頼むイメージ。司書（Repository）が条件付きで持ってくる
- 結果として返ってくる行は、**最初から見えるものだけ**

#### 選択肢 B: 全部取ってきてからアプリで判定（Service 側でやる）

「SQL は全件取ってきて、Service の中で 1 件ずつ『これは見て良い? 良くない?』を判定する」やり方。

- 例えると: 司書には「全部持ってきて」と頼み、自分の手元で「これは禁帯出だから返す、これは OK だから貸す…」と仕分けるイメージ
- 結果として最終的に返るのは絞ったあとのもの

### 2.4 リスト系（チャンネル一覧）でなぜ A を選んだか

ここで **ページング** が効いてくる。

ユーザーが「最初の 20 件ください」とリクエストしてきたとき:

- **A の場合**: SQL の段階で「見えるもの 20 件」を取る → 返すのも 20 件
- **B の場合**: SQL で「全件取ってきて」と頼むのは現実的じゃない。仕方なく「先頭 20 件取って」と頼むと、その 20 件のうち見えないものを除外することになり、**最終的に返るのは 18 件、15 件のようにバラバラ** になる

B でやると「20 件下さい」と頼んだのに毎回違う件数が返ってきて、画面の表示も次のページの呼び出しも狂う。ページングは **「件数が正確であること」が前提** の仕組みなので、B は致命的に相性が悪い。

だから **リスト系は A（SQL に条件を埋め込む）一択**。

### 2.5 詳細系（チャンネル 1 個取得）でなぜ B を選んだか

詳細系では、状況が変わる。1 つしか取らないので、ページングの問題は起きない。

ここで重要なのは **HTTP のステータスコードを使い分けたい** こと:

- そのチャンネルが **存在しない** → `404 Not Found`（ない）
- そのチャンネルは存在するが **見る権限がない** → `403 Forbidden`（あるけど見せない）

この 2 つを使い分けると、API を使う側（フロントエンド）が「あれ、リンクが古いのかな?」「あれ、招待されてないのかな?」と区別できる。

- A でやると: SQL の段階で「見えないものは結果に含めない」ので、PRIVATE で非メンバーの人が叩くと「結果ゼロ」 → 404 を返すしかない → 「存在しない」と区別できない
- B でやると: まず Repository に「ID で 1 件取って」と素直に頼み、取れたあと Service で「この人は見て良いか?」をチェックする → 取れなければ 404、取れたけどダメなら 403 と分けられる

詳細系では **「あるけど見せない」を表現するために B が自然**。

### 2.6 実際の F-04 は多段になっている

ここまでで「リストは A、詳細は B」と単純化したが、実際の F-04 ではどちらの操作にも **粗い権限チェックは B、細かい絞り込みは A** という構造が入っている。

例: チャンネル一覧 API

1. まず Service の先頭で **「あなたは このワークスペースのメンバー?」** を B で判定（メンバーでなければ即 403）
2. メンバーであることが確認できてから、**「PRIVATE のうち自分が参加しているもの」** を A で SQL に埋め込んで取得

つまり「粗い権限は B で先に弾く → 細かい行レベルの絞り込みは A」という二段構え。

例えると: 会員制ジムに入るとき、まず入口で **会員証チェック**（粗い権限、B 型）。中に入れたら **個別のラウンジは VIP 会員専用** みたいな細かい区分けは中で別の仕組みで弾く（細かい絞り込み、A 型）。

### 2.7 引き出し

| シーン | AI への指示 |
| --- | --- |
| リスト系 API で可視性ルールがある | 「可視性条件は Repository の SQL に埋め込んで。ページングと整合するように」 |
| 詳細系 API で「ある / ない」と「見て良い / だめ」を分けたい | 「Repository は素直に 1 件取得、Service で権限チェックして 403 と 404 を分けて」 |
| 粗い権限 + 細かい絞り込みが両方あるとき | 「粗い権限（メンバーか否か）は Service の先頭で先に弾いて、細かい絞り込みは Repository に任せて」 |
| 可視性ルールの設計時に最初に問うべきこと | **「可視性の単位は『行ごと』? それとも『親リソース単位』?」**。親単位なら B で 1 回チェックすれば子は素通しで OK |

### 2.8 自問で確かめる

F-05 メッセージ API で「チャンネル内のメッセージ一覧」を作るとき、どう設計する?

→ メッセージは「親チャンネルへのアクセス権」で見えるか決まる（メッセージごとに権限はない）ので、**「親チャンネルへのアクセスを Service で B 型チェック → 通ったらメッセージは『WHERE channel_id = ?』で全部取る（A だが可視性条件は無し）」** が自然。

これが言えるようになっていれば、この章の引き出しは身についている。

## 3. 重点章 2 — URL の階層と Controller の境界

### 3.1 用語整理

| 言葉 | 1 行説明 |
| --- | --- |
| **URL の階層** | URL を `/` で区切ったときの並び順。`/api/workspaces/1/channels` なら「api → workspaces → 1 → channels」と入れ子になっている |
| **リソース指向 URL** | URL に動詞を入れず、名詞（モノの名前）で組み立てる設計。「チャンネル一覧を取る」を `GET /api/channels` と書く（`getChannels` のような動詞は使わない） |
| **Controller クラス** | リクエストの受付窓口役の Java クラス。1 つのクラスにいくつもの「窓口メソッド」が集まる |
| **クラスレベルのマッピング** | Controller クラスの先頭に「このクラスは `/api/workspaces` 配下を担当」と書く方式。配下のメソッドにはプレフィックス（頭につく部分）が自動で付く |
| **メソッドレベルのマッピング** | クラスの先頭には何も書かず、メソッド 1 つ 1 つに「私は `/api/workspaces/{wsId}/channels` を担当」とフルパスで書く方式 |

### 3.2 何が問題だったか — F-04 の URL は 2 系統に分かれた

設計上、チャンネル関係の URL は次の 2 種類に分かれた:

| 系統 | URL の頭 | 例 |
| --- | --- | --- |
| ワークスペース配下 | `/api/workspaces/{wsId}/channels` | 作成、一覧 |
| チャンネル単体 | `/api/channels/{id}` | 詳細、参加、退出、削除 |

なぜ 2 系統になるかというと、リソース指向 URL の慣習に従ったため:

- 「**このワークスペースの中の** チャンネルを作る / 一覧で見る」は、文脈に **ワークスペースの ID** が必要なので親階層に置く
- 「**このチャンネル**（ID で特定済み）に参加する / 削除する」は、ワークスペースの ID は不要（チャンネル ID から逆引きできる）ので親階層は要らない

URL は「リソースの場所を表す住所」なので、文脈に必要な情報だけが階層に入るのが自然。だから 2 系統に分かれること自体は **正しい設計**。

### 3.3 選択肢の比較

URL が 2 系統あるとき、それを受け付ける Controller クラスをどう分けるか:

#### 選択肢 1: URL の頭で分ける（クラスレベルマッピングを使う）

- `WorkspaceController` クラスを `/api/workspaces` 担当として、その中に「チャンネル作成」「チャンネル一覧」も入れる
- `ChannelController` クラスを `/api/channels` 担当として、その中に「チャンネル詳細」「参加」「退出」「削除」を入れる

つまり **URL の階層構造に合わせて** Controller を分ける。

#### 選択肢 2: 機能で分ける（メソッドレベルで個別にフルパス指定）

- 1 つの `ChannelController` クラスを作り、URL の頭が違っても全部この中に書く
- クラスレベルでは「ここは何の URL を担当」と宣言しない
- 各メソッドが「私は `/api/workspaces/{wsId}/channels` を担当」「私は `/api/channels/{id}` を担当」とフルパスを書く

つまり **「チャンネルという機能を扱う窓口」を 1 つにまとめる**。

### 3.4 F-04 で選択肢 2 を選んだ理由

「**Controller の境界は URL ではなく、機能（責任範囲）で引く**」 という考え方を採用した。

選択肢 1（URL で分ける）でやると、こうなる:

- `WorkspaceController` の中に「ワークスペース作成 / ワークスペース一覧 / ワークスペース詳細 / **チャンネル作成 / チャンネル一覧**」が混在
- `ChannelController` の中に「チャンネル詳細 / 参加 / 退出 / 削除」

この場合、**「チャンネルというモノの責任範囲が 2 クラスに分裂する」**。チャンネルに関する仕様変更（例えば「作成時のバリデーション規則を変える」と「削除時のバリデーション規則を変える」）が、2 つのクラスを行き来する作業になる。

選択肢 2（機能で分ける）にすると:

- `WorkspaceController` の中にはワークスペース系のみ
- `ChannelController` の中にチャンネルに関するすべて（作成、一覧、詳細、参加、退出、削除）

**「チャンネルの面倒は 1 つのクラスが見る」** という整理になり、変更が 1 箇所で済む。

例えると: 役所の住民票関係。「窓口で住民票を取る」と「コンビニ交付で住民票を取る」では、お客さんの動線（URL）は違うけれど、業務（住民票発行）は同じ。「住民票係」が両方を引き受けたほうが、住民票のルールを変えるときに 1 つの係だけ動かせば良い。窓口の場所（URL の階層）で係を分けると、両方を同期して変えないといけなくなる。

### 3.5 「機能で分ける」の判断材料

「機能のかたまり」をどう見極めるかには、複数の材料がある:

1. **扱っているリソース（モノ）が同じか**: チャンネルを扱っているなら 1 つにまとめる候補
2. **アクセス制御のルールが揃っているか**: 認証あり / なしが違うなら、同じモノでも分けたほうが良いことがある
3. **データの保存先（テーブル）が共通か**: 同じテーブルを触るなら 1 つにまとめる候補

例えば、将来「公開 URL で誰でも見られるチャンネル一覧」(`/api/public/channels`) を追加するとしたら、

- リソース: 同じ「チャンネル」
- アクセス制御: 認証不要（既存は全部認証必須）
- データ: 同じテーブル

**アクセス制御のルールが違う** ので、これは別の Controller に分けたほうが整理しやすい（認証系統ごとに見直しがしやすくなる）。

### 3.6 引き出し

| シーン | AI への指示 |
| --- | --- |
| URL が複数の階層に分かれるリソースを実装するとき | 「Controller はリソース（機能）単位で 1 つにまとめて。URL の階層に Controller を合わせない」 |
| クラスレベルマッピングを使うか迷ったとき | 「URL の頭が複数あるなら、クラスレベルマッピングは付けずに、各メソッドでフルパス指定で」 |
| 既存の WorkspaceController にチャンネル系メソッドが混ざりそうになったら | 「チャンネル機能は ChannelController に分離して。URL の親階層を理由に WorkspaceController に入れない」 |
| 「同じ機能か」を判断する材料 | **リソース / アクセス制御 / データ保存先** の 3 つを見て、揃っていれば 1 つに、ズレていれば分ける |

### 3.7 自問で確かめる

F-05 でメッセージ API を実装するとき、`POST /api/channels/{id}/messages`（送信）と `PUT /api/messages/{id}`（編集）と `DELETE /api/messages/{id}`（削除）が登場する。これは どこに置く?

→ メッセージというリソースを扱っているので、**新しい `MessageController` クラスを 1 つ作って 3 つとも入れる** のが自然。URL の頭が 2 系統あっても、機能が同じ「メッセージ」なら 1 つにまとめる。

これが言えるなら、この章の引き出しは身についている。

## 4. 重点章 3 — 論理削除と再参加対応

### 4.1 用語整理

| 言葉 | 1 行説明 |
| --- | --- |
| **物理削除** | DB の `DELETE` 文で行を本当に消すこと。消えた行は元に戻せない（バックアップから戻すしかない） |
| **論理削除** | 行は残したまま「これは消えた扱い」と示す印（フラグ、削除日時など）を立てる。普段の表示からは外す |
| **UNIQUE 制約** | DB のルールの 1 つ。「この列（または列の組み合わせ）の値は表全体で重複してはいけない」と宣言する仕組み |
| **複合 UNIQUE** | 列を組み合わせた重複禁止。例: `(channel_id, user_id)` の組み合わせは表全体でユニーク |
| **再参加** | いったん退出したユーザーが、同じチャンネルにもう一度参加すること |

### 4.2 何が問題だったか — DB のルールと業務要件がぶつかる

F-04 で扱った 2 つの場面で、論理削除の判断が必要になった。

#### 場面 A: チャンネルそのものを削除

要件: 「削除されたチャンネルは普段の表示からは消えるが、過去のメッセージや履歴は残したい」（将来、監査や検索で必要になる可能性がある）。

#### 場面 B: チャンネルから退出 → 再参加

要件: 「ユーザーは退出できる。退出した履歴は残したい。だが将来同じチャンネルにもう一度入る（再参加する）こともある」。

DB 側にはこんなルールがある:

- `channel_members` テーブルには **`(channel_id, user_id)` の組み合わせはユニーク** という制約がある（同じ人が同じチャンネルに 2 行存在してはいけない）

これと「退出履歴は残したい」「再参加できる」を両立しなければならない。

### 4.3 選択肢の比較

#### 選択肢 1: 退出 = 行を物理削除、再参加 = 新規 INSERT

退出するときに `channel_members` から該当行を `DELETE` で消す。再参加するときは新しい行を `INSERT` する。

- 利点: シンプル。行が 1 つだけ存在する状態が常に保証される
- 欠点: **退出履歴が残らない**（消えてしまったので「いつ退出したか」が分からなくなる）
- 欠点: UNIQUE 制約とは噛み合うが、業務要件「履歴を残したい」と噛み合わない

#### 選択肢 2: 退出 = 「退出日時」を書き込む（行は残す）、再参加 = 「退出日時」を空に戻す

退出するときに `channel_members` の行はそのまま残し、「退出日時」という列に現在時刻を書き込む。再参加するときはその「退出日時」を `NULL`（空）に戻す。

- 利点: **退出履歴がそのまま残る**（「退出日時」を見れば、いつ退出したか分かる）
- 利点: 行は 1 行のまま、UNIQUE 制約と矛盾しない
- 利点: 普段「現在のメンバー」を取るときは「退出日時が空のものだけ」を絞り込む条件を 1 つ足せば良い

### 4.4 F-04 で選択肢 2 を選んだ理由

業務要件「履歴を残したい」と DB ルール「重複禁止」を両立するには、**「消す」ではなく「印を付ける」** しかない。これが論理削除のパターン。

ジムの会員管理に例えると:

- 退会するとき、会員カードを破棄する → 再入会のとき新しい会員カードを発行 → カードがどんどん増える、過去の退会履歴を別途管理しないと残らない
- 退会するとき、会員カードに **「退会日」を書き込む** → 再入会のときその退会日を消す → カードは 1 枚で済み、過去の退会日を見れば履歴が読み取れる

F-04 ではジムの後者と同じ仕組みを使った。

### 4.5 チャンネル削除（場面 A）でも同じ思想

チャンネルそのものの削除でも、同じ論理削除を使った。`channels` テーブルに **「削除日時」** という列があり、削除のときに現在時刻を書き込む。普段のチャンネル一覧 SQL は **「削除日時が空のものだけ」** を絞り込む条件を入れて取得する。

これによって、

- 削除されたチャンネルは普段の一覧から消える（ユーザー視点では「消えた」)
- DB には残っている（過去メッセージとの参照関係も壊れない）
- 万一「削除したけど復活したい」が出てきても、削除日時を空にすれば一発で復活できる

### 4.6 論理削除と物理削除の使い分け

論理削除は万能ではない。物理削除を選ぶべき場面もある:

| 状況 | 選ぶ削除方式 | 理由 |
| --- | --- | --- |
| 履歴を残したい、参照関係を壊したくない | 論理削除 | 削除済みでも参照は維持される |
| 関連データが大量にあり、削除後に絶対に参照しない | 物理削除（外部キーの CASCADE 削除） | 行が残るとストレージと SQL のパフォーマンスを圧迫する |
| 個人情報の完全消去要請（GDPR の忘れられる権利など） | 物理削除 | 「印を付けるだけ」ではコンプライアンス要件を満たさない |
| 一時的なデータ（セッション、トークン）の期限切れ | 物理削除 | 履歴を残す意味がない |

要件を聞いたときに「これは履歴を残すべきか? 完全消去すべきか?」を最初に確認するのが起点。

### 4.7 副産物 — 「ついでに消す」が要らなくなる

論理削除を採用しておくと、F-04 でやっていない別の便益も生まれる。

例えば「チャンネルを削除したらそのチャンネルのメッセージも全部消したい」要件が出てきたとする。物理削除なら「メッセージも一緒に消す」処理が必要だが、論理削除なら:

- チャンネルに「削除日時」を書き込むだけ
- メッセージ取得時に「親チャンネルが削除されていないか」をフィルタすれば、自動的に表示されなくなる
- メッセージ自体は何もしなくて良い

「ついでの処理」が要らなくなる。これは次の章（副作用配置）にも繋がる重要な気づき。

### 4.8 引き出し

| シーン | AI への指示 |
| --- | --- |
| 削除機能を作る要件が出てきた | 「履歴を残す必要があるか確認してから、論理削除か物理削除を選んで。RaiseChat の方針は基本論理削除」 |
| 退出 / 再参加のような状態変化がある関係テーブル | 「(channel_id, user_id) のような複合ユニーク制約と矛盾しないように、退出は『退出日時』を書き込む方式で。再参加は『退出日時』を NULL に戻して」 |
| 一覧取得 SQL を書くとき | 「論理削除対応で『削除日時が空のものだけ』を WHERE に必ず入れて」 |
| 「○○を消したら ●● も一緒に消す」要件が出てきたら | **まず「本当に消す必要があるか?」と疑う**。論理削除なら親が消えたら子は自動的に表示されなくなる |

### 4.9 自問で確かめる

F-05 で「メッセージの削除」を作るとき、どう設計する?

→ メッセージにも `messages.deleted_at` 列がある前提で（DB スキーマ上は既に用意済み）、**論理削除を採用**。削除時は `deleted_at` に時刻を書き込み、メッセージ一覧取得時は「`deleted_at IS NULL` のもの」を絞り込む。**物理削除はしない**（過去の引用やスレッドの参照関係を壊したくないため）。

これが言えるなら、この章の引き出しは身についている。

## 5. 重点章 4 — 副作用処理をどこに書くか

### 5.1 用語整理

| 言葉 | 1 行説明 |
| --- | --- |
| **副作用** | メインの処理に付随する追加の処理。「ワークスペースを作る」がメインなら、「同時に general チャンネルも作る」が副作用 |
| **トランザクション** | DB の処理を「全部成功か、全部失敗か」のひとまとまりとして扱う仕組み。途中で失敗すると、それまでにやった処理も巻き戻る |
| **トランザクション境界** | 「ここからここまでが 1 つのトランザクション」の範囲。Service のメソッド 1 つを境界にするのが普通 |
| **直書き** | 別の Service を呼ばずに、自分のメソッドの中で直接処理を書くこと |
| **呼び出し** | 別の Service が用意してくれているメソッドを呼んで処理を任せること |
| **DRY 原則** | 「Don't Repeat Yourself」の略。同じことを 2 箇所に書かない、1 箇所にまとめる、というプログラミングの原則 |

### 5.2 何が問題だったか — ワークスペース作成時の general 自動作成

要件: **「ワークスペースを新しく作るとき、必ず `general` チャンネルも同時に作る」**。これは F-05 でメッセージ機能を作るときに「最低 1 つチャンネルが必要」という前提があるため。

このとき、`general` 作成のコードを誰が書くか:

- ワークスペース作成担当（`WorkspaceService`）が、自分の `create()` メソッドの中で `general` まで作る（直書き）
- ワークスペース作成担当が、チャンネル作成担当（`ChannelService`）の `create()` メソッドを呼んで作ってもらう（呼び出し）

### 5.3 一見すると「呼び出し」が良さそうに見える

`ChannelService.create()` は **チャンネル作成のロジックを 1 箇所にまとめた** メソッド。バリデーション、メンバー追加、ログなど、チャンネル作成に必要な処理が全部入っている。

「**1 箇所にまとめる**」という DRY 原則からすると、ワークスペース作成からもこれを呼ぶのが自然に見える。general も「ただのチャンネル」なので、`ChannelService.create()` を再利用すれば、

- 同じ処理を 2 箇所に書かなくて良い
- 後で「チャンネル作成時にログを出すように変える」みたいな変更が 1 箇所で済む

DRY を信じて、呼び出し方式を選ぶのが普通の判断。

### 5.4 でも F-04 では「直書き」を選んだ

理由が 3 つある。

#### 理由 1: トランザクションを揃えたい

ワークスペース作成と general 作成は **不可分** だ。「ワークスペースは作れたけど general 作成で失敗しました」という中途半端な状態を作ったら、その後の F-05 メッセージ API の「general に最初のメッセージを送ろうとしたら無い」という事故が起きる。

直書き方式なら、`WorkspaceService.create()` の中ですべての処理が 1 つのトランザクションに入る。どこで失敗しても全部巻き戻る。

呼び出し方式でも工夫すればトランザクションを揃えられる（Spring の `@Transactional` の propagation 設定など）が、**最初から 1 つのトランザクションに入れる直書きの方が、トランザクション境界の設計でミスしにくい**。

#### 理由 2: ChannelService の事前チェックと噛み合わない

`ChannelService.create()` には **「あなたはワークスペースのメンバーですか?」という事前チェック** が入っている（チャンネル作成は当該ワークスペースのメンバーじゃないと許可されないため）。

ところが、ワークスペースを **まさに今作っている瞬間** は、メンバー登録が一瞬前に終わったところ。順番が:

1. ワークスペース行を INSERT
2. メンバー行（OWNER）を INSERT
3. general チャンネルを作る ← ここで `ChannelService.create()` を呼ぶ?

この時点でメンバー登録は終わっているので大丈夫…と思いきや、トランザクションの中ではまだコミットされていないので、別のサービスから「あなたはメンバーですか?」と問うと **見えるはずだけど見えないかもしれない** という微妙な状況になる（DB の分離レベルや実装次第）。

それより、「ワークスペース作成のオマケなんだから事前チェックは不要、信じて INSERT する」のほうが筋が通る。直書きならこの事前チェックを通らずに済む。

#### 理由 3: 「業務の一塊」として捉えたい

`general` チャンネルは、ワークスペース作成という業務の **オマケ** であって、独立した「チャンネル作成」ではない。

- ユーザーが「チャンネルを作る」と能動的に呼んだわけではない（裏で自動的に作られる）
- general は「最初から無くてはならない、特別なチャンネル」（後から退出禁止、削除禁止のルールも入れる）

つまり「general を作る」は「ワークスペースを作る」の中の **付帯作業** として捉えるのが意味的に自然。それをワークスペース作成担当の責任範囲に置く（直書きする）と、コードの読み手は「ワークスペース作成の中身を見れば、何が一緒に作られるか全部分かる」状態になる。

呼び出し方式だと、`WorkspaceService.create()` を読んでいる人が「あれ、general はどこで作られているんだ?」と `ChannelService.create()` までジャンプしないと分からない。

### 5.5 「直書き vs 呼び出し」の 3 軸での判断

整理すると、次の 3 つの軸で判断する:

| 軸 | 直書きが向いている | 呼び出しが向いている |
| --- | --- | --- |
| **トランザクション** | A と B を「失敗したら全部巻き戻し」にしたい | A と B が独立しても良い、別トランザクションで OK |
| **事前チェックの整合性** | B 単体の事前チェックが A の途中状態と噛み合わない | B が常に独立して動く前提で書かれていて、A から呼んでも問題ない |
| **B の独立性** | B はあくまで A の付帯作業で、単体では使わない | B は単体でも頻繁に呼ばれる、本来独立した機能 |

F-04 では 3 軸すべてが「直書きが向いている」側に寄っていたので、直書きを選んだ。

### 5.6 例えると — 会社設立時の総務部設立

会社を新しく設立するとき、定款で「総務部を必ず置く」と決められていたとする。

- 直書き方式: 設立担当者が、設立手続きの中で総務部の設置申請も自分で出す
- 呼び出し方式: 設立担当者が、「総務部設置担当」を別途呼んで設置してもらう

F-04 が選んだのは前者。理由を会社設立に重ねると:

- 設立失敗時は総務部設置申請も無効にしたい（トランザクション）
- 総務部設置担当は本来「すでに存在する会社の中で総務部を新設する」前提で動いているので、「設立中の会社」を渡すと「あれ、登記が完了してないよ」とエラーにする可能性がある（事前チェックの不整合）
- 総務部は設立のオマケ業務で、単体で「総務部を後から新設」する必要はない（独立性が低い）

### 5.7 引き出し

| シーン | AI への指示 |
| --- | --- |
| 「機能 A を作るとき必ず B もする」要件が出てきた | 「3 軸（トランザクション / 事前チェック / 独立性）で判断して、直書きが妥当なら A の中に B のロジックを直接書いて。呼び出しが妥当なら別 Service を呼んで」 |
| トランザクションを揃えたい場面 | 「失敗したら全部巻き戻したいので、同じトランザクション境界の中で直書きで」 |
| ある Service の事前チェックが、別 Service の途中状態と噛み合わないとき | 「B の事前チェックが A の途中状態と噛み合わないなら、B を呼ばず A の中に直書きで」 |
| 「ついでに消す / 作る」要件が出てきたら | **まず「論理削除や CASCADE で済まないか?」を疑う**。それで済むなら副作用ロジックを書かなくて良い |

### 5.8 自問で確かめる

F-05 でメッセージを送信したとき、「最終アクセス日時の更新」のような副作用が必要だとする。これは「メッセージ送信処理に直書き」か「別 Service を呼ぶ」か?

→ 3 軸で見る:
- トランザクション: メッセージ送信が成功したら最終アクセス日時も更新したい → 揃えたほうが自然 → 直書き寄り
- 事前チェック: 別 Service の事前チェックは特に問題ない（自分自身の最終アクセス時刻を更新するだけ） → 中立
- 独立性: 最終アクセス日時更新は、メッセージ送信以外（ログイン時、画面遷移時など）でも呼ばれる可能性が高い → 呼び出し寄り

総合すると、**最終アクセス日時更新は独立した Service にして呼び出すのが妥当**（独立性が決め手）。

このように 3 軸で迷わず判断できるなら、この章の引き出しは身についている。

- `JOIN FETCH` での N+1 回避 — F-04 のチャンネル一覧クエリも `JOIN FETCH c.createdBy JOIN FETCH c.workspace`

これらは F-04 学習として再学習する必要はない（F-03 ノートで理解できていれば適用するだけ）。
