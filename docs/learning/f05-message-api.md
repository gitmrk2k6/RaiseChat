# F-05 メッセージ API 学習ノート

**対象**: チャンネルメッセージの送受信・編集・削除（REST + WebSocket + Redis Pub-Sub）  
**前提知識**: なし（HTTP の基本概念があれば十分）

## Step 1: HTTP の「仕組み」をもう一度確認する

まず WebSocket を理解するために、HTTP の動き方を復習します。

HTTP は **「リクエスト → レスポンス」の繰り返し**で成り立っています。

### 郵便のたとえ

HTTP の通信は **郵便のやり取り** に似ています。

- あなた（クライアント）が手紙（リクエスト）を書いて投函する
- 郵便局（サーバー）が処理して、返信（レスポンス）を送り返す
- やり取りが終わると、そのつながりは切れる

重要なのは **「あなたが手紙を出さない限り、郵便局からは何も届かない」** という点です。

### HTTP でチャットを作ろうとすると

誰かが新しいメッセージを送ったとき、それを他のユーザーの画面に表示したいとします。

HTTP だけで実現しようとすると、ブラウザが「新しいメッセージありますか？」と何度も何度も聞き続けるしかありません。これを **ポーリング** と呼びます。

```
ブラウザ: 「新しいメッセージありますか？」→ サーバー: 「ないです」
（1秒後）
ブラウザ: 「新しいメッセージありますか？」→ サーバー: 「ないです」
（1秒後）
ブラウザ: 「新しいメッセージありますか？」→ サーバー: 「1件あります！」
```

これは非効率です。サーバーへの無駄なリクエストが大量に発生し、新着メッセージも「次に聞くまで」伝わりません。1秒ポーリングだと最大1秒遅れが生じます。

**WebSocket が登場した背景**: リアルタイム通信に HTTP は根本的に向いていない、という問題意識から生まれました。

---

## Step 2: WebSocket とは何か

WebSocket は **「一度接続したら、互いに好きなタイミングで送り合える通話」** の仕組みです。

### 電話のたとえ

- 最初に「接続確立」（HTTP でハンドシェイク）して電話をかける
- 通話中は、どちらからでも好きなタイミングで話せる
- 切断（close）するまで接続は維持される

HTTP と WebSocket の最大の違いは **サーバーからクライアントに「プッシュ」できるかどうか**です。

| | HTTP | WebSocket |
|---|---|---|
| 通信方向 | クライアント→サーバーのみ | 双方向（どちらからでも） |
| 接続の維持 | リクエストごとに切断 | 明示的に切断するまで持続 |
| リアルタイム性 | ポーリング必要 | イベント発生時に即送信できる |
| 用途 | API 呼び出し、ページ取得 | チャット、通知、ライブ更新 |

### RaiseChat での使い方

- ユーザーが「送信ボタン」を押す → WebSocket でサーバーにメッセージを送信
- サーバーが全チャンネルメンバーの画面に → WebSocket でメッセージをプッシュ

## Step 3: STOMP プロトコルとは何か

WebSocket は「双方向通信できる電話回線」ですが、**話し方のルールが決まっていません**。

文字列をそのまま送り合うことはできますが、「どのチャンネルへのメッセージか」「ACK なのか通常のメッセージか」などを自分で解析しなければなりません。

**STOMP（Simple Text Oriented Messaging Protocol）** は、WebSocket の上に乗る **「会話のルールブック」** です。

### 居酒屋の注文システムのたとえ

居酒屋で注文する場面を想像してください。

- **WebSocket だけ**: テーブルから厨房に直接叫ぶ。「ビール！」「えっ何テーブルですか？」「3番です！」「数量は？」 → 毎回ルールを自分で作る必要がある
- **STOMP あり**: 「3番テーブル、生ビール2つ、以上」という決まったフォーマットで注文する。厨房もそのフォーマットを理解している

### STOMP の3つの主要操作

| 操作 | 意味 | 例え |
|------|------|------|
| **SUBSCRIBE** | 「このトピックの配信を受け取りたい」と登録する | 「○○チャンネルの新着を通知してください」と申し込む |
| **SEND** | 宛先（destination）にメッセージを送る | 「このチャンネルに投稿する」 |
| **MESSAGE** | サーバーが購読者にメッセージを届ける | 「購読者全員に届ける」 |

### RaiseChat での STOMP の使い方

```
クライアント → サーバー: SUBSCRIBE /topic/channels/1
（「チャンネル1の新着を受け取ります」と宣言）

クライアント → サーバー: SEND /app/channels/1/messages  {"body":"こんにちは"}
（「チャンネル1にメッセージを送ります」）

サーバー → クライアント全員: MESSAGE /topic/channels/1  {...メッセージデータ...}
（全購読者にブロードキャスト）
```

## Step 4: SockJS の役割

WebSocket は便利ですが、**すべての環境で使えるとは限りません**。

### WebSocket が使えないケース

- 古いブラウザ（まれ）
- 企業の厳格なプロキシ・ファイアウォール（HTTP 以外を遮断している環境）
- 一部のクラウドロードバランサー

### SockJS = WebSocket の「保険」

SockJS は「**WebSocket が使えない場合に自動で代替手段に切り替える**」ライブラリです。

優先度順に試みます：
1. WebSocket（最優先）
2. XHR Streaming（HTTP の長期接続）
3. XHR Polling（HTTP のポーリング）

### クライアントから見ると透明

アプリを使うユーザーは、どの方式が使われているかを意識しません。SockJS が裏でよしなにやってくれます。

**設計判断**: 今回 SockJS を採用したのは「すべての環境で確実に動くこと」を保証するためです。WebSocket だけでは動かない環境を想定外として切り捨てない、という判断です。

## Step 5: Spring の「メッセージブローカー」とは何か

STOMP の「配達屋さん」役を誰が担うかを決める必要があります。これを **メッセージブローカー** と呼びます。

### 宅配業者のたとえ

あるユーザーがメッセージを送ったとき、チャンネルを購読しているユーザー全員に届けるのがブローカーの仕事です。

- 「どのユーザーが /topic/channels/1 を購読しているか」を記憶している
- 新しいメッセージが来たら、購読者全員の接続に転送する

### Spring の2種類のブローカー

| | Simple Broker | Broker Relay |
|---|---|---|
| 実装 | Spring がメモリ内で管理 | RabbitMQ などの外部サーバーに丸投げ |
| インフラ | 追加不要 | RabbitMQ のセットアップが必要 |
| スケール | 1サーバーのみ | 複数サーバーでも可 |
| 安定性 | サーバー再起動で購読情報が消える | 外部サーバーが状態を保持 |

### 今回 Simple Broker を選んだ理由

**Redis は STOMP を話せない**からです。

Broker Relay が機能するには、外部ブローカーが STOMP プロトコルをサポートしている必要があります。RabbitMQ は対応していますが、今回使う Redis はしていません。

また、RabbitMQ を追加するのは今回の要件に対してオーバーエンジニアリングになります。

**では、複数サーバー対応はどうするのか？** → Step 8 で説明します。

## Step 6: アプリケーション宛先（/app と /topic）の設計

STOMP の宛先（destination）には2種類のプレフィックスが使われています。これはよく混乱するポイントなので丁寧に説明します。

### /app プレフィックス：「サーバーの処理が必要」

`/app/channels/1/messages` への SEND は、Spring が受け取って **MessageWebSocketController の処理を呼び出します**。

処理の流れ：
```
クライアント --SEND-→ /app/channels/1/messages
↓
MessageWebSocketController.sendMessage() が呼ばれる
↓
DB に保存、Redis に publish
```

### /topic プレフィックス：「ブローカーへの購読」

`/topic/channels/1` への SUBSCRIBE は、Simple Broker に直接届きます。Spring のコントローラを経由しません。

```
クライアント --SUBSCRIBE-→ /topic/channels/1
↓
Simple Broker が「このユーザーは /topic/channels/1 を待っている」と記録
↓
後で /topic/channels/1 にメッセージが来たときに転送
```

### なぜプレフィックスで分けるのか

「サーバーが処理すべきか」「ブローカーに直接渡すか」を区別するためです。

- `/app` ＝ 「受付カウンター」。スタッフが確認・処理する
- `/topic` ＝ 「メールボックス」。直接投函される

## Step 7: WebSocket 認証の仕組み

HTTP API では「リクエストのヘッダに JWT を入れて送る」のが認証の標準的な方法でした。

WebSocket では事情が異なります。

### なぜ HTTP と同じ方法が使えないのか

WebSocket 接続は一度確立されると、以降のメッセージは「ヘッダなしのストリーム」として流れます。最初の HTTP ハンドシェイクにはヘッダを付けられますが、その後の STOMP フレームには標準的な Authorization ヘッダという概念がありません。

### STOMP CONNECT フレームで認証する

STOMP には接続確立時に送る **CONNECT フレーム**があります。このフレームにカスタムヘッダを追加できます。

```
CONNECT
Authorization: Bearer eyJ...（JWT トークン）

```

クライアントは接続時にこのフレームを送り、サーバーはそこで JWT を検証します。

### ChannelInterceptor = 入口の警備員

**ChannelInterceptor** は「STOMP メッセージが処理される前に割り込む仕組み」です。

郵便物のX線検査機のようなイメージです：
- すべての STOMP フレームがここを通過する
- CONNECT フレームのときだけ JWT を取り出して検証する
- 正当なトークンなら「この接続はこのユーザーのもの」と記録する
- 不正なら接続を拒否する

### なぜ /ws/** を HTTP セキュリティで許可するのか

SockJS の接続開始時は、まず HTTP の GET リクエストが `/ws/info` などに飛びます（WebSocket か他の方法が使えるかの探索）。

この HTTP リクエストには JWT が付いていません。Spring Security のフィルターがここで弾いてしまうと、SockJS の初期接続が失敗します。

**解決策**: HTTP セキュリティ層では `/ws/**` を「無条件通過」させ、実際の認証は STOMP CONNECT の ChannelInterceptor で行います。セキュリティが緩くなるように見えますが、JWT なしで STOMP CONNECT を送っても弾かれるので問題ありません。

## Step 8: Redis Pub-Sub とマルチインスタンス問題

F-05 で最も重要な設計トピックです。

### 問題：1台のサーバーでは何も困らないが

1台のサーバーで動かす分には、Simple Broker だけで動きます。すべてのユーザーが同じサーバーに接続しているので、ブローカーが全員に届けられます。

```
ユーザーA ─── サーバー1 ─── ユーザーB
（Simple Broker がユーザーA, B の購読を管理）
```

### 問題：2台以上にスケールアウトすると

現実のシステムでは、トラフィックが増えたときに**サーバーを複数台に増やす（スケールアウト）**ことがあります。

```
ユーザーA ─── サーバー1
ユーザーB ─── サーバー2
```

ここでユーザーAがサーバー1にメッセージを送ると：

- サーバー1の Simple Broker は「ユーザーAとの接続を持つ」
- サーバー2の Simple Broker は「ユーザーBとの接続を持つ」
- **サーバー1とサーバー2は互いを知らない**

結果：ユーザーAがメッセージを送っても、ユーザーBの画面には何も表示されません。

### Redis Pub-Sub が架け橋になる

**Pub-Sub（パブリッシュ-サブスクライブ）** は「放送局とラジオ」のたとえが分かりやすいです。

- **放送局（Publisher）**: 番組（メッセージ）を電波で流す
- **ラジオ（Subscriber）**: 特定の周波数（チャンネル）を聞いている

Redis を共有の「電波塔」として使います：

```
ユーザーA → サーバー1 → Redis に "messages:channel:1" チャンネルで放送
                                 ↓
                     サーバー1 も受信 → ユーザーA に届ける
                     サーバー2 も受信 → ユーザーB に届ける
```

すべてのサーバーが「Redis の同じチャンネルをラジオで聞いている」ため、どのサーバー経由でメッセージが来ても全員に届きます。

### PatternTopic とは

チャンネルは 1番、2番、3番... と無数にあります。それぞれについて別々のラジオ（Subscriber）を用意するのは煩雑です。

**PatternTopic** はワイルドカードによる「一括購読」です。

`messages:channel:*` の `*` は「何でもよい」を意味します。チャンネル1も2も100も、すべて一つのリスナーで受け取り、チャンネル番号を取り出して適切な宛先に転送します。

## Step 9: メッセージの一生（全体の流れ）

ここまでの概念を、一つのメッセージが「送信されてから表示されるまで」の流れでまとめます。

### ケース：ユーザーAがチャンネル1に「こんにちは」を投稿

```
【クライアント】
ユーザーAが送信ボタンを押す
↓
WebSocket/STOMP: SEND /app/channels/1/messages {"body":"こんにちは"}
↓

【サーバー1: ChannelInterceptor】（STOMP CONNECT 時に検証済み）
ユーザーAのアイデンティティを確認

【サーバー1: MessageWebSocketController】
受け取り、MessageService.sendChannelMessage() を呼ぶ

【サーバー1: MessageService】
1. DB に保存（永続化）
2. Redis の "messages:channel:1" に WsEvent を publish
↓

【Redis】
"messages:channel:1" チャンネルに放送
↓

【サーバー1: MessageChannelRedisSubscriber】（受信）
SimpMessagingTemplate で /topic/channels/1 に転送
→ サーバー1に接続中のユーザー全員に届く

【サーバー2: MessageChannelRedisSubscriber】（受信）
SimpMessagingTemplate で /topic/channels/1 に転送
→ サーバー2に接続中のユーザー全員に届く

【クライアント全員】
SUBSCRIBE /topic/channels/1 していた全員の画面に
MESSAGE_CREATED イベントが届き、メッセージが表示される
```

### なぜ MessageService から SimpMessagingTemplate を直接呼ばないのか

これが今回の設計で最も重要な判断の一つです。

「Redis 経由でなく、サービス層から直接ブロードキャストすれば早いのでは？」と思うかもしれません。

しかし直接呼んだ場合、**自分のサーバーに接続しているユーザーにしか届きません**。別サーバーのユーザーは取りこぼされます。

Redis 経由を強制することで、どのサーバーもすべてのユーザーに届けられる一貫性を保てます。

## Step 10: WsEvent の設計

WebSocket でクライアントに送るデータの形（イベント形式）を設計しました。

### なぜ「イベント型 + ペイロード」の形にするのか

WebSocket の `/topic/channels/1` に届くメッセージは複数の種類があります：

- 新しいメッセージが投稿された
- 既存のメッセージが編集された
- メッセージが削除された

クライアント（フロントエンド）は受け取ったとき「何が起きたのか」を判断して適切に画面を更新します。

**イベント駆動の設計原則**：「何が起きたか（type）」と「その内容（payload）」をセットで送ることで、クライアントは switch 文で処理を分岐できます。

```
{
  "type": "MESSAGE_CREATED",
  "payload": { "id": 42, "body": "こんにちは", ... }
}

{
  "type": "MESSAGE_DELETED",
  "payload": { "id": 42, ... }  ← id を使って画面から削除
}
```

### 削除時も全フィールドを送る理由

削除イベントは「id だけ送れば十分」とも言えます。しかし今回は削除時も `MessageResponse` の全フィールドを送っています。

理由は**クライアントの処理を統一するため**です。いずれのイベントも同じ形で受け取れるため、フロントエンドの型定義が1種類で済みます。

## Step 11: REST と WebSocket の役割分担

今回、REST と WebSocket を両方使っています。それぞれの役割を明確にします。

### REST が担う部分

| エンドポイント | 用途 |
|---|---|
| GET /api/channels/{id}/messages | **過去ログの取得**（チャンネルを開いたとき） |
| PATCH /api/messages/{id} | **編集**（WebSocket でもブロードキャスト） |
| DELETE /api/messages/{id} | **削除**（WebSocket でもブロードキャスト） |

### WebSocket が担う部分

| 宛先 | 用途 |
|---|---|
| /app/channels/{id}/messages へ SEND | **新規投稿**（リアルタイム送信） |
| /topic/channels/{id} を SUBSCRIBE | **受信**（新着・編集・削除を受け取る） |

### なぜ新規投稿だけ WebSocket なのか

**即時性が必要**だからです。送信ボタンを押してから「自分の画面に表示される」まで、REST 経由では往復のHTTPレイテンシが発生します。WebSocket は既に接続が確立されているため、即座に送信できます。

また、WebSocket で受け取ったイベントが「自分の投稿確認」も兼ねます。投稿者も `/topic/channels/1` を購読していれば、Redis 経由でブロードキャストされた自分のメッセージが届きます。

## Step 12: cursor ベースページングの設計（メッセージ版）

F-03/F-04 でも使ったカーソルページングですが、メッセージでは「最新から過去へ遡る」方向での使い方が特徴的です。

### チャンネルを開いたときの表示順

チャットアプリは「最新メッセージが下に表示される」UIが一般的です。チャンネルを開いたとき、まず最新の N 件を読み込みます。

### 過去のメッセージを「無限スクロール」で追加読み込み

上にスクロールして過去に遡るとき、**「今表示している中で最も古いメッセージ（ID が小さいもの）」を cursor として使います**。

```
初回: cursor なし → 最新50件（ID 100〜51 など）を降順で返す
2回目: cursor=51 → ID < 51 の最新50件（ID 50〜1 など）を返す
```

### 「ID < cursor」という条件の意味

メッセージ ID は自動連番（大きいほど新しい）です。「cursor より小さい ID = cursor よりも先に投稿されたメッセージ = 古いメッセージ」です。

この方向での cursor ページングは「チャットの歴史を掘り起こす」操作に自然にマッピングされます。

## Step 13: 今回の主要設計判断まとめ

### 判断① Simple Broker を選んだ

**状況**: リアルタイムブロードキャストの基盤をどう作るか  
**選択**: Spring の Simple Broker（インメモリ）  
**理由**: Redis は STOMP 非対応のため Broker Relay に使えない。RabbitMQ の追加は過剰。  
**トレードオフ**: Redis Pub-Sub を別途追加する必要がある

---

### 判断② Redis Pub-Sub を「Simple Broker の補完」として使う

**状況**: スケールアウト時にサーバー間でメッセージが届かない問題  
**選択**: Redis を共有メッセージバスとして使い、各インスタンスが受信して自前でブロードキャスト  
**理由**: D-2 要件「複数インスタンス対応」を Simple Broker のシンプルさを保ちながら達成  
**トレードオフ**: メッセージが Redis を経由するぶん、理論上わずかな遅延が加わる

---

### 判断③ MessageService は SimpMessagingTemplate を直接呼ばない

**状況**: DB 保存後にどうブロードキャストするか  
**選択**: 常に Redis 経由  
**理由**: 直接呼ぶとシングルインスタンス専用コードになる。Redis 経由を強制することでマルチインスタンスの一貫性を保証する  
**トレードオフ**: 処理が一歩増える（Redis への publish → Redis からの受信 → ブロードキャスト）

---

### 判断④ Redis publish の失敗をログのみにした

**状況**: Redis への publish が失敗したとき  
**選択**: 例外をスローせず、エラーログを出力して続行  
**理由**: メッセージは既に DB に保存済み。WS ブロードキャストの失敗は「画面への即時通知が届かない」だけで、データ損失ではない。次の GET リクエストで取得できる  
**トレードオフ**: ブロードキャストが静かに失敗する可能性がある。監視・アラートの設定が重要になる

---

### 判断⑤ JOIN FETCH m.author で N+1 を回避

**状況**: メッセージ一覧で各メッセージの投稿者名を返す必要がある  
**選択**: JPQL で `JOIN FETCH m.author` を指定  
**理由**: `author` 関係は LAZY（必要なときだけ読む）設定。明示的に一緒に読まないと、50件のメッセージを返すとき50回の追加クエリが走る  
**判断軸**: 「取得後に別のエンティティへのアクセスが確実に発生するなら、最初から JOIN FETCH で取ってくる」

---

### 判断⑥ 編集・削除の権限設計

**状況**: 誰が編集・削除できるか  
**選択**: 編集は author のみ。削除は author または ws OWNER  
**理由**: Slack の動作に準拠。OWNER はワークスペースのモデレーター役として、チャンネル未参加でもメッセージを削除できるべき  
**トレードオフ**: 削除時にチャンネルメンバーシップチェックを省略するため、OWNER が参加していないチャンネルのメッセージも削除できる。これは意図的な設計

## 付録: 用語集

| 用語 | 噛み砕き |
|------|----------|
| WebSocket | 一度接続したら双方向に通信し続けられるプロトコル |
| STOMP | WebSocket 上で動く「メッセージの形式と操作を決めたルール」 |
| SockJS | WebSocket が使えない環境での代替手段を自動選択するライブラリ |
| Pub-Sub | 「放送局と受信機」のモデル。Publisher が送ったメッセージを複数の Subscriber が受け取る |
| Simple Broker | Spring 内蔵のインメモリメッセージ配送機能 |
| Broker Relay | 外部のメッセージサーバー（RabbitMQ 等）にブローカー機能を委託する方式 |
| ChannelInterceptor | STOMP フレームの前処理を割り込ませる仕組み。認証や検証に使う |
| PatternTopic | ワイルドカード（*）で複数チャンネルをまとめて購読する Redis の機能 |
| N+1 問題 | 1つのリクエストのために N 件のデータを取得するとき、各行ごとに追加クエリが走ってしまう問題 |
| JOIN FETCH | JPA で関連エンティティを「最初から一緒に」読み込む指定（N+1 回避） |
| WsEvent | WebSocket で送るイベントデータの形式。type（何が起きたか） + payload（内容）で構成 |
| LAZY ロード | 関連データを「必要になったときに初めて読み込む」JPA のデフォルト動作 |
