# RaiseChat 学習ノート — 最終版（引き出し再構成）

このノートは、RaiseChat の MVP 開発（設計フェーズ D-1〜D-4 ＋ バックエンド実装 F-01〜F-15 ＋ 基盤構築）を通して積み上げた**学習ノート 15 本を、1 本に統合・再構成したもの**です。

これまでは「タスクごと」にノートを分けていたため、同じ概念（RFC 7807・cursor ページング・WebSocket・Controller 境界 …）が複数ファイルに散らばっていました。本ノートは**テーマ別に重複を排除**し、各機能で得た「**引き出し**（＝再利用できる設計判断のパターン）」を体系化しています。

## このノートの読み方

- **目的**: 「あの判断、なぜそうしたんだっけ?」を後から 1 か所で引けるようにする
- **方針**: コードの記法（syntax）ではなく、**設計判断とその根拠**を残す。概念は日常語と例え話で説明する
- **到達ゴール**: 各引き出しを自分の言葉で言え、**「次に同じ状況が来たら AI にどう指示するか」**まで言える状態
- **使い方**: 新機能を AI に任せる前に「これは第◯章のどの引き出しが効くか?」と自問する。指示に詰まったら [付録 A の指示テンプレ集](#付録-a-ai-への指示テンプレ集横断) を引く

### 通底するメンタルモデル（全体を貫く 2 本柱）

1. **AI 前提のスタンス** — 目指すのは「A: 部品の名前と役割が言える / B: 動作やエラーから原因を推測できる / C: コードが何をしているか分かる / **D: AI に具体的に指示できる**」まで。「E: 1 から手書きできる」は副産物でよい。**判断できることが本体、実装は AI に任せる**。
2. **割り切りの精神（YAGNI / MVP）** — 「将来必要かも」で先回り実装しない。今のサイズに合った最小設計を保ち、必要になってから足す。**やらないことを意図的に決める**のも設計。

## 第 0 章 設計哲学 — すべての判断の土台

機能ごとの引き出しの前に、**全機能に通底した姿勢**をまとめる。ここがブレなければ、個別の判断は自然に決まる。

### 0-1. YAGNI — 必要になるまで作らない

> **YAGNI** = You Aren't Gonna Need It（それ、必要にならないよ）

「将来こうなるかも」で先回り実装すると、実際は使われずに残る／仕様が固まって書き直しになる。**先回り実装は技術的負債を生む**。

| 場面 | YAGNI の適用 |
| --- | --- |
| API バージョニング（`/api/v1`） | **並走させる相手（古いクライアント）がいない**ので導入しない。破壊的変更が出たら後から `/api/v2` を新設すればよい |
| Repository の検索メソッド | UNIQUE INDEX があるキーの一意検索だけ書く。「使うかも」は書かない（第 3 章 3-8） |
| 機能スコープ | 設計書に複合的な振る舞いが書いてあっても、**実装は段階的に切り出す**（0-3） |

### 0-2. 割り切りと「完璧主義をどこで捨てるか」（引き出し: F-15）

防ぐコストと被害を**天秤にかける**。実害が小さく高負荷も来ないなら、シンプルな実装で割り切ってよい。ただし**逃げ道を残す**（理由と将来の厳密化手段をコメント／未決事項に記録）。

- 例: 招待リンクの使用回数を厳密に同時実行制御しない → 多少の超過は実害が小さい。お金・在庫・一意性が絡むなら厳密に防ぐ
- 例えると「最後の 1 個のセール品」: 厳密な在庫管理は重いが、無料招待枠の数本超過は誰も困らない

**判断軸**: お金・在庫・一意性が絡む → 厳密に。それ以外で実害が小さい → 割り切って逃げ道を記録。

### 0-3. スコープを絞る／中間状態をあえて残す（引き出し: F-02 / F-03）

設計書は**最終形**を描くもの。**実装フェーズではスコープを切り出して段階的に進めてよい**。設計書は自分が書いたもの、スコープも自分が決めてよい。

- F-03: `general` チャンネル自動作成を F-04 に回した（channels テーブルへの低レベル INSERT を F-03 に混ぜない）
- F-02: 旧 `AuthExceptionHandler`（Map 形式）に手を入れず、新 advice を `basePackages` でスコープ限定 → **「auth は旧形式、user は ProblemDetail」の混在状態をあえて一時的に残す**

> **「あえて中間状態を残す」**スコープ判断は、PR 単位の学習効率と将来のリファクタしやすさを両立する。1 タスク 1 スコープが学習効率に直結する。

- 依存が深い機能（外部システム連携：S3 / SES など）は **PR を分ける**

### 0-4. DRY と「結合を避ける」のせめぎ合い（引き出し: F-15）

「同じ処理があるから使い回す」は常に正解ではない。**別ドメインの処理に安易に依存しない**。小さく変わりにくいなら**コピーして独立**させるほうが、結合が増えないぶん変更しやすい。

- 例えると「隣の部署の判子を借りる」: 一度借りると、相手の都合に振り回される
- 第三の道: 共通化したいなら**中立な場所**（共通モジュール）に置く
- 重複のコストと結合のコストを天秤にかけ、**必要になってから共通化する**

### 0-5. 「分ける」も「まとめる」も目的は変更しやすさ

- F-15「再利用と結合の天秤」= 安易に依存させない（**分ける**）
- F-08「新機能は既存を揃える好機」= 散らばった分岐を 1 か所に集約する（**まとめる**）

一見逆だが、**どちらも目的は「変更しやすさ」を上げること**。状況でどちらに倒すかが設計判断。

## 第 1 章 通信の設計 — REST と WebSocket

RaiseChat の通信は **「普通の取得・更新は REST、リアルタイム配信は WebSocket」** のハイブリッド。この章はその全体像と引き出し。

### 1-1. なぜ 2 経路あるのか — HTTP の限界

- **HTTP/REST** = 「お願い 1 回 → 返事 1 回」で完結。**サーバーから話しかけられない**（手紙）
- チャットは「他人が投稿したら、自分が何もしなくても画面に出る」体験 → HTTP だけだとポーリング（「新着ある?」を繰り返す）になり、無駄・遅い
- **WebSocket** = 繋ぎっぱなしの双方向通信路。サーバーから能動的にプッシュできる（電話）

| | REST（HTTP） | WebSocket |
| --- | --- | --- |
| 通信モデル | 1 往復で完結 | 接続後はどちらからでも送れる |
| 得意 | 取得・更新の結果を確実に返す | リアルタイム配信 |
| 不得意 | リアルタイム配信 | 結果応答が要る単発操作には大げさ |

### 1-2. 引き出し: 送信は WebSocket 一本、編集・削除は REST + WebSocket 配信

検討した 3 案のうち、**操作の「入口」と配信の「出口」を意識的に分けた**案 Z を採用。

| 操作 | 経路 | 理由 |
| --- | --- | --- |
| **新規メッセージ送信** | **WebSocket のみ** | 主目的が「リアルタイム配信」。配信路と一体化し、経路の二重化を防ぐ |
| メッセージ履歴取得 | REST | ページング・キャッシュと相性が良い |
| メッセージ編集・削除 | REST + WebSocket 配信 | 主目的が「操作結果を確実に伝える」。`200/403/404` で結果が明確 |
| ログイン・プロフィール更新 | REST | リアルタイム性不要 |

**なぜ送信を 2 経路（REST と WS 両方）にしないか** — 入口が 2 つだと、サーバーに送信処理を 2 系統持つことになり、**重複表示・順序逆転・コードの二重化**を招く。Redis Pub-Sub（後述）が絡むほどリスクが膨らむ。

> 設計原則: **同じ操作の入口を 2 経路で提供しない。**

### 1-3. WebSocket の上に乗る部品たち（STOMP / destination / broker）

WebSocket は**通信路（パイプ）だけ**を提供し、中身の形式は決めない。そこで上に **STOMP**（メッセージのお作法）を被せる。

- **STOMP** = 「コマンド + ヘッダ + 本文」のフレーム形式。HTTP リクエストに似ている（`CONNECT` / `SEND` / `SUBSCRIBE` / `MESSAGE`）
- **destination** = 「これを購読します」「ここに送ります」とサーバーに伝える**文字列ラベル**。URL でもファイルパスでもない（実体はない、ただの仕分け用ラベル）
- **broker** = 「destination → 購読中 session の名簿」を持ち、頼まれたら名簿を引いて配る**中央郵便局**。この配信モデルが **Pub-Sub**

#### 詰まりやすい点トップ 3

1. **destination は URL ではない** — 実体のない、チームで決めた命名規則のラベル
2. **`/app/` と `/topic/` は方向が逆**
   - クライアント → サーバー（投げる）= **`/app/...`** → **Java ハンドラ行き**（`@MessageMapping`。DB 保存・認可チェックを挟める「一般道」）
   - サーバー → クライアント（配信）= **`/topic/...`** → **broker 直行**（検証ゼロでブロードキャストする「高速道路」）
   - **検証が要る操作は必ず `/app/`（一般道）を通す**。`/topic/` に直接 SEND させると認可なしで投稿できてしまう
3. **simple broker は自プロセス内の名簿しか見えない**（→ 1-4）

### 1-4. 引き出し: マルチインスタンスは Redis Pub-Sub で橋渡し

本番はサーバーを複数台動かす（負荷分散・冗長化）。ロードバランサーが接続をランダムに振り分けるため、**同じチャンネルを見ている人が別インスタンスに繋がる**ことが起きる。

- **問題**: あなたが #1 に、Alice が #2 に繋がっていると、#1 の simple broker の名簿に Alice がいない → Alice に届かない
- **解決**: インスタンス間に**伝言役（Redis Pub-Sub）**を置く。#1 が処理したら ① 自分の broker に配信 ② Redis に `PUBLISH` → 全インスタンスが `SUBSCRIBE` で受け取り、各自の名簿に配信

| 部品 | 役割 |
| --- | --- |
| simple broker | **インスタンス内**の配信 |
| Redis Pub-Sub | **インスタンス間**の橋渡し |

**設計判断（F-05）**: `MessageService` は `SimpMessagingTemplate` を直接呼ばず、**常に Redis 経由**で配信する。直接呼ぶとシングルインスタンス専用コードになるため、Redis 経由を強制してマルチインスタンスの一貫性を保証する。

**設計判断（F-05）**: Redis への publish 失敗は**例外を投げずログのみ**。メッセージは既に DB 保存済みで、配信失敗は「即時通知が届かない」だけ（次の GET で取得できる）。データ損失ではないので握りつぶす。ただし監視・アラートは要る。

> simple broker を選んだ理由: Redis は STOMP 非対応のため broker 本体にはできず、RabbitMQ 追加は過剰。**既に Redis を立てるので、Pub-Sub を補完に使う**のがバランス点。

### 1-5. 引き出し: WebSocket 認証は STOMP CONNECT フレームに JWT を載せる

REST は `Authorization: Bearer <JWT>` ヘッダで認証する。だが**ブラウザの `new WebSocket()` はカスタムヘッダを付けられない仕様**。

| 案 | 評価 |
| --- | --- |
| URL クエリ `?token=` | トークンがアクセスログ・履歴に残る → ❌ |
| Cookie | CSRF 対策が要る・既存 REST が Bearer なので二重管理 → △ |
| **STOMP CONNECT フレームのヘッダ** | クリーン・**REST と同じ JWT・同じ検証ロジックを流用できる** → ✅ |

サーバー側は `ChannelInterceptor`（入口の警備員）が CONNECT フレームのヘッダから JWT を取り出し、REST と共通の `JwtTokenProvider` で検証する。`/ws/**` 自体は HTTP セキュリティで許可しておき（ハンドシェイクは認証なしで通す）、**認証は CONNECT フレームで行う**。

### 1-6. 引き出し: 1 destination に複数種類が流れる → 共通エンベロープで `type` 分岐

REST は「1 URL = 1 操作」だが、WebSocket は **1 つの destination（例: `/topic/channels/5`）に新規・編集・削除・リアクション・タイピングが全部流れる**。クライアントは本文を見ないと種類が分からない。

→ 全イベントを**同じ封筒**に入れ、表に種類を書く：

```json
{ "type": "message.created", "serverTime": "...", "payload": { /* 種類ごとに違う */ } }
```

- 種別は `<リソース>.<動詞>` で統一（`message.created` / `message.updated` / `reaction.added` / `typing.started` / `presence.changed` …）
- クライアントは `type` を見るだけで UI を分岐できる
- 削除イベントも全フィールドを送る（クライアントが何を消すか特定できるように）

### 1-7. 引き出し: Pub-Sub チャネルは粒度を決め、専用 prefix を切る

「どの単位で Redis チャネルを切るか」は粒度の設計：

| 粒度 | 例 | 評価 |
| --- | --- | --- |
| 全部 1 本 | `ws:all` | 雑。関係ないインスタンスにも届く |
| **ワークスペース単位** | `ws:workspace:1` | **MVP のバランス点（採用）** |
| destination 単位 | `ws:topic:channels:5` | 無駄ないがチャネル数が爆発 |

**設計判断（F-06）**: 新しいリアルタイム配信（DM など）を足すときは、**既存トピックへ相乗りせず専用 prefix を切る**（例 `messages:dm:`）。名前は用途と一致させ、Subscriber は責務ごとにクラスを分ける。

## 第 2 章 データの取り方 — API 設計の引き出し

REST API を「どう設計するか」で繰り返し使った引き出し。

### 2-1. 引き出し: 一覧は cursor ベースページング

大量データは小分けに取る。方式は 2 つ：

| | offset / limit（古典） | cursor（採用） |
| --- | --- | --- |
| 指定 | 「○件目から○件」 | 「しおりからの続き」 |
| データ増減への耐性 | ❌ ズレる（途中で追加されると重複・抜け） | ✅ 影響を受けない |

- **実装テクニック**: `limit + 1` 件取得し、余分が取れたら `hasMore = true`、最後の要素を `nextCursor` にする
- **ソートキーと目印を揃える**: id 昇順なら cursor も id。時系列降順が要るなら複合 cursor（created_at + id）
- レスポンスは `{ items, nextCursor, hasMore }`。`nextCursor` は不透明文字列（base64）で、クライアントは中身を解釈せずそのまま返す
- チャットの「過去に遡る」は `id < cursor` で降順になる

### 2-2. 引き出し: 部分更新（PATCH 的セマンティクス）

更新 API には「全フィールド必須（PUT 的）」と「送ったフィールドだけ更新（PATCH 的）」がある。プロフィール・設定など**細かく編集される系**は部分更新が向く（`displayName` だけ・`statusMessage` だけ送れる）。チャンネル設定・ユーザー設定でも再利用。

### 2-3. 引き出し: 「既存なら返す、なければ作る」は POST 1 本＋200/201（引き出し: F-06）

DM を開く操作は「相手との部屋が既にあれば再利用、なければ作る」。素直な REST だと「探す GET」と「作る POST」に割れて、クライアントが分岐を持つ。これを **1 つの POST** で表現：

- 既存があれば **200 OK**（既存の部屋を返す）
- 新規作成したら **201 Created**
- **409 Conflict は使わない** — 「既にある」は失敗ではなく正常な結果

これは「**普通の操作をエラーにしない**」という態度。冪等性（2-4）と同じ思想。

### 2-4. 引き出し: 冪等性 — 何度押しても同じ結果（引き出し: F-15）

**冪等** = 同じ操作を何度実行しても結果が同じ。ネットワーク再送・ダブルクリックで壊れないために重要。

- 招待受諾を冪等に: **既にメンバーなら、エラーにせず黙って成功**を返す
- 「使用回数」のようなカウンタは、**状態が実際に変わったときだけ**更新する（二重カウント防止）
- 無効化（revoke）も冪等に（既に無効でも成功）
- ここでも **409 にしない** — 既に目的の状態なのは正常

### 2-5. 引き出し: エラーは「形式」と「意味」の両方を設計する

#### 形式: RFC 7807 ProblemDetail（引き出し: D-1 / F-02）

エラー JSON の形は HTTP も JSON も決めていない → 各社バラバラ（`{error}` / `{errorCode}` / `{status,reason}` …）→ クライアントが毎回違う読み取りを書くハメに。

**RFC 7807 ProblemDetail** は業界標準の共通フォーマット。`type` / `title` / `status` / `detail` / `instance` ＋ 拡張 `errors`（フィールド単位）。`Content-Type: application/problem+json` で形式を宣言する。Spring Boot 3 が標準対応するので自前実装より楽。**ステータスコード（機械が分岐）と Content-Type（形式宣言）の両方が要る**。

#### 意味: ステータスコードは「結果の意味」で選ぶ（引き出し: F-15）

| コード | 意味 |
| --- | --- |
| **404 Not Found** | 最初から存在しない |
| **410 Gone** | 存在したが利用不可になった（期限切れ・無効化） |
| **422 Unprocessable** | ボディの値が不正 |
| **403 Forbidden** | 権限がない |

- 「無い」にも種類がある（404 と 410 を区別）
- **403 を「非メンバー」と「非オーナー」の両方に寄せる** — 「メンバーではある」という所属情報を漏らさないため、あえて同じ番号にする（情報漏洩を避ける意図的設計）

## 第 3 章 永続化とデータモデル — DB × JPA

データの「持ち方」と「JPA での扱い」の引き出し。

### 3-1. 引き出し: DB が守れるルールはアプリで書かない（引き出し: B-2）

| ルールの種類 | どこで守る |
| --- | --- |
| **データ整合性**（NOT NULL / UNIQUE / FK / CHECK / XOR） | **DB 制約** |
| **ビジネスロジック**（レート制限・禁止語フィルタ） | アプリ層（Service / Validator） |
| ユーザー入力の即時フィードバック | フロント＋アプリ層（DB は最終防衛線） |

DB の CHECK 制約は JPA 経由でも psql 直 INSERT でも**必ず効く**。アプリで二重に書くと「JPA 経由のときだけ守られるルール」になり整合性がズレる。Entity は素のマッピングに集中させる。

- 例: `messages` の「channel か dm のどちらか片方」XOR は CHECK 制約に任せ、Java では例外を書かない
- ENUM も VARCHAR + CHECK で表現（PostgreSQL ENUM 型は使わない）

### 3-2. 引き出し: DB 制約をサービス層で吸収して正規化（引き出し: F-06）

DB 側で順序や一意性を強制する場合（例: `dm_rooms` は `user_a < user_b` で「2 人組を 1 行に」）、**クライアントに制約を意識させない**。サービス層に入った直後に**正規化**（小さい ID を user_a に揃える）し、Repository には正規化済みの値だけ渡す。

- 例えると「双子の片方を常に左に立たせる」: 順序を固定すれば「同じペア」を 1 通りに表せる
- 無向グラフ系のデータ（フォロー・マッチング）全般で再利用できる

### 3-3. 引き出し: トランザクション境界と JPA dirty checking（引き出し: F-02）

「保存処理を書いていない」のに DB が更新される — これは JPA の **dirty checking**。`@Transactional` の境界内で取得したエンティティのフィールドを変えると、コミット時に変更が自動で SQL 化される。

- `@Transactional` を**どこに置くか＝トランザクション境界の設計**。「失敗したら全部巻き戻したい範囲」を意識して引く
- ほぼ全ての書き込み Service メソッドで効く

### 3-4. 引き出し: DB トリガー設定カラムは `entityManager.refresh()` で読み戻す（引き出し: F-03）

`created_at` のように**DB トリガー / DEFAULT が値を埋めるカラム**は、INSERT 直後の Java オブジェクトでは `null`（DB が埋めた値を Java は知らない）。レスポンスに含めたいなら：

- `entityManager.refresh(entity)` で DB から読み戻す、または `@Generated(GenerationTime.INSERT)`
- **テストで初めて気づきやすい**設計ポイント（INSERT 直後の auto-set 値を返す API 全般で要注意）

### 3-5. 引き出し: リストに関連データを含めるなら JOIN FETCH で N+1 回避（引き出し: F-03 / F-05）

`author` などの関連は LAZY（必要なときだけ読む）が既定。一覧で各行の関連を使うと、50 件返すのに 50 回の追加クエリが走る（**N+1 問題**）。JPQL で `JOIN FETCH m.author` を指定し一括取得する。

> 判断軸: **取得後に別エンティティへのアクセスが確実に発生するなら、最初から JOIN FETCH で取る。** 関連を返さないなら JOIN FETCH は不要。

### 3-6. 引き出し: 論理削除と再参加対応（引き出し: F-04）

「履歴を残したい」＋「(親 ID, ユーザー ID) のユニーク制約」がぶつかるとき、**物理削除ではなく論理削除**（`deleted_at` / 退出日時に印を付ける）で両立させる。

- 退出 = 日時を書き込む / 再参加 = 日時を NULL に戻す
- 一覧取得は「現在アクティブな関係のみ」で絞る
- **副産物**: 親を論理削除すれば子は自動的にフィルタされ、「ついでに子も消す」処理が要らなくなる
- 「○○を消したら ●● も」が出てきたら、まず**「本当に消す必要があるか?（論理削除や CASCADE で済まないか）」を疑う**

### 3-7. 引き出し: 木構造は階層を固定する／絞り込みで見せ分ける（引き出し: F-08）

スレッド（返信）は親子＝木になりうる。深い木は表示も取得も破綻する。

- **木構造を 1 階層に固定**: 返信は常に根にぶら下げ、返信への返信は**根に付け替える**（エラーにせず吸収）
- **絞り込みで見せ分ける**: 返信も通常メッセージも**同じテーブル**に入れ、「親を持たない＝本流一覧」「親が X＝そのスレッド」とフィルタで分ける。**返信専用テーブルを安易に作らない**
- 入れ子になりうるデータ（コメント・リプライ・サブタスク）全般で再利用

### 3-8. 引き出し: パッケージ分割と Repository は最小限から（引き出し: B-2）

- **パッケージ分割の軸**: 「そのテーブルは単独で存在できるか?」。主役（独立して意味を持つ → 専用フォルダ）／脇役（必ず親にぶら下がる → 親と同居）。主役単位で切ると、将来サービス分離するときの単位になる
- **Repository は YAGNI**: `JpaRepository` 継承だけで CRUD は使える。検索メソッドは **UNIQUE INDEX があるキーの一意検索**（仕様確定済み）だけ書く。集計系など仕様が固まらないものは API 実装時に書く

## 第 4 章 認証・認可・秘密情報

### 4-1. 引き出し: JWT 2 トークン構成 + DB レス認証 + 回転（引き出し: F-01）

- **JWT** = ヘッダ.ペイロード.署名 を `.` で繋いだ文字列。ペイロードは**暗号化ではなく Base64**（誰でも読める）。守っているのは**改ざん**（署名）であって秘匿ではない → **機密情報を入れない**
- **DB レス認証**: 署名検証 + ペイロードの `sub` を読むだけで「誰か」が分かる（DB アクセス 0 回 → 速い・スケールしやすい）。代償は「発行済み JWT を無効化できない」 → access は短命（15 分）にして漏洩時の被害時間を限定
- **2 トークン**: access（短命・毎回送る）/ refresh（長命・更新時のみ）。漏れリスクと UX を両立（リストバンドとチケット控えの関係）
- **回転（rotation）**: refresh を使うたびに旧を revoke + 新を発行。漏洩しても正規ユーザーか攻撃者の**片方が必ず詰まる**ので、**漏洩の検知**になる

| 仕組み | 守るもの |
| --- | --- |
| JWT 署名（HS256） | リクエストの改ざん |
| JWT 短命（15 分） | 漏洩時の被害時間 |
| refresh を hash 保存 | DB 漏洩時のなりすまし |
| refresh 回転 | refresh 漏洩の検知 |
| bcrypt(password) | DB 漏洩時のパスワード復元 |
| login 失敗メッセージ統一 | 「この userId は存在する」の漏洩 |

ハマり所: Filter 内で例外を投げない（通過させて先で 401 にさせる）／ Spring Security を入れたら `permitAll` を先に列挙してから `anyRequest().authenticated()`。

### 4-2. 引き出し: 秘密はハッシュで保存、平文は発行時の一度だけ（引き出し: F-15）

招待トークン・refresh トークンなど秘密情報は、**DB にハッシュ（SHA-256）で保存**し、平文は発行時に一度だけ返す。照合は受け取った平文を同じ方法でハッシュ化して比較。

- DB が漏れても**ハッシュから平文は復元できない** → なりすまし不可。password を bcrypt 保存するのと同じ思想（**サーバーが知らなくていい情報は持たない**）
- ランダムな高エントロピートークンは辞書攻撃の心配がないので、bcrypt でなく高速な SHA-256 で十分（パスワードは bcrypt）

### 4-3. 引き出し: 権限は親リソースから継承する（引き出し: F-08）

子リソース（スレッド返信・添付・いいね）の閲覧権限は、**親（チャンネル / DM）の権限をそのまま継承**する。専用の権限ルールを作らず、既存の親の判定を呼ぶ。

- 例えると「会議室の鍵」: 会議室に入れる人は、その中のホワイトボードも見られる
- **権限の二重定義を避ける**ことで、ルール変更が 1 か所で済む。F-04/F-06 で作った「メンバー判定」を再利用する形

### 4-4. 引き出し: 可視性チェックは「単位」で置き場所を決める（引き出し: F-04）

「PRIVATE は招待された人だけ見える」をどう守るか：

| 操作の種類 | 置き場所 | 理由 |
| --- | --- | --- |
| **リスト系**（一覧） | **Repository のクエリで絞る** | 「見える行だけ SELECT」が自然・効率的 |
| **単一取得系**（1 個） | **Service の権限チェック** | 取ってから「見ていいか」を判定 |

最初に**可視性の単位**（行ごと / 親リソース単位 / ユーザー権限単位）を見極める。`@PreAuthorize`（SpEL）より**素直な Java の if（Service 層手動チェック）**を優先（学習コストが低くテストしやすい。F-02 と一貫）。

## 第 5 章 コードの構造判断 — どこに何を書くか

「正しく動く」の先の「どこに書くと変更しやすいか」の引き出し。

### 5-1. 引き出し: Controller の境界はリソース（Entity）単位で引く（引き出し: F-04 / F-06）

**URL の階層と Controller の境界は別物**。URL が同じ前半でも、扱うリソースが違えば Controller を分ける。逆に 2 系統の URL でも同じリソースなら 1 Controller。

- 同じリソース → 2 系統 URL でも **1 Controller**（F-04: チャンネル操作を集約）
- 別リソース → 同じ URL 前半でも **別 Controller**（F-06: DM ルームと DM メッセージ）
- 例えると「役所の窓口」: 窓口は建物の階数ではなく**手続きの種類**で分ける

### 5-2. 引き出し: 副作用処理は「3 軸」で直書きか呼び出しか決める（引き出し: F-04）

「機能 A をするとき必ず B もする」（例: ワークスペース作成時に `general` 自動作成）を、A の中に直書きするか、別 Service を呼ぶか：

| 軸 | 直書き寄り | 呼び出し寄り |
| --- | --- | --- |
| **トランザクション** | 失敗したら一緒に巻き戻したい | 別でよい |
| **事前チェック** | 別 Service の事前チェックが A の途中状態と噛み合わない | 噛み合う |
| **独立性** | A 以外から呼ばれない | 他の場所からも呼ばれる |

- 例: `general` 自動作成 → トランザクションを揃えたい・途中状態と噛み合わない → **直書き**
- 例: 最終アクセス日時更新 → ログイン・画面遷移など他でも呼ばれる → **独立 Service で呼び出し**
- まず「その副作用は本当に必要か?（論理削除や CASCADE で消えないか）」を疑う

### 5-3. 引き出し: 既存パターンを伸ばす／新機能は既存を揃える好機（引き出し: F-06 / F-08）

- **既存パターンを伸ばす（F-06）**: 新機能は似た既存機能の**コピー＋差分**で作る。同じ形を崩さない。DM は「メッセージ（F-05）をそのまま伸ばす」設計だった。AI への指示が「**F-XX と同じパターンで、差分は◯◯**」の 2 行で済むようになる ＝ これが「AI を前提に作る」スタンスの中核
- **既存を揃える好機（F-08）**: 新機能を足すとき、散らばった同種の分岐を **1 か所に集約**する好機。集約後は**既存テストを流して動作不変を確認**。整理は今いじる範囲に留める

## 第 6 章 キャッシュ戦略 — Redis の使い分け

DB（PostgreSQL）が**ソース・オブ・トゥルース**、Redis は**派生キャッシュ**（消えても DB から作り直せる、メモリ上で約 1000 倍速い key-value）。この前提が全判断の土台。

### 6-1. 3 つの戦略の使い分け（中心の引き出し）

| 対象 | 戦略 | TTL | 書き込み時の操作 |
| --- | --- | --- | --- |
| ユーザー情報・メンバー一覧・チャンネル一覧 | **cache-aside** | 1h | **DELETE** |
| 直近メッセージ ID リスト | cache-aside | 24h | DELETE（編集削除）/ 追記（送信） |
| 未読数 | **カウンタ直接運用** | なし | INCR / DECR / SET 0 |
| プレゼンス | **TTL 任せ** | 90s | SET（ハートビートで上書き） |
| JWT ブラックリスト | TTL 任せ | トークン残存時間 | SET |
| レート制限 | TTL 任せ | 60s | INCR |

### 6-2. 引き出し: cache-aside と「無効化は DELETE」

**cache-aside** = アプリが自分で書く「まず Redis → なければ DB → DB の結果を Redis に入れる」パターン（hit / miss）。Redis が落ちても try-catch で握れば DB 直行できる。

**無効化（古くなったら消す）は SET 上書きでなく DELETE**。理由: ほぼ同時の更新があると SET は到着順で古い値に上書きされ DB と不整合になりうる。DELETE なら「次に読む人に DB から取り直させる」ので競合しない。

### 6-3. 引き出し: カウンタ系（未読数）は cache-aside の例外

未読数を毎回 DB で COUNT すると重い（チャンネル 50 個 × サイドバー開くたび）。Redis の `INCR/DECR` で直接運用し、Redis を正本に近い形で持つ。Redis が飛んだら DB の「最終既読位置」から 1 回 COUNT して再構築できる。

### 6-4. 引き出し: TTL は無効化の安全網

TTL = Redis が時計を見て勝手に消す期限。**DELETE を書き忘れても期限で消える保険**。整合性が緩いものほど長い TTL、揮発性のものほど短い TTL。プレゼンスは「30 秒ごとに生存を送り、90 秒 TTL で上書き」＝**ハートビート式**（来なくなったら自動失効＝offline）。

### 6-5. 引き出し: キャッシュと Pub-Sub は同じ Redis を prefix で共有

キャッシュも Pub-Sub も同じ 1 つの Redis を使う。**別インスタンスや論理 DB index で分けず、key の頭の prefix（`cache:` / `unread:` / `presence:` / `jwt:` / `rate:` / `ws:`）で区別**する。

- 別 Redis を立てる案 → 運用コスト 2 倍で却下
- 論理 DB index 案 → 接続を 2 種類使い分ける必要・設定ミスで事故りやすく却下
- prefix 案 → 接続 1 本・key を見れば用途が一目で分かる（採用）。例えると「同じ倉庫の荷物に種類別シールを貼る」

### 6-6. 知っておく: 失敗パターン（MVP では深入りしない）

- **cache stampede**: 人気 key の TTL が切れた瞬間、同時 miss が DB に殺到。対策は TTL を長めにする等。MVP では許容
- **Redis ダウン**: try-catch で握って DB 直行。未読バッジは諦める・全員 offline 表示など「データが消えても致命的にしない」設計＝「Redis は派生キャッシュ」の真意

## 第 7 章 画面設計 — URL は場所、状態は一時的

D-4 の判断はほぼ全て次の一文に還元できる：

> **URL = 安定した「場所の住所」 / モーダル・ペイン・スレッド開閉 = 画面内の「一時的な状態」**

迷ったら「**そのリンクを他人に送って、相手に同じ意味になるか?**」で決める（なる→URL を変える／ならない→変えない）。

### 7-1. 引き出し: 3 ペインは「同時参照」のため

業務チャットは「#A を見ながら #B に書く」が頻発。画面遷移だと内容が消える → ペインを並べる。rail（WS 切替）は「頻度は低いが状況把握が常時必要」なので独立させる。**操作頻度が違う情報を 1 ペインに混ぜると情報過多**になる。

### 7-2. 引き出し: URL 設計 3 原則

1. **動詞を URL に書かない**（リソース指向）— `/channels/5/edit` ではなく `/channels/5` ＋ 編集モーダル。URL は共有するものなので、共有して自然な内容だけ入れる
2. **名前でなく ID（数字）**— `/channels/general` はリネームで死ぬ。ID は変わらないので `/channels/5`
3. **WS を先頭階層に固定**— `/channels/5` だとどの WS の 5 番か不明（ID は WS 内で一意であって全体で一意ではない）。`/workspaces/1/channels/5` で確定

共通する芯は「**URL は安定・共有して自然・システム内部の都合を見せない**」。

### 7-3. 引き出し: スレッドは右ペイン／モーダルは URL を持たない

スレッドの表示場所 3 候補（右ペイン / 独立ルート / モーダル）のうち、**「本流を見続けられる」を最優先**して右ペインを採用（独立ルートとモーダルは本流が見えなくなる）。URL シェアできない欠点は MVP では妥協し未決事項に残す。

モーダルが URL を持たないのも同じ理屈 — 「場所の移動」でなく「画面内の一時状態」だから。URL を変えると共有時に相手の画面でも開いてしまうし、履歴ノイズになる。閉じるのは `Esc`/`✕` であってブラウザバックではない。

### 7-4. 引き出し: 認証境界とルートグループ

URL は「公開 / 未ログインのみ / ログイン必須」の 3 タイプ。ログイン済みが login 画面に来たら別所へ飛ばす（「未ログインのみ」）。Next.js の `(group)` 記法で URL に出さず論理グループ化し、共通レイアウトと共通の認可チェックを `(group)/layout.tsx` にまとめる。**URL は対外的な契約、フォルダは内部整理**で別責務。

### 7-5. 引き出し: MVP は PC 優先（手抜きではなく優先順位）

業務利用 × 3 ペイン構成 × MVP の 3 つが重なり PC 優先。モバイルは「捨てた」のではなく「**最初のリリースに含めないと意図的に決めた**」。反応を見て後で足すか判断する（0-1 / 0-2 と同じ割り切り）。

## 第 8 章 基盤・運用の土台

### 8-1. Docker Compose / Spring Boot / Flyway の押さえどころ

- ローカルは `docker compose up -d` で PostgreSQL/Redis を起動（S3 を使う機能のときだけ `--profile storage` で LocalStack）
- Spring Boot は starter（必要な依存をまとめた箱）で構成。依存は**必要になってから追加**（最初は最小構成）
- `ddl-auto: validate` で Entity と DB スキーマの整合をチェック（アプリがスキーマを勝手に変えない）

### 8-2. 引き出し: Flyway は V（一度きり）と R（毎回）を使い分け

- **V__**（Versioned）= バージョン付き、一度だけ適用。**マージ済みの V ファイルは編集禁止**（チェックサムが変わると他環境で不整合）。作り直したいときはローカルの DB ボリュームを消す
- **R__**（Repeatable）= 毎回チェックサムが変われば再実行。シードデータ向き。先頭で全消し（TRUNCATE）して**冪等**にする
- **seed は dev プロファイルだけ**で流す（Spring Profile で `R__seed_dev.sql` を分離）。FK は id 直書きを避け、参照で解決

### 8-3. 確定した DB 設計ルール（V2 以降も踏襲）

- 主キー `BIGINT GENERATED ALWAYS AS IDENTITY` / ENUM は VARCHAR + CHECK / 論理削除 `deleted_at` / `updated_at` は共通トリガーで自動更新 / FK の ON DELETE は基本 RESTRICT・結合系のみ CASCADE・`parent_message_id` は SET NULL

> 次の機能を実装してください。設計と構造は **<参考 PR / F-XX>** と同じパターンを踏襲し、既存コードと同じ形を崩さないでください。差分は次の通りです: <差分>

**WebSocket / リアルタイム配信を足すとき**
> リアルタイム配信を追加します。送信は WebSocket 一本（REST 送信は作らない）、編集・削除は REST + WebSocket 配信で。配信は `MessageService` から直接でなく **Redis Pub-Sub 経由**。Redis publish 失敗は例外を投げずログのみ。Pub-Sub の prefix は専用に切り（既存への相乗り禁止）、用途を表す名前にしてください。

**WebSocket 認証**
> 認証は STOMP **CONNECT フレームのヘッダの JWT** を `ChannelInterceptor` で検証。REST と同じ `JwtTokenProvider` を流用。`/ws/**` は HTTP セキュリティで許可してください。

**一覧 API**
> ページングは **cursor ベース**（id 昇順 + `limit+1` で hasMore 判定、最後の要素を nextCursor）。関連データを各行に含めるなら **JOIN FETCH** で N+1 を回避してください。

**「既存なら返す」エンドポイント**
> 「既存があれば再利用、なければ作る」挙動です。既存→200 / 新規→201 / **409 は使わない**。

**何度も呼ばれる操作**
> **冪等**に作る。既に目的の状態ならエラーにせず成功を返す。カウンタは状態が実際に変わったときだけ更新。

**エラー設計**
> エラーは RFC 7807 ProblemDetail（`application/problem+json`）。ステータスは意味で選ぶ: 最初から無い→404 / 消えた・期限切れ→410 / 値が不正→422 / 権限なし→403（所属を漏らさないため非メンバーと非権限を 403 に寄せる）。

**秘密のトークン**
> トークンは DB に **SHA-256 ハッシュで保存**、平文は発行時に一度だけ返す。照合は平文を同じ方法でハッシュ化して比較。平文は DB に残さない。

**DB 制約があるとき**
> 整合性（NOT NULL / UNIQUE / FK / CHECK / XOR）は **DB 制約に任せ**、Java で二重に書かない。クライアントに見せたくない制約（順序固定など）は**サービス層に入った直後に正規化**してから Repository に渡す。

**削除機能**
> 履歴を残すなら **論理削除**（`deleted_at` / 退出日時）。退出=日時セット、再参加=NULL に戻す、一覧はアクティブのみ絞る。「○○を消したら●●も」は、まず論理削除や CASCADE で済まないか確認してください。

**入れ子データ（返信・コメント）**
> 階層は **1 階層に固定**。返信は根にぶら下げ、返信への返信は根に付け替える。**同じテーブル**に保存し、絞り込み（親を持つ/持たない）で見せ分ける。専用テーブルは作らない。

**子リソースの権限**
> 子の権限は**親の権限を継承**する。専用ルールを作らず既存の親判定を呼ぶ（権限の二重定義を避ける）。

**Controller の境界**
> 境界は **扱うリソース（Entity）** で引く。URL 階層では引かない。同じリソースなら 2 系統 URL でも 1 Controller、別リソースなら同じ URL 前半でも別 Controller。

**副作用（ついで処理）**
> 「直書き / 別 Service 呼び出し」は **トランザクション・事前チェック・独立性** の 3 軸で判断。揃えて巻き戻したい/途中状態と噛み合う→直書き、他からも呼ばれる→呼び出し。

**並行処理の競合**
> 防ぐコストと被害を天秤に。実害が小さく高負荷も来ないなら割り切り、理由と将来の厳密化手段をコメントに残す。お金・在庫・一意性が絡むなら厳密に防ぐ。

**既存に似た処理があるとき**
> 別ドメインには安易に依存しない。小さく変わりにくいならコピーして独立。重複と結合のコストを天秤にかけ、必要になってから共通化。

## 付録 B 自問チェックリスト

新機能の設計を始める前に：

- [ ] この通信は**リアルタイム配信が要るか**? 要る→WebSocket、結果応答が主→REST
- [ ] この一覧は cursor ページングか? 関連を含めるなら JOIN FETCH したか?
- [ ] このエンドポイントはリスト系/単一取得系? 可視性の単位は行/親リソース/権限のどれ?
- [ ] エラーのステータスは「意味」で選んだか（404/410/422/403）? 形式は ProblemDetail か?
- [ ] 秘密情報を平文で保存していないか? ハッシュにしたか?
- [ ] この操作は冪等か? 既に目的の状態のときエラーにしていないか?
- [ ] 整合性ルールを DB 制約に寄せたか? アプリで二重管理していないか?
- [ ] 削除は論理削除で済むか? 「ついで処理」は CASCADE/論理削除で消えないか?
- [ ] 子リソースの権限は親から継承できるか?
- [ ] Controller はリソース単位で分けたか?
- [ ] この副作用は 3 軸（トランザクション/事前チェック/独立性）でどちらに倒れるか?
- [ ] この機能は既存の F-XX のどのパターンの応用か? AI に「F-XX と同じで、差分は◯◯」と言えるか?
- [ ] 画面の操作は「場所の移動（URL 変える）」か「一時状態（変えない）」か?
- [ ] 今これは**本当に必要か**（YAGNI）? 割り切るなら逃げ道を記録したか?

## 付録 C 用語ひとこと辞典

| 用語 | ひと言 |
| --- | --- |
| HTTP | 「お願い 1 回 → 返事 1 回」の片方向通信 |
| REST | URL でモノ、メソッドで動作を表す HTTP のお作法 |
| WebSocket | 常時接続の双方向通信路（通信路だけ提供） |
| STOMP | WebSocket 上のメッセージのお作法（コマンド+ヘッダ+本文） |
| destination | 購読先・配信先を表す文字列ラベル（実体はない） |
| broker | destination→購読 session の名簿を持って配る部品（Pub-Sub の核） |
| simple broker | Spring プロセス内で動く broker（自プロセス内しか見えない） |
| Pub-Sub | 1 つに publish→購読者全員に配る配信モデル |
| Redis Pub-Sub | インスタンス間の伝言役（Redis の機能） |
| エンベロープ | `{type, serverTime, payload}` の共通封筒 |
| JWT | 「私は誰々」を署名付きで証明する文字列（ペイロードは Base64、暗号化ではない） |
| 回転(rotation) | refresh を使うたび旧を無効化＋新発行（漏洩検知） |
| cursor ページング | 「しおりからの続き」式。データ増減でズレない |
| ProblemDetail | RFC 7807 のエラー JSON 標準形式 |
| dirty checking | `@Transactional` 内でエンティティを変えると自動で UPDATE される JPA の挙動 |
| N+1 問題 | リストの各行ごとに追加クエリが走る問題（JOIN FETCH で回避） |
| 論理削除 | 物理削除せず `deleted_at` 等で印を付ける |
| 冪等 | 何度実行しても結果が同じ |
| cache-aside | 「まず Redis→なければ DB→結果を Redis に置く」パターン |
| 無効化 | 古くなったキャッシュを Redis から消す（SET でなく DELETE） |
| TTL | Redis が時計を見て勝手に消す期限（無効化の安全網） |
| YAGNI | 必要になるまで作らない |
