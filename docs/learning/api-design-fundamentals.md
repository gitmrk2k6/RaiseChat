## 1. Web アプリ通信の前提

### 1.1 ブラウザとサーバー

Web アプリは **ブラウザとサーバーがインターネット越しに通信** することで動く。

```
[ブラウザ（自分の PC）]  ⇔ インターネット ⇔  [サーバー（遠くのコンピュータ）]
        画面を見ている人                          データを持っている人
```

### 1.2 HTTP — 通信のお作法

**HTTP** = ブラウザとサーバーがお話する時の **「お作法・ルール」** の名前。

| 性質 | 内容 |
| --- | --- |
| 通信モデル | **お願い 1 回 → 返事 1 回で完結** |
| サーバーから話しかけられる？ | ❌ できない（クライアントが聞かないと黙ったまま） |

```
[ブラウザ] ── お願い（リクエスト）──→ [サーバー]
[ブラウザ] ←── 返事（レスポンス）─── [サーバー]
                  終わり
```

🔴 重要: 「お願いを出さない限りサーバーは話しかけてこない」。これが後のチャットアプリで困る理由になる。

---

## 2. REST — HTTP を使う時の「決まった書き方ルール」

### 2.1 一言で

**REST** = 「URL でモノを指す、HTTP メソッドで動作を表す」というお作法。

### 2.2 HTTP メソッド 4 つ（CRUD）

| メソッド | 意味 | URL 例 | 日本語 |
| --- | --- | --- | --- |
| **GET** | 取得 | `GET /users/12` | 「ユーザー 12 を見せて」 |
| **POST** | 作成 | `POST /users` | 「ユーザーを作って」 |
| **PUT** | 更新 | `PUT /users/12` | 「ユーザー 12 を更新して」 |
| **DELETE** | 削除 | `DELETE /users/12` | 「ユーザー 12 を消して」 |

🔴 **同じ URL でもメソッドが違えば意味が違う**。

### 2.3 なぜ REST に従うのか

ルールがないと各プロジェクトで好き勝手な URL になり、新しい人の学習コストが高い:

```
❌ /getUser?id=12  /createNewUser  /deleteUserById?uid=12
✅ GET /users/12   POST /users     DELETE /users/12
```

世界中の Web API がこのお作法を使っているので、覚えると応用が効く。

### 2.4 設計書での対応

[docs/api-design.md](../api-design.md) **§3 エンドポイント一覧** の 24 エンドポイントすべてが REST のお作法に従っている。

## 3. WebSocket — リアルタイム通信のための別経路

### 3.1 HTTP だけでチャットを作ろうとすると困る

HTTP は「お願いがない限りサーバーは黙る」性質。チャットでは **A さんが送ったメッセージを B さんが即座に受け取りたい** が、B さん側が「新しいメッセージある?」と聞かないと教えてくれない。

#### 案: ポーリング（無理やり HTTP で解決しようとすると…）

```
ブラウザ: 「新しいメッセージある?」 → サーバー: 「ないよ」  (3 秒待つ)
ブラウザ: 「新しいメッセージある?」 → サーバー: 「ないよ」  (3 秒待つ)
ブラウザ: 「新しいメッセージある?」 → サーバー: 「あるよ!」
```

問題: 通信が無駄、最大 3 秒の遅延、100 人いるとサーバーが「ないよ」と返すだけで疲弊。

### 3.2 WebSocket の解決

**WebSocket** = ブラウザとサーバーを **「繋ぎっぱなしにする」** 仕組み。一度繋ぐと、どちらからでも自由に話しかけられる。

```
[HTTP]  📬 手紙のやり取り。封筒で 1 往復、それきり。
[WebSocket]  ☎️ 電話。一度繋いだら両方が自由に話せる。
```

### 3.3 比較表

| | REST（HTTP）| WebSocket |
| --- | --- | --- |
| 通信モデル | 1 往復で完結 | 繋ぎっぱなし |
| サーバーから話しかけられる？ | ❌ | ✅ |
| 得意 | データ取得・更新の結果を確実に返す | リアルタイム配信 |
| 不得意 | リアルタイム配信 | 1 往復で済む用途には大げさ |

### 3.4 設計書での対応

[docs/api-design.md](../api-design.md) **§6 WebSocket との境界** で責務分担を明示:

| 操作 | 経路 | 理由 |
| --- | --- | --- |
| 新規メッセージ送信 | **WebSocket のみ** | 配信経路を一本化し重複・順序問題を回避 |
| メッセージ履歴取得 | REST | ページング・キャッシュと相性が良い |
| メッセージ編集・削除 | REST + WebSocket 配信 | 操作元はクライアント単発、結果は全員に配信 |
| ログイン・プロフィール更新 | REST | リアルタイム性不要 |

### 3.5 なぜ「送信を REST と WebSocket 両方」にしなかったか

入口を 2 経路にすると次の問題:

1. **二重表示の危険** … 送信者が REST レスポンスと WebSocket 配信の両方で自分の発言を受け取る
2. **入口が 2 つ** … サーバー側で送信処理を 2 箇所に書く、片方変えるとバグ
3. **順序の混乱** … REST 送信と WebSocket 送信が時間的にどっちが先か判定が複雑

🔴 **同じ操作の入口を 2 経路で提供しない** が設計原則。

## 4. ページング — 大量データを小分けに取る仕組み

### 4.1 ページングが必要な理由

メッセージ 10 万件を一度に返すと: 通信が重い / ブラウザがフリーズ / そもそも使わない。
→ **小分けに区切って取得** する必要がある。

### 4.2 2 つの方式の比較

| | offset / limit 方式（古典） | cursor 方式（採用） |
| --- | --- | --- |
| 指定の仕方 | 「○件目から○件」 | 「しおりからの続き」 |
| URL 例 | `?offset=20&limit=20` | `?cursor=ABC123&limit=20` |
| たとえ | 本のページ番号で指定 | しおりを挟む |
| データ増減への耐性 | ❌ ズレる | ✅ 影響を受けない |

### 4.3 offset 方式の弱点（具体例）

```
時刻 12:00  メッセージ 100 件存在 → offset=0, limit=20 で 1〜20 を取得
時刻 12:01  メッセージ 5 件追加（→ 105 件に）
時刻 12:01  offset=20, limit=20 で続きを取得
            → 思った「21 件目」がズレて 16 件目になっている
            → 16〜20 を 2 重に読む
```

### 4.4 cursor 方式の利点

- ID ベースのしおりなので、データが増減しても位置がズレない
- DB の処理も「この ID より前」と直接指定するので速い
- 無限スクロール UI と相性が良い

### 4.5 設計書での対応

[docs/api-design.md](../api-design.md) **§1.2 ページング仕様** + 各メッセージ取得エンドポイント:

```
リクエスト:
  GET /api/channels/5/messages?cursor=eyJpZCI6OTAwfQ==&limit=50

レスポンス:
  { "items": [...], "nextCursor": "eyJpZCI6ODgwfQ==", "hasMore": true }
```

`nextCursor` は不透明文字列（base64）。クライアントは内容を解釈せずそのままサーバーに渡す。

## 5. RFC 7807 ProblemDetail — エラーの伝え方の業界標準

### 5.1 用語ほどき

- **RFC** = Request for Comments の略。インターネットの公式ルールブック
- **7807** = そのルールブックの番号
- **ProblemDetail** = エラーレスポンスの標準フォーマットの名前

### 5.2 なぜ業界標準があるのか

各プロジェクトでエラー JSON 形式がバラバラだと、クライアント側で毎回違う読み取りコードを書くハメに:

```
❌ A 社: { "error": "duplicate user_id" }
❌ B 社: { "errorCode": 1002, "errorMessage": "..." }
❌ C 社: { "status": "fail", "reason": "..." }
```

→ 業界共通フォーマットに揃えれば、クライアント処理を共通化できる。

### 5.3 ProblemDetail の形式

```json
{
  "type": "https://raisechat.example.com/problems/validation",
  "title": "Validation Failed",
  "status": 400,
  "detail": "リクエストボディに不正な値があります",
  "instance": "/api/auth/signup",
  "errors": [
    { "field": "userId", "message": "userId は半角英数字..." }
  ]
}
```

| フィールド | 役割 |
| --- | --- |
| `type` | エラーの種類を表す URL（分類タグ） |
| `title` | 短いタイトル |
| `status` | HTTP ステータスコード |
| `detail` | 詳しい説明 |
| `instance` | どのリクエストで起きたか |
| `errors`（拡張）| フィールド単位の詳細 |

### 5.4 採用理由

1. **クライアント処理を共通化できる** … エラーは全部同じ形なので 1 つの処理で全部読める
2. **Spring Boot 3 が標準対応** … フレームワークが組み込みで対応、自前実装より楽
3. **業界標準** … 新メンバーに「あー RFC 7807 ね」で済む

### 5.5 設計書での対応

[docs/api-design.md](../api-design.md) **§2.2 エラーレスポンス**。`Content-Type: application/problem+json` を使う。

## 6. JWT — ログイン済み証拠カードの形式

### 6.1 トークンが必要な理由

ログイン後、毎回ユーザー ID とパスワードを送るのは: 危険（漏洩リスク）+ 面倒（UX 悪化）。
→ ログイン時に **証拠カード（トークン）** を発行し、それを毎回見せる方式に。

### 6.2 JWT とは

- **JWT** = JSON Web Token の略
- 実体: 長い文字列（例: `eyJhbGci...`）
- 中身に「誰か」「いつまで有効か」を含み、改ざんできないように署名されている

### 6.3 2 トークン構成

| 種類 | 役割 | 寿命 | 使う場面 |
| --- | --- | --- | --- |
| アクセストークン | 「ログイン済み」入場証 | 短い（15 分） | ほぼ全 API リクエスト |
| リフレッシュトークン | アクセストークンを更新する鍵 | 長い（数週間） | `POST /api/auth/refresh` の時だけ |

### 6.4 たとえ話

- アクセストークン = コンサートの **リストバンド**（その日限り、落としても被害小）
- リフレッシュトークン = **チケット控え**（家にしまっておく、リストバンド再発行用）

### 6.5 なぜ 2 つに分けるか

1. **漏れた時の被害を最小化** … アクセストークンは通信で頻繁に使うので漏れやすい。寿命短く
2. **UX を保つ** … 15 分ごとに再ログインじゃキレる。リフレッシュトークンで裏でこっそり更新

### 6.6 詳細は別ノート

実装の詳細は [docs/learning/auth-jwt.md](auth-jwt.md) を参照。本ノートでは API 設計書 [§5.1 認証（F-01）](../api-design.md) との対応関係だけ示す:

| エンドポイント | 役割 |
| --- | --- |
| `POST /api/auth/signup` | 新規登録 + 2 トークン発行 |
| `POST /api/auth/login` | ログイン + 2 トークン発行 |
| `POST /api/auth/refresh` | リフレッシュトークン → 新アクセストークン |
| `POST /api/auth/logout` | リフレッシュトークン失効 |
| `GET /api/auth/me` | アクセストークン必須、自分の情報取得 |

## 7. API バージョニング不採用と YAGNI

### 7.1 そもそも API バージョニングとは

URL の中にバージョン番号を入れて、新旧仕様を並走させる仕組み:

```
GET /api/v1/users/12   ← 古い仕様（バージョン 1）
GET /api/v2/users/12   ← 新しい仕様（バージョン 2、並走可能）
```

### 7.2 なぜ並走が必要なのか（核心）

**サーバー側を v2 にしても、クライアント側がすぐ追従できるとは限らない**:

| クライアントの種類 | アップデート速度 |
| --- | --- |
| Web ブラウザのフロント | サーバー配信なので即時切替可 |
| スマホアプリ | ユーザーがストアでアップデートしないと古いまま |
| 他社の連携サービス | 他社のスケジュール次第、コントロール不可 |

サーバーだけ v2 に切り替えると、世界中の古いクライアントが一斉にエラーになる。
→ **移行期間として v1 と v2 を並走** させる必要がある。

### 7.3 たとえ話: 銀行 ATM

銀行が ATM ソフトを v2 に更新したい場合:
- 全 ATM 機を一斉更新は無理 → v1 と v2 が混在する期間が必ずある
- サーバー側は両方を受け付ける必要がある
- 全 ATM が v2 になって初めて v1 サポート終了

### 7.4 RaiseChat で採用しなかった理由

設計書 [§1 設計方針 原則 2](../api-design.md) で明記:

> URL プレフィックスは `/api`。バージョニング（`/api/v1`）は MVP 時点では導入しない。破壊的変更が発生したら導入を検討。

理由:

- まだクライアント（フロントエンド・スマホアプリ・外部連携）が存在しない
- **並走させる相手がいない** = バージョニングのコストを払う意味がない
- 必要になったら後から `/api/v2/` を新設するだけで対応可能

### 7.5 YAGNI の原則

**YAGNI** = You Aren't Gonna Need It（それ、必要にならないよ）

「将来必要かも」で先回り実装をしない、という設計の重要原則。
- 必要になってから入れる
- 今のサイズに合った設計を保つ

🔴 設計判断の際の汎用ガイドライン: **「先回り実装は技術的負債を生む」**

## 8. まとめチートシート

### Webアプリ通信の基礎

- **HTTP** = お願い 1 回 → 返事 1 回。サーバーから話しかけられない
- **REST** = HTTP の「URL でモノ、メソッドで動作」お作法
- **HTTP メソッド 4 つ**: GET（取得）/ POST（作成）/ PUT（更新）/ DELETE（削除）

### リアルタイム通信

- **WebSocket** = 繋ぎっぱなしの双方向通信。サーバーから話しかけられる
- **送信は WebSocket 一本、編集・削除は REST + WebSocket 配信** の責務分担
- **同じ操作の入口を 2 経路にしない** が設計原則

### ページング

- **cursor ベース** を採用（offset/limit はデータ増減でズレる）
- レスポンスに `nextCursor` `hasMore` を含める

### エラー設計

- **RFC 7807 ProblemDetail** に準拠（業界標準・Spring Boot 3 標準対応）
- フィールド: `type` / `title` / `status` / `detail` / `instance` + 拡張 `errors`

### 認証

- **JWT 2 トークン構成**（アクセス短期 + リフレッシュ長期）
- 漏れリスクと UX のトレードオフを両立

### 設計哲学

- **YAGNI** = 必要になるまで先回り実装しない
- API バージョニングは「並走させる相手が出てきたら導入」
