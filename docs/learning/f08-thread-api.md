# F-08 スレッド API 学習ノート

このノートは、F-08 スレッド API（PR #64）の実装で身に付けた **設計判断と引き出し** を、後日 1 人で再学習できる質で書き残したものです。前提知識ゼロから読み始めても付いてこられるように章を組んでいます。

このノートは **読む順** に章を並べています。途中で「飛ばしても理解できる章」はありません。各章ともすべて重点章扱いで書いています。

スレッド機能は「メッセージに返信できる」だけの、地味な機能に見えます。ところが実装してみると、**「データの形」「同じデータの見せ方」「権限の継ぎ方」「リアルタイム配信の設計」「新機能を足すときに既存をどう揃えるか」** という、設計の核心がいくつも顔を出しました。しかも F-08 は、これまでの F-05（チャンネルメッセージ）/ F-06（DM）の土台の上に乗っているので、「過去の設計が今どう効くか」を体感できる、おいしい題材でした。

---

## このノートで身に付く 5 つの引き出し

| # | 引き出し | このパターンが役立つ場面 |
|---|---|---|
| 1 | 木構造（親子関係）を「何階層まで」と決めて強制する | 返信・コメント・カテゴリなど「入れ子になりうる」データを扱うとき |
| 2 | 同じデータを「絞り込み」で別々のビューに見せる | 1 つのテーブルから一覧・詳細・サブ画面など複数の見え方を作るとき |
| 3 | 子リソースの権限は親から継承する | 「この一覧を見ていい人は誰か」を、親の権限から自動で決めたいとき |
| 4 | リアルタイム配信先は「見え方」の設計（ライブと履歴を一致させる） | WebSocket / 通知などで「どこに何を流すか」を決めるとき |
| 5 | 新機能の追加は、既存の似た処理を「揃える」好機 | 機能を足すついでに、散らばった分岐を 1 箇所にまとめたいとき |

最後の章でこの 5 つを「AI への指示テンプレ」として再掲します。次に別機能を AI に任せるときに、ここから引いて貼れる形にしてあります。

## はじめに: スレッドは裏側で何をしているのか

本題に入る前に、スレッドが実際にどう成り立っているのかを一枚絵で掴んでおきましょう。これが全章の土台になります。

```
チャンネルのタイムライン               スレッド（親メッセージの中）
┌─────────────────────────┐
│ Aさん: おはよう              │
│ Bさん: 今日の会議どうする？  │◀──┐ ← この「親」をタップすると
│ Cさん: ランチ行こう          │   │
└─────────────────────────┘   │
                                  │   ┌───────────────────┐
                                  └── │ Bさん: 今日の会議どうする？│ ← 親（再掲）
                                      │  └ Aさん: 10時からで       │ ← 返信1
                                      │  └ Cさん: OKです           │ ← 返信2
                                      └───────────────────┘
```

ポイントは、**返信（10時から / OKです）はタイムラインには出てこない** ということです。タイムラインに出るのは「親」だけ。返信は、親を開いたときに初めて見える「別の場所」に格納されます。

この絵の中に、これから学ぶ論点が全部入っています。

- 返信に、さらに返信したら？ どこまで入れ子にする？ → **引き出し1（木構造を1階層に固定）**
- 「タイムラインには出ないが、スレッドには出る」をどう実現する？ → **引き出し2（同じデータを絞り込みで見せ分ける）**
- そのスレッドを見ていいのは誰？ → **引き出し3（権限の継承）**
- 誰かが返信した瞬間、それをリアルタイムでどこに届ける？ → **引き出し4（配信先の設計）**
- 返信って、結局「親を持ったメッセージ」では？ 送信の仕組みは作り直す？ → **引き出し5（既存を揃える）**

では 1 つずつ見ていきます。

## Chapter 1: 木構造を「1 階層」に固定する

F-08 で最初に決めるのが「スレッドの形」です。ここはデータ構造の話なので、一番丁寧に書きます。

### Step 1-1: メッセージは「親子」を持てる

スレッドとは、要するに **「あるメッセージにぶら下がる返信たち」** です。メッセージ同士に「親 - 子」の関係を持たせることで表現します。

- 「今日の会議どうする？」というメッセージ = **親**
- 「10時からで」という返信 = 親に **ぶら下がった子**

データの上では、返信メッセージが「私の親はこのメッセージです」という情報（親の ID）を 1 つ持つだけです。たったこれだけで、親子関係が表現できます。

### Step 1-2: 親子は「木（ツリー）」になりうる

ここで一つ、当然の疑問が浮かびます。

> 返信（子）に、さらに返信できるの? その返信にも、また返信できるの?

理屈の上では、できてしまいます。子の子の子の…と、どこまでも枝分かれできる。これを **木構造（ツリー）** と呼びます。家系図や、フォルダの入れ子をイメージしてください。

```
親
 ├─ 子
 │   └─ 孫
 │        └─ ひ孫 …（無限に続きうる）
 └─ 子
```

木構造は強力ですが、**無限に深くなれる** という厄介さを持っています。

### Step 1-3: 深い木の何が困るのか

返信の返信の返信の…が許されると、こんな問題が起きます。

- **表示が破綻する**：画面の右へ右へとインデント（字下げ）が深くなり、文字を表示する幅が無くなる。スマホだと数階層で読めなくなる。
- **取得が複雑になる**：「このスレッドの全部の返信を取ってきて」と言われたとき、木をぜんぶ掘り下げて辿る必要があり、処理が重く・複雑になる。
- **ユーザーが迷子になる**：「今どの返信に返信してるんだっけ?」が分からなくなる。

実際、世の中の多くのチャットアプリ（Slack も）は、**スレッドをわざと「1 階層」に制限** しています。親があって、その下に返信がフラットに並ぶだけ。返信の下にさらに階層は作らない。

### Step 1-4: 例えると「会議の議題と発言」

例え話で言うと、こういうことです。

会議で「今日の会議どうする?」という **議題（親）** が出されたとします。それに対してみんなが **発言（返信）** する。

- Aさん「10時からで」
- Cさん「OKです」
- Aさん「あ、やっぱり11時に」

これらの発言は、**全部「その議題に対する発言」** としてフラットに並びます。「Cさんの発言に対するAさんの発言に対する…」と階層を作る必要はありません。みんな同じ議題にぶら下がっているだけ。これが 1 階層スレッドの考え方です。

### Step 1-5: F-08 の判断 ― 返信への返信は「親」に付け替える

そこで F-08 では、こういうルールにしました。

> 返信(子)に、さらに返信しようとしたら、その新しい返信を **「子」ではなく「親（スレッドの根）」にぶら下げ直す**。

「根（root）」というのは、スレッドの一番上の親メッセージのことです。返信の返信が来ても、子の下に孫を作らず、**全部まとめてスレッドの根に並べる**。

```
やりたいこと（深い木）          実際にやること（1階層に付け替え）
親                              親（根）
 └─ 子                          ├─ 子
     └─ 孫 ← これを…            └─ 孫 ← 根に付け替え！
```

こうすれば、どんなに「返信に返信」しても、スレッドは常に「親 + フラットな返信の列」という単純な形に保たれます。表示も取得も迷子も、全部解決します。

### Step 1-6: なぜ「エラーにする」のではなく「付け替える」のか

ここは設計判断です。「返信に返信しようとしたらエラー（拒否）」にする手もありました。でも、**付け替える方を選びました**。理由はこうです。

- ユーザーから見ると、「返信に返信」は自然な操作です。Cさんの発言を引用して返したいことは普通にある。それをエラーにすると「なんで返信できないの?」と不親切。
- 付け替えれば、ユーザーの操作は成功し、発言はちゃんとスレッドに残る。ただ「位置」が根にそろうだけ。ユーザーの目的（スレッドで会話する）は達成される。
- エラーにすると、クライアント側に「エラー時はどうするか」という新しい処理を増やすことになる。付け替えなら、その手間もいらない。

「制約を破る操作が来たとき、**拒否する** のか **丸めて受け入れる** のか」。今回は「丸めて受け入れる（根に付け替える）」を選んだ、ということです。ユーザーにとって自然な操作は、できるだけ成功させてあげる。

### Step 1-7: 引き出し1「木構造を1階層に固定する」

**引き出し**：親子関係を持てるデータ（返信・コメント・カテゴリなど）は、**「何階層まで許すか」を最初に決める**。無限に深い木は表示・取得・UX が破綻しがち。多くの場合 1 階層で十分。制限を超える操作が来たら、**エラーにするか / 上位に丸めて受け入れるか** を、ユーザーの自然さで判断する。

**AI への指示テンプレ**

> この返信（コメント / スレッド）機能は、**スレッドを 1 階層に固定** してください。
> - 返信は常に「スレッドの根（最上位の親）」にぶら下げる
> - 返信に対してさらに返信が来たら、親をたどって **根に付け替える**（深い入れ子を作らない）
> - エラーにせず、付け替えて受け入れる方針で（ユーザーの操作はできるだけ成功させる）

## Chapter 2: 同じデータを「絞り込み」で見せ分ける

スレッド機能で次に効いてくるのが、**「タイムラインには返信を出さない。でもスレッドを開けば返信が見える」** をどう実現するか、です。

### Step 2-1: 返信もメッセージも「同じ箱」に入っている

まず大事な事実から。チャンネルの通常メッセージも、スレッドの返信も、**まったく同じ「メッセージ」というデータ** です。保存場所も同じ（同じテーブル＝同じ箱）。違いは、返信だけが **「親の ID」を持っている** という一点だけです。

- 通常メッセージ → 親を持たない（親 ID は空っぽ）
- スレッド返信 → 親を持つ（親 ID が入っている）

つまり「箱の中身」は同じで、ラベルが 1 個違うだけ。

### Step 2-2: 「親を持つか持たないか」で世界を分ける

ここが今回の肝です。同じ箱から、**取り出すときの条件（絞り込み）** を変えるだけで、まったく違う 2 つの画面を作れます。

| 画面 | 絞り込み条件 | 何が出るか |
|---|---|---|
| チャンネルのタイムライン | **親を持たない** メッセージだけ | 通常の投稿だけ。返信は出ない |
| スレッド画面 | **親が「このメッセージ」である** ものだけ | その親への返信だけ |

「親を持たないものだけ見せる」とタイムラインになり、「親が X のものだけ見せる」とスレッドになる。**同じデータを、絞り込みの条件を変えて 2 つの顔に見せている** わけです。

### Step 2-3: 例えると「同じ書類棚の引き出し方」

例え話で言うと、巨大な書類棚があるとします。書類には「親番号」を書く欄があります。

- 親番号が **空欄** の書類だけ集める → 「独立した案件の一覧」ができる
- 親番号が **"案件42"** の書類だけ集める → 「案件42 に関する補足書類の束」ができる

棚（保存場所）は 1 つ。でも「どの欄でフィルタするか」で、見える書類の束がガラッと変わる。データベースの世界でも、これとまったく同じことをしています。

### Step 2-4: なぜ「返信専用の箱」を作らなかったのか

ここで設計判断。「返信は通常メッセージと別物だから、別の箱（別テーブル）に入れたら?」という案もありえます。でも、それはしませんでした。理由はこうです。

- 返信と通常メッセージは、**持っている情報がほぼ同じ**（誰が・いつ・何を書いた）。別の箱にすると、ほぼ同じ構造の箱が 2 つでき、二重管理になる。
- 「返信を編集する」「返信を削除する」も、通常メッセージの編集・削除と **まったく同じ処理** でいい。箱を分けると、同じ処理を 2 つ書くことになる。
- 「親を持つ/持たない」という 1 つのラベルだけで見せ分けられるなら、箱は 1 つで十分。

**「見た目が違うもの＝データも分けるべき」とは限らない**。中身がほぼ同じなら、1 つの箱に入れて「絞り込み」で見せ分ける方が、ずっとシンプルです。これは Chapter 1 の「無限の木にしない」と並んで、「複雑にしない」ための判断です。

### Step 2-5: 引き出し2「絞り込みで見せ分ける」

**引き出し**：見た目が違う複数の画面（一覧・サブ画面など）でも、扱うデータの中身がほぼ同じなら、**同じ保存場所に入れて「絞り込み条件」で見せ分ける**。データを分ける前に「本当に別物か? それとも同じものの違う切り口か?」を問う。1 つのラベル（親の有無など）で見分けられるなら、それで十分なことが多い。

**AI への指示テンプレ**

> 通常メッセージとスレッド返信は **同じテーブルに保存** し、「親を持つかどうか」で見せ分けてください。
> - タイムライン一覧 → 親を持たないメッセージだけを返す
> - スレッド一覧 → 親が指定メッセージのものだけを返す
> - 返信専用のテーブルは作らないでください（編集・削除も通常メッセージと同じ処理を使い回せるため）

## Chapter 3: 子リソースの権限は「親」から継承する

スレッドの返信を「見ていい人 / 投稿していい人」は誰か。この **権限（アクセス制御）** の決め方が、この章のテーマです。

### Step 3-1: そもそも権限チェックとは

API には「誰でも触れていいわけではない」ものがあります。たとえば、自分が入っていないチャンネルのメッセージは読めてはいけない。これを守るのが **権限チェック（認可）** です。

スレッドの返信にも、当然これが必要です。「無関係なスレッドの返信を、部外者が読んだり書き込んだりできる」のは事故です。

### Step 3-2: スレッドは「どこかのチャンネル or DM」に属している

ここで思い出してほしいのが、Chapter 2 の事実です。**返信も親も、同じ「メッセージ」** でした。そしてメッセージは必ず、**どこかのチャンネル、またはどこかの DM** に属しています。

つまりスレッドは、宙に浮いているのではなく、**必ず「ある親メッセージ」を通じて、あるチャンネル / DM につながっている** のです。

```
スレッドの返信 ──ぶら下がる──▶ 親メッセージ ──属する──▶ チャンネル(または DM)
```

### Step 3-3: だったら、権限も親からたどればいい

ここで素直な発想が効きます。

> スレッドを見ていい人 = その親メッセージがあるチャンネル（or DM）を見ていい人

わざわざスレッド専用の権限ルールを新しく作る必要はありません。**親がいる場所の権限を、そのまま受け継げばいい**。これを **権限の継承** と呼びます。

実際の処理はこうです。「このスレッドの返信を見せて」と言われたら、

1. まず親メッセージを見つける
2. その親が **チャンネル** にあるなら → 「あなた、このチャンネルのメンバー?」をチェック
3. その親が **DM** にあるなら → 「あなた、この DM の当事者?」をチェック
4. OK なら返信を見せる。ダメなら拒否

「スレッドの権限」という新しいルールは一切作らず、**既にあるチャンネル / DM の権限チェックを呼ぶだけ** で済みました。

### Step 3-4: 例えると「会議室の鍵」

例え話で言うと、こういうことです。

ある会議室（チャンネル）に入れるのは、鍵を持っている人だけです。その会議室の中で行われた議論（スレッド）の議事録を読めるのは、**当然、その会議室に入れる人** ですよね。議事録ごとに別の鍵を作る必要はない。「会議室の鍵を持っている＝その中の議事録も読んでいい」で十分。

スレッドの権限も同じ。「親メッセージがある部屋に入れる人＝そのスレッドも見ていい人」。部屋の鍵を流用するわけです。

### Step 3-5: なぜ継承が嬉しいのか

権限を継承する設計には、こんな良さがあります。

- **ルールが二重にならない**：チャンネルの権限ルールが 1 つあれば、スレッドの権限も自動で正しくなる。チャンネルの権限を変えたら、スレッドの権限も勝手に追随する。
- **矛盾が起きない**：もしスレッド専用の権限ルールを別に作ると、「チャンネルは見られるのにスレッドは見られない」みたいな矛盾が生まれうる。継承なら、そういう食い違いが原理的に起きない。
- **コードが小さい**：新しい権限チェックを書かず、既存のものを呼ぶだけ。

権限のような「絶対に間違えてはいけないもの」ほど、**新しく作るより、信頼できる既存のものを継承する** ほうが安全です。

### Step 3-6: 引き出し3「権限は親から継承する」

**引き出し**：子リソース（スレッド返信・コメント・添付など）の権限は、**それが属する親リソースの権限をそのまま継承** する。子専用の権限ルールを新しく作らない。「この子を見ていい人＝親を見ていい人」と定義すれば、ルールが二重にならず、矛盾も起きず、コードも小さくなる。権限のような間違えられない部分ほど、既存の信頼できる仕組みを流用する。

**AI への指示テンプレ**

> スレッド返信の閲覧・投稿の権限は、**親メッセージが属するチャンネル / DM のメンバーシップを継承** してください。
> - スレッド専用の権限ルールは作らない
> - 親がチャンネルにあるなら「チャンネルのメンバーか」、DM にあるなら「DM の当事者か」を、**既存の権限チェックを呼んで** 判定する
> - 権限は二重に定義せず、親の判定を再利用してください

## Chapter 4: リアルタイム配信先は「見え方」の設計

ここが F-08 で一番頭を使った章です。テーマは **「誰かが返信した瞬間、それをリアルタイムでどこに届けるか」**。

### Step 4-1: リアルタイム配信のおさらい

チャットでは、誰かが発言すると、見ている全員の画面に **即座に** 表示されます。これは、サーバーが「新しいメッセージが来たよ」という放送を、関係者に流しているからです（この仕組みの詳細は F-05 のノート参照）。

放送には「チャンネル」があります。テレビのチャンネルと同じで、**「どの放送に、誰が耳を傾けているか」** が決まっています。

- チャンネルの放送 → そのチャンネルを開いている人が聞いている
- DM の放送 → その DM を開いている人が聞いている
- **スレッドの放送** → そのスレッドを開いている人が聞いている ← F-08 で追加

### Step 4-2: 返信を「どの放送」に流すか

さて、誰かがスレッドに返信しました。この返信を、どの放送に流すべきでしょう? 候補は 2 つあります。

- **案A**：スレッドの放送だけに流す
- **案B**：スレッドの放送 + 元のチャンネルの放送、両方に流す

案B は「返信したことを、スレッドを見ていない人にもチャンネル上で知らせる」発想です。一見、親切そうに見えます。実際、設計の初期メモには「チャンネルにも流す」と書かれていました。

でも、最終的に **案A（スレッドの放送だけ）** を選びました。なぜか。ここが重要です。

### Step 4-3: ライブと「再読込」が食い違う問題

思い出してください。Chapter 2 で、**タイムラインには返信を出さない**（親を持つメッセージは一覧から除外する）と決めました。

ここで案B（チャンネルにも流す）を採ると、おかしなことが起きます。

```
返信した瞬間（ライブ）      → チャンネルにも流れるので、画面に返信がパッと出る
                              ↓
ページを再読込した後        → タイムラインは「返信を除外」するので、さっきの返信が消える！
```

つまり、**「さっき見えていたものが、再読込したら消える」** という、ユーザーを混乱させる食い違いが生まれます。「あれ? さっきの返信どこ行った?」となる。

これは **「ライブで見えるもの」と「保存されていて後で見えるもの」が一致していない** 状態です。リアルタイムの世界とデータの世界がズレている。これは気持ち悪い。

### Step 4-4: 配信先は「見え方」を決めている

ここで大事な気付きです。

> **「どの放送に流すか」は、技術的な配線の問題ではなく、「ユーザーに何をどこで見せるか」という見え方の設計である。**

返信をチャンネルの放送に流す = 「返信はチャンネルに表示されるべきもの」と宣言していることになる。でも保存ルール（Chapter 2）では「返信はチャンネルに出さない」と決めている。**配信ルールと保存ルールが矛盾している** わけです。

正しくは、両者を一致させる。「返信はスレッドの中だけで見えるもの」と決めたなら、**ライブ配信もスレッドの放送だけ** にする。そうすれば、ライブで見えるものと再読込で見えるものが、ピタッと一致します。

### Step 4-5: 「チャンネルにも出す」は将来の選択肢として残す

ちなみに Slack には「このスレッド返信をチャンネルにも投稿する」というチェックボックスがあります。あれは「案B を、ユーザーが選んだときだけ」やる仕組みです。

F-08（MVP）では、そこまでは作りませんでした。「まずはスレッドの中だけで完結する、シンプルな形」にして、チャンネルへのミラー（複製表示）は **将来必要になったら足す** ことにしました。この「今は作らない」という判断も、設計書とコードのコメントに残しています（Chapter 5 と通じる「やらないことを決める」姿勢）。

### Step 4-6: 引き出し4「配信先は見え方の設計」

**引き出し**：リアルタイム配信の「どこに流すか」は、技術配線ではなく **「ユーザーに何をどこで見せるか」の設計判断**。必ず **保存（履歴）の見え方と一致させる**。ライブで見えたものが再読込で消える / 出てくる、という食い違いを作らない。「ライブの世界」と「保存の世界」をズレさせないことが、混乱しない UX の土台。

**AI への指示テンプレ**

> スレッド返信のリアルタイム配信は、**スレッドの配信先だけ** に流してください。
> - チャンネル / DM の配信先には流さない（タイムラインの履歴が返信を除外しているため、流すとライブと再読込が食い違う）
> - 「ライブで見えるもの」と「保存されていて後で見えるもの」を必ず一致させる
> - チャンネルへのミラー表示（"also send to channel"）は今回スコープ外。必要になったら別途追加する方針でコメントを残す

## Chapter 5: 新機能の追加は「既存を揃える」好機

最後は、F-08 を実装していて気付いた「リファクタリングのタイミング」の話です。

### Step 5-1: 返信は「親を持ったメッセージ」にすぎない

ここまでで分かった通り、スレッド返信は **特別なデータではなく、ただ「親を持っているメッセージ」** でした。送信の仕組みも、通常のメッセージ送信とほとんど同じ。新しく作るというより、**既にある送信の仕組みに「親をセットする」だけ** で済みます。

実は、F-05 / F-06 の時点で、送信処理はすでに「親を指定できる」入り口を持っていました。スレッド機能を見越して、前もって用意してあったのです。F-08 は、その下地の上に乗っかる形になりました。

### Step 5-2: ところが「放送の流し方」がバラバラだった

ここで問題が見つかります。F-08 で「親を持つ返信はスレッドの放送に流す」（Chapter 4）と決めました。ところが既存のコードを見ると、**放送を流す処理が、チャンネル用・DM 用とバラバラの場所に散らばっていました**。

```
チャンネルメッセージを送る処理 → 自分でチャンネルの放送に流す
DM メッセージを送る処理       → 自分で DM の放送に流す
（編集・削除の処理）            → また別の場所で放送に流す
```

このまま「親があればスレッドに流す」を足そうとすると、**散らばった全部の場所に、同じ "親があれば…" の分岐を書き足す** ことになります。同じ判断が 3 箇所にも 4 箇所にもコピーされる。これは将来、必ずバグの温床になります（1 箇所だけ直し忘れる、など）。

### Step 5-3: 例えると「各自バラバラに郵便を出している」

例え話で言うと、こういうことです。

会社で、部署ごとに各自が好き勝手に郵便を出しているとします。営業部は営業部のやり方で、経理部は経理部のやり方で。ここに「速達の場合は赤いシールを貼る」という新ルールを足すと、**全部署に個別に「赤シール貼ってね」と伝えて回る** ことになります。1 部署でも伝え忘れたら、ルールが守られない。

それより、**郵便はすべて「郵便係」を通す** ことにすればどうでしょう。新ルールは郵便係 1 人に教えればいい。全部署の郵便が自動的に新ルールに従います。

### Step 5-4: F-08 の判断 ― 配信を 1 箇所に集約する

そこで F-08 では、新機能を足すついでに、**散らばっていた「放送を流す処理」を 1 箇所にまとめました**。「郵便係」を 1 人立てたわけです。

その郵便係は、こう判断します。

> メッセージが渡されたら、まず「親を持っているか」を見る。
> - 親があれば → スレッドの放送へ
> - 親がなくてチャンネル所属なら → チャンネルの放送へ
> - 親がなくて DM 所属なら → DM の放送へ

送信・編集・削除のどの処理も、この郵便係に「これ流しといて」と渡すだけ。**「どこに流すか」の判断は郵便係 1 人だけが持つ**。これで、判断が 1 箇所に集約され、コピーが消えました。

### Step 5-5: 「機能追加」と「整理整頓」を同時にやる

ここで学んだのは、**新機能の追加は、既存のコードを整える絶好のチャンスだ** ということです。

- もし「とにかく F-08 を動かす」だけが目的なら、散らばった場所に分岐をコピペするのが一番早い。でもそれは「負債」を増やす。
- 少し手を止めて「この散らばり、1 箇所にまとめられるな」と気付き、郵便係に集約する。すると、F-08 が動くだけでなく、**コード全体が前より整う**。

ただし注意点もあります。**整理整頓をやりすぎない** こと。今回は「配信処理がきれいに 1 箇所にまとまる」という明確な利益があったから集約しました。関係ない部分まで「ついでに直そう」と手を広げると、変更が膨らんで、何が原因で壊れたか分からなくなる。「**今いじっている機能と地続きの範囲**」に留めるのがコツです。

### Step 5-6: 「壊れないこと」を保証するのはテスト

集約のような整理整頓には、不安がつきまといます。「まとめたせいで、既存の送信が壊れないか?」と。

ここで効くのが **テスト** です。F-05 / F-06 のときに書いてあった「メッセージ送信のテスト」が残っているので、配信処理を集約したあとにそのテストを流せば、「既存の送信が今も正しく動く」ことが自動で確認できます。テストが緑（全部成功）なら、安心して集約できる。

**テストがあるから、こわがらずに整理整頓できる**。これはリファクタリングの大原則です。テストは「動作を変えずに構造だけ変える」ことを保証してくれる安全網なのです。

### Step 5-7: 引き出し5「新機能の追加は既存を揃える好機」

**引き出し**：新機能を足すとき、同じ判断が複数箇所に散らばっているなら、**コピペで増やさず、1 箇所に集約（郵便係化）する好機** と捉える。機能追加と整理整頓を同時にやると、コードが前より整う。ただし整理は「今いじる機能と地続きの範囲」に留める。集約の安全網は **既存のテスト**（緑なら動作が変わっていない証拠）。

**AI への指示テンプレ**

> この新機能（スレッド配信）を足すにあたり、既存の「配信を流す処理」が複数箇所に散らばっているなら、**1 箇所のメソッドに集約** してください。
> - 「親があればスレッド、チャンネル所属ならチャンネル、DM 所属なら DM」の判断を 1 箇所にまとめる
> - 送信・編集・削除のどれも、その集約した処理を呼ぶだけにする
> - 集約のあとに **既存のテストを実行** し、全て緑（動作が変わっていない）ことを確認してください
> - 整理は今いじる範囲に留め、無関係な箇所まで手を広げないこと

## Chapter 6: F-08 で増えた引き出しまとめ

最後に、ここまでの 5 つの引き出しを **AI への指示テンプレ集** として 1 箇所にまとめます。次に別機能を実装するときは、ここから引いて貼ってください。

### 6-1: 引き出し一覧（再掲）

| # | 引き出し | 一行で言うと |
|---|---|---|
| 1 | 木構造を1階層に固定 | 入れ子は何階層まで許すか決める。深い木は破綻するので根に付け替える |
| 2 | 絞り込みで見せ分ける | 同じ箱のデータを、フィルタ条件で別々の画面に見せる |
| 3 | 権限は親から継承 | 子を見ていい人＝親を見ていい人。専用ルールを作らない |
| 4 | 配信先は見え方の設計 | ライブで見えるものと再読込で見えるものを一致させる |
| 5 | 新機能は既存を揃える好機 | 散らばった分岐を1箇所に集約。安全網は既存テスト |

### 6-2: AI への指示テンプレ集

**入れ子になりうるデータ（返信・コメント）を扱うとき**

> スレッドは 1 階層に固定。返信は常に根にぶら下げ、返信への返信は根に付け替える。深い入れ子は作らない。

**複数の画面に同じ種類のデータを見せるとき**

> 同じテーブルに保存し、絞り込み条件で見せ分ける。「親を持たない＝一覧」「親が X＝サブ画面」。専用テーブルは安易に作らない。

**子リソースの権限を決めるとき**

> 子の権限は親リソースの権限を継承する。専用の権限ルールを作らず、既存の親の判定を呼ぶ。権限の二重定義を避ける。

**リアルタイム配信の流し先を決めるとき**

> 配信先は「見え方」の設計。保存（履歴）の見え方と必ず一致させる。ライブで見えたものが再読込で消える食い違いを作らない。

**新機能を足すついでに既存を整えるとき**

> 散らばった同種の分岐は 1 箇所に集約する。集約後は既存テストを流して動作不変を確認。整理は今いじる範囲に留める。

### 6-3: F-04 / F-05 / F-06 / F-15 とのつながり

F-08 の引き出しは、これまでのノートと地続きです。

- **絞り込みで見せ分ける（引き出し2）** は、F-04 チャンネルの「可視性チェックを 1 本のクエリで」の延長。「同じデータを、見る人・条件で違う顔に見せる」という一貫した考え方。
- **権限は親から継承（引き出し3）** は、F-04 / F-06 で作った「メンバーかどうかの判定」をそのまま再利用したもの。F-06 の「既存パターンを伸ばす」が、ここでは「既存の権限判定を継承する」形で効いている。
- **配信先は見え方の設計（引き出し4）** は、F-05 で学んだ「放送（Pub-Sub）の仕組み」の上に乗っている。仕組みを知ったうえで「どこに流すか」という一段上の設計判断をした。
- **新機能は既存を揃える好機（引き出し5）** は、F-15 の「再利用と結合の天秤」と表裏一体。F-15 は「安易に依存させない（分ける）」判断、F-08 は「散らばりを 1 箇所に集める（まとめる）」判断。**「分ける」も「まとめる」も、目的は "変更しやすさ" を上げること**。状況でどちらに倒すかが設計。
- **1 階層に固定 / チャンネルミラーは作らない（引き出し1・4）** は、F-04 / F-05 / F-15 で繰り返してきた「MVP では◯◯を割り切る・今は作らない」という、やらないことを決める姿勢の続き。

### 6-4: 次に役立つ視点

スレッドで学んだ 5 つは、チャット以外でも繰り返し登場します。

- ブログのコメント・SNS のリプライ・タスクのサブタスク → **引き出し1（入れ子の階層を決める）**
- 1 つのデータを一覧・詳細・絞り込みビューで見せる全機能 → **引き出し2（絞り込み）**
- 投稿への添付・いいね・編集履歴など「何かにぶら下がるもの」の権限 → **引き出し3（親から継承）**
- 通知・実況・ライブ更新を伴う全機能 → **引き出し4（配信先＝見え方）**
- 機能追加のたびに散らかるコード → **引き出し5（集約の好機）**

次にどんな機能を AI に任せるときも、「これは F-08 のどの引き出しが効くか?」と自問するクセをつけてください。「これは入れ子だから階層を決めよう」「これは子だから親の権限を継ごう」「配信先は履歴と揃えよう」と言えるようになると、AI に対して **「何を・なぜ」そう作るのかを指示できる** ようになります。これが上級編で目指す「AI を前提にしてアプリを作る」スタンスそのものです。

## おわりに

F-08 スレッドは、コード量こそ少なく、土台（F-05 / F-06）の上にすっと乗る機能でした。でもその「すっと乗った」こと自体が、実は一番の学びかもしれません。

F-05 のときに送信処理へ「親を指定できる入り口」を用意し、メッセージを「親の有無」で見分けられる形にしておいた。F-04 / F-06 で「メンバー判定」を作っておいた。それらの **過去の小さな設計の積み重ねが、F-08 を薄く・簡単にした** のです。逆に言えば、もし過去にそれらを雑に作っていたら、F-08 はもっと苦労したはずです。

このノートの中で 1 つだけ「絶対に忘れたくないもの」を選ぶなら、Chapter 4 の **「配信先は見え方の設計」** です。「どこに流すか」を技術配線の問題だと思っていると、案B（チャンネルにも流す）を選んで、ライブと履歴が食い違う罠にはまります。「配信は UX の設計だ」「保存と見え方を一致させろ」と意識できるかどうかが、リアルタイム機能の質を分けます。

次の機能に進むときは、まず「これは F-08 のどの引き出しが効くか?」を自問するところから始めてみてください。
