# 「Slack 風」をどう捉えるか — RaiseChat 設計の前提

関連: [要件定義書](requirements.md) / [機能要件書](functional-requirements.md)

本書は RaiseChat の要件定義の前段として、**「お客様が『Slack 風のチャットアプリを作って』と言ったときに、何を期待しているのか」** を読み解くための分析ドキュメントである。  
要件定義書（`requirements.md`）の機能スコープ・スコープ外・非機能要件の判断根拠を、本書の第 4 章にぶら下げる。

---

## 1. お客様が「Slack 風」と言うときの期待値

「Slack 風」という発注言葉は、見た目（サイドバーにチャンネル一覧、中央にメッセージ、右にスレッド）を指すだけではない。実際には、**Slack が業務の中で提供している体験価値**ごと再現してほしいというニュアンスを含む。

### 1.1 業務利用が前提になっている

Slack はパーソナルな SNS ではなく、**仕事のコミュニケーション基盤**として広まった。お客様が「Slack 風」と言う背景には、以下のような業務シーンが暗黙の前提として置かれている。

| シーン | Slack で起きていること |
| --- | --- |
| 朝会・進捗共有 | チームのチャンネルに「今日やること」を投稿する |
| 開発の議論 | スレッドで個別トピックの会話を分岐させる |
| 障害対応 | 専用チャンネルを立て、関係者を招待し、時系列で記録を残す |
| ナレッジ参照 | 「過去に同じ議論あったよね？」と検索する |
| 軽い意思表示 | スタンプ（絵文字リアクション）で「了解」「ありがとう」を伝える |

→ **「業務の会話が、後から検索できる形で蓄積される」** ことが Slack の中核体験である。

### 1.2 LINE や Discord の代わりにならないか？という問い

お客様が Slack を選んだということは、その時点で **LINE（プライベート寄り）や Discord（コミュニティ・ボイス寄り）では満たせなかった要件がある** ことを意味する。具体的には次のあたり。

- 仕事の文脈で **チャンネルを話題ごとに整理したい**（LINE のグループ単位だと粒度が粗い）
- **スレッドで会話を分岐させたい**（Discord は基本的に 1 チャンネル 1 ストリームで流れていく）
- 過去ログを **全文検索で引きたい**（LINE はトーク内検索が貧弱、Discord は検索体験が弱い）
- **ワークスペース単位**でメンバー管理・権限管理をしたい

つまり「Slack 風で」という言葉は、**「他の選択肢ではなく、Slack の体験を選んだ理由」を理解した上で作ってほしい** という要求である。

## 2. 競合ツールとの比較

ビジネスチャット領域の主要プレイヤーを並べ、Slack の位置付けを相対化する。

| ツール | 主な強み | 主な弱み / 制約 | 想定ユースケース |
| --- | --- | --- | --- |
| **Slack** | チャンネル設計の自由度・スレッド・全文検索・絵文字リアクション・外部連携の豊富さ・洗練された UX | 無料プラン制限（メッセージ履歴 90 日）・コスト・音声/ビデオ会議は別ツール併用が主流 | スタートアップ〜エンタープライズの社内コミュニケーション、エンジニア組織 |
| **Microsoft Teams** | Office 365 / Outlook / Teams 会議とのシームレス連携、エンタープライズ統制 | UI が重く感じられる、スレッド体験が Slack ほど洗練されていない | Office を全社導入している企業、会議＋チャットを一本化したい組織 |
| **Chatwork** | 日本企業向けにローカライズ、タスク管理機能を内包、シンプル | グローバル機能・外部連携・スレッド体験は限定的 | 国内中小企業、業務連絡＋タスク管理を一体化したい組織 |
| **LINE WORKS** | LINE と同じ UI、勤怠・カレンダー・掲示板など業務機能、社外メンバー（LINE ユーザー）と繋がりやすい | チャンネル設計の自由度は低め、開発者向け連携は弱い | 現場業務（小売・サービス業）、LINE 文化に親しんでいる組織 |
| **Google Chat** | Google Workspace との統合、Gmail からシームレスに使える | スタンドアロンでの体験は薄く、Workspace 前提 | Google Workspace を全社導入している組織 |
| **Discord** | 高品質な音声/ビデオ通話、ロールベース権限の細粒度、ボット文化、コミュニティ運営機能 | 業務向けの整理（経費精算・人事連携）には弱い、スレッド体験はあるが二次的 | ゲームコミュニティ、配信、オンライン勉強会、社外コミュニティ運営 |
| **Mattermost / Rocket.Chat** | OSS でセルフホスト可能、データガバナンス | 機能・連携・運用負荷で SaaS に劣る | セキュリティ要件で自社管理が必須な組織、開発実習 |

## 3. Slack が選ばれる理由（差別化要因）

上記の比較から、Slack が「業務チャットの第一想起」になっている理由を 5 つに整理する。これが **RaiseChat で再現すべきコア体験** となる。

### 3.1 チャンネルベースの情報整理

- 話題ごとにチャンネルを立てる文化（`#general`、`#dev-backend`、`#random` のような）
- パブリック / プライベートを使い分け、必要な人だけに見せる
- 結果として「あの議論はあのチャンネル」というメンタルマップが作られ、情報のサイロ化を防ぐ

### 3.2 スレッドによる会話の分岐

- メインのチャンネル流れを汚さずに、特定メッセージに対する深掘り議論ができる
- スレッドビューが独立しているため、後から見返しやすい
- これが他ツール（特に Discord）との大きな体験差

### 3.3 強い全文検索

- ワークスペース全体を横断検索できる
- 「過去に同じ議論あったよね」を再利用できることで、ナレッジが蓄積される
- 検索を前提に投稿する文化が育つ

### 3.4 絵文字リアクション

- 一言で意思表示できる軽量フィードバック（👍 ✅ 🙏 など）
- コメントを書くほどではないが反応を返したい、というニーズに刺さる
- 通知ノイズを増やさずにエンゲージメントを示せる

### 3.5 外部サービス統合

- GitHub・PagerDuty・カレンダー等からの通知をチャンネルに集約
- 「業務の情報がチャットに集まる」ハブとして機能する
- → RaiseChat ではここまでは MVP に含めない（後述）

## 4. RaiseChat への落とし込み

第 3 章で挙げた差別化要因のうち、本プロジェクトの **学習目的（RaiseTech 上級編）と工数** を踏まえて取捨選択する。

### 4.1 MVP に必ず入れるもの（Slack 風を名乗る上で外せない）

| 機能 | 理由 |
| --- | --- |
| ワークスペース + チャンネル（パブリック / プライベート） | 3.1 の前提。これがないと「Slack 風」と呼べない |
| チャンネル内テキストメッセージ + WebSocket リアルタイム配信 | チャットアプリの土台。上級編テーマ（WebSocket）の中核 |
| スレッド（返信） | 3.2 の差別化要因。Discord でも代替できないコア体験 |
| メッセージ全文検索 | 3.3 の差別化要因。Slack らしさの根幹 |
| 絵文字リアクション | 3.4 の差別化要因。実装コストの割に体験差が大きい |
| メンション + 未読 / メンション通知 | 業務利用前提なら必須。見逃したくない情報を浮かせる |
| ダイレクトメッセージ | 公開チャンネルに出せない会話を受ける受け皿 |
| マークダウン記法・ファイル添付 | 業務利用前提なら最低限の表現力 |
| メッセージ編集・削除 | 誤投稿の訂正は業務チャットでは必須 |
| プロフィール（アバター・表示名・ステータス） | 誰が発言したか可視化するため |
| 招待・キック等のオーナー権限 | ワークスペース管理の最低限 |

### 4.2 スコープ外にする機能（理由を明示して切る）

| 機能 | 切る理由 |
| --- | --- |
| ボイスチャンネル / ハドル | Slack の主軸ではない（むしろ Discord の主軸）。WebRTC は本プロジェクトの学習スコープ外 |
| 音声・ビデオ通話 | 同上 |
| カスタム絵文字のアップロード | 標準絵文字リアクション（F-11）で 3.4 の体験は再現可能。運用機能の比重が大きく、上級編テーマとは離れる |
| Bot / 外部サービス連携（GitHub・Webhook 等） | 3.5 の体験はあるが、API 設計と運用が重く、学習主題（リアルタイム性・キャッシュ・冗長化）から逸れる |
| モバイルネイティブアプリ | Web で十分。React Native などは別領域 |
| ワークフロー / フォーム自動化 | 高度機能。MVP には不要 |
| 多言語化・国際化 | 学習用途では日本語のみで足りる |

→ これらの結論を `requirements.md` の **第 9 章「スコープ外」** にそのまま転記する。

### 4.3 上級編の学習目的として強調するポイント

本プロジェクトは「Slack の機能再現」自体が最終目的ではなく、その実装を題材にして **以下の上級編テーマを身につける** ことが本旨である。

| テーマ | RaiseChat での扱い |
| --- | --- |
| **WebSocket リアルタイム通信** | Spring Boot の STOMP over WebSocket でメッセージ・リアクション・タイピング表示等をプッシュ配信 |
| **Redis キャッシュ戦略** | 直近メッセージ・チャンネル一覧・未読カウンタ等を Redis に寄せ、DB 負荷を下げる |
| **冗長化構成 / スケーリング** | バックエンドを複数インスタンス化した際に Redis Pub/Sub を介してメッセージをブロードキャストする（STOMP の単一プロセス限界を超える設計） |
| **自動デプロイ / IaC / Ansible** | AWS（ECS Fargate + ElastiCache + RDS + ALB + S3）を採用。Terraform による IaC、GitHub Actions → ECR → ECS の自動デプロイ、運用 EC2(bastion) を題材にした Ansible プロビジョニングまで実装（[docs/infrastructure.md](infrastructure.md)） |
| **Claude Code 自動コードレビュー** | 実装が一通り揃った段階で `.github/workflows/claude-code-review.yml` を導入し、複数機能が乗った PR で動作確認（トークン消費を考慮し、最終課題提出時の運用判断は別途） |

これらは要件定義書の **第 4 章「非機能要件」** に **目標値**（例: メッセージ送信から表示まで 1 秒以内、複数バックエンドインスタンス間でメッセージブロードキャスト可能）として落とし込む。実装方式（STOMP / Pub/Sub の選択）は機能要件側には書かず、設計フェーズの [docs/realtime-design.md](realtime-design.md) / [docs/cache-strategy.md](cache-strategy.md) で確定済み。

---

## 5. 結論

RaiseChat は **「業務チャットとして使われた Slack の体験」をミニマムに再現する Web アプリケーション** として設計する。

- 中核機能は **チャンネル + スレッド + 検索 + リアクション + メンション**（第 4.1 節）
- 切るものは **ボイス・通話・Bot・外部連携・モバイルアプリ**（第 4.2 節）
- 実装を題材に **WebSocket / Redis / 冗長化 / 自動デプロイ / Claude Code レビュー** という上級編テーマを学ぶ（第 4.3 節）

要件定義書本体（`requirements.md`）と機能要件書（`functional-requirements.md`）は、本書の第 4 章を根拠として書く。
